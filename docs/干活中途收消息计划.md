# 干活中途收消息计划（T11.7）

> 状态：Tony 2026-11-07 提出并说开工。Claude 窗口已提交 1.0.24，待验收；Codex 窗口未做，等 Tony 定（见 §5）。总览见 [`改进计划总览-2026-10.md`](./改进计划总览-2026-10.md)。

## 1. 起因

Tony 看 dsh-superagent 的介绍视频，问能不能「临时插入消息阅读」：agent 正在干活时来了新消息，下一步就能读到，不用等这一轮干完。

我们原来的做法：消息一律等窗口这一轮结束、空闲了，才往终端里打字投递（`idle-deliver.ts`）。管理者发一句「停，做偏了」，执行要把手上这一轮做完才看得到。

查了本机装的两个 CLI 本身支持什么：

- **Claude Code 2.1.302**：PostToolUse / PostToolUseFailure hook 可以返回 `hookSpecificOutput.additionalContext`，模型下一步就能看到。2026-11-07 用 `claude -p --model haiku` 实测过：hook 在 Read 之后插了一句带暗号的话，模型在回答里原样复述了暗号。
- **Codex 0.166.0**：hooks 已是稳定功能，PostToolUse 也有 `additionalContext`。但只靠启动参数启用 hooks 要加 `--dangerously-bypass-hook-trust`，这个参数会让用户自己配置的、项目目录里的 hooks 也一起免审核运行。

## 2. 已定的事

- 不往终端里打字：走 hook 的附加上下文，所以和「输入框有字就不投递」不冲突。
- 只插上级和用户本人（「待你拍板」点的选项）的消息。下级汇报、平级消息照旧等这一轮结束再提醒，免得打断。
- 未读全是该插的：把正文插进去，读出即标记已读，空闲时的提醒随之撤掉。未读里还夹着不急的：只插一句「谁发来几条，做完这一步先读收件箱」，不标已读（收件箱游标只能整体往前走，不能只标一部分）。
- 同一批只说一次：最新那条该插的消息没变，就不再说。
- 每调用完一个工具问一次，CLI 等着 hook 退出，所以只等 800ms，取不到就算了，这一轮结束还有原来的提醒兜底。
- Codex 先不做（§5）。

## 3. 代码

- 新模块 `main/workbench/mid-turn-inbox.ts`（纯函数）：`planMidTurnInbox(unread, lastAnnouncedId)` 返回不插 / 插正文 / 插一句提示。
- `mcp-tools.ts` 的 `takeMidTurnInbox`：读未读，按「用户本人或上级」分类，插正文时复用 `takeInboxDigest`（标已读、撤提醒）。
- `handlers.ts`：控制通道新请求类型 `inbox-midturn`，按窗口记上次插过的那条（只放内存）。
- `mcp/workbench-hook.ts`：PostToolUse / PostToolUseFailure 上报之后请求 `inbox-midturn`，有内容就输出 `additionalContext`。
- 只对用 `--settings` 装了我们 hooks 的 Claude 窗口生效（含 DeepSeek 窗口，它跑的是 Claude）。

## 4. 限制

- 只在工具调用之间生效。窗口在跑一条很长的命令、或者一直在想不调工具，就得等那一步结束；这时仍靠原来的空闲提醒。
- 插的是正文时已标记已读；模型如果没理会，平台不会再提醒同一批。

## 5. 待定：Codex

要做的话：启动时用 `-c` 传 hooks（PostToolUse 指向同一个 hook 脚本），并加 `--dangerously-bypass-hook-trust`。代价是这一次启动里，用户在 `~/.codex` 里自己配的 hooks、项目目录 `.codex/hooks.json` 里的 hooks 也都免审核运行，打开别人的仓库时有风险。另外 Codex hooks 的 TOML 写法要实测。等 Tony 定做不做。
