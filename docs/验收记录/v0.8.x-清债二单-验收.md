### 1.3 那次 `as unknown as RequestInit` 的护栏

`withDispatcher` 里确有一次 `as unknown as RequestInit`（两套同形 undici 类型声明漂移所致，模块注释已写明理由）。
**护栏确实存在且有效**，核实如下：

- `provider-proxy.test.ts` 自写最小 HTTP 代理（`startMockProxy`），**CONNECT 隧道**（`server.on("connect")` 记 `host:port`）
  与**绝对形式转发**（`createServer` 回调记完整 URL）两种形态都记账，断言只看"代理见到了这次请求"，不把实现细节写死。
- 判决性在于：断言 `proxy.seen.some(entry => entry.includes(target.authority))` 为真。若 `dispatcher` 因类型漂移
  或实现回退而**未被 fetch 采纳**，请求会直连目标、`proxy.seen` 为空数组 → 测试立刻红。**这正是"流量真走了代理"的证明**，
  而不是"对象形状看起来对"。反向对照用例（「没配 proxy：直连目标，代理零记录」断言 `proxy.seen` 恰为 `[]`）排除了
  "代理记录恒为真"的伪通过。
- 做法沿用 W1.5c：**不打桩 fetch**（桩掉 fetch 就把被测对象一起桩掉了），真实走网络栈。

✅ 断言有真实代理服务器单测钉住，结论成立。

## 2. 抽查发现

**未发现声明与实现不符之处，未发现红线被绕开，未发现真实失败。** 以下三条是抽查中记录的口径偏差与
加固建议，**均不影响事实正确性，不构成不通过理由**。

1. **`timedFetch` 的调用点实为 5 处，不是 4 处。**
   分别是 `fetch-models.ts` 2 处（openai_compatible / anthropic）与 `test-connection.ts` 3 处
   （/models · chat 回退 · anthropic messages）。diff 里 `fetchImpl: params.fetchImpl` 恰为 5 行，
   **覆盖完整、无一漏接**，故这只是交付方口头报告里的计数偏差（进度文档正文未给出该数字，**落档无误**）。
   记此一条是为了让"逐处对上"这件事有据可查。

2. **`resolveProbeKey` 落在 `try` 之外，ProxyAgent 的关闭窗口比它应有的窄一点。**
   两个 handler 的次序是「解析 outlet（可能已 `new ProxyAgent`）→ `await resolveProbeKey(request)` → `try/finally`」。
   而 `revealSecret` 是**会抛的**（`SecretNotFoundError` / 后端不可用；见 `main/secrets/store.ts:45,56` 的契约声明）。
   一旦它抛在这个窗口里，`agent.close()` 就不会执行。
   **实际危害很小**：此刻还没发出任何请求，ProxyAgent 里没有任何 keep-alive 连接——而 `close()` 要防的恰恰是
   "连接随每次点击累积"，故泄漏的只是一个空调度器对象，且异常会正常上抛为 IPC 错误、不静默。
   **建议（不阻塞，下次触碰该 handler 时顺手改）**：把 `resolveProbeKey` 一并挪进 `try`，让"构造出来的 agent
   一定会被 close"成为无条件成立的性质，而不是"取密钥不抛时才成立"。

3. **`formFromProvider` 的读入侧没有单测，往返闭合是"读代码 + 类型"确认的。**
   `buildProviderDraft`（写出侧）有 2 项新单测；而 `formFromProvider` 住在 `ProviderEditorDialog.tsx` 里、
   不属于可单测的纯逻辑模块，故"手工 proxy 值编辑后不丢"这条**由代码与类型保证、无用例钉住**。
   E2E `create-provider.spec.ts` 走的是新建路径，也未覆盖"读回已存 proxy 再保存"。
   本次验收对这条的核实方式是读三处代码（`formFromProvider` 的 `provider.proxy ?? ""` · `buildProviderDraft` 的条件展开 ·
   `providers:update` 的整表替换语义）并确认闭合。**建议（不阻塞）**：日后若把 `formFromProvider` 下沉进
   `provider-form.ts`（与 `buildProviderDraft` 同处），顺手补一条"provider → form → draft 往返恒等"的用例——
   那才是能在漂移时先红的做法。
   顺带记一处**刻意的取舍**（非缺陷）：`cli_login` 类型下 proxy 一律省略，故手工给 cli_login 写的 proxy 值
   在编辑后仍会被丢弃。这与 `baseUrl` 受 `usesBaseUrl` 门槛约束的既有口径一致，且 cli_login 的网络由 CLI 自管、
   本就不消费该字段。

**另记两条正面观察（非偏差）**：

- **接缝的位置选对了。** `contracts.ts` 里把 proxy 与 provider **分列两个字段**而不是塞进 `ProbeProviderInput`，
  并在注释里写明理由（"塞进去会让任何直接调用 core 的人以为传了就生效——那是一个静默失效的陷阱"）。
  这是把"不会生效的配置"在类型层面就变得不可表达，比事后文档提醒强。
- **W2.4 的替代断言比原断言覆盖更宽。** 原用例带 `it.runIf(process.platform === "win32")`，在非 Windows 上是空跑；
  改写后的"不钉基底"断言无平台门槛，三平台都会跑。删代码的同时把守卫的适用面扩大了。
