# 计划评审与结构化汇报计划

> 状态：Tony 2026-10-24 要求写计划。未开工，未改版本。总览见 [`改进计划总览-2026-10.md`](./改进计划总览-2026-10.md)。

## 1. 为什么做

现在的流程是：管理者写计划（或派规划写）→ Tony 拍板 → 直接执行 → 检查看 diff。**执行前没人挑计划的毛病**，计划层面的错到检查时已经变成代码。cc-pane 有跨模型评审（Claude 写、Codex 审），我们没有。

但多轮讨论有 Tony 指出的老问题：一方不停提新问题和细节，陷进细节里出不来；回合数一限，该细的没细，不该细的反而很细，问题还剩一大堆。

原因是两样东西缺了：**哪些地方该细没人规定；什么时候算讨论完也没有标准。** 光限回合数是硬砍，砍掉的不一定是不重要的。

## 2. 计划分三层，每层写明细到什么程度

规划和管理者写计划时用这个模板：

| 层 | 写什么 | 细到什么程度 |
|---|---|---|
| 目标层 | 目标、不做什么、验收标准 | 必须精确：能判断「做完没有」 |
| 边界层 | 改哪些文件或目录（每个执行一份清单）、窗口之间的接口、不可逆操作、独占资源（Unity 等）、风险 | 必须精确：这里错了代价最大 |
| 实现层 | 具体怎么写 | **交给执行**。只写方向，评审不在这一层提意见 |

另加一节 **「反驳项」**（借 zf3d_agent）：写计划的人自己列出这个方案最可能错在哪，评审必须逐条回应。

这就是 cc-pane 说的「先冻结契约，再放并行」：细节放在不可逆、跨窗口的地方，其余留给执行。执行遇到计划没覆盖的情况，本来就报 blocked（`worker.md`），不用事先讨论穷尽。

## 3. 评审规则

### 3.1 谁来评审

- 管理者主持，评审窗口只读（`read-only`），一到两个。
- **换模型或换账号**：Claude 写的计划给 Codex 审，反过来也行。同一个模型多开几个，盲区是一样的。
- 一个项目只有一个管理者，不开多个管理者互相讨论。

### 3.2 什么时候必须评审

满足任意一条就评审：

- 要开两个以上执行；
- 跨三个以上目录或模块；
- 有不可逆操作（删数据、迁移、改存档格式、发布）；
- Tony 要求。

小改动（单文件、几十行）不评审，管理者直接派。

### 3.3 问题分级、限量

每条问题必须标：

- 级别：**阻断**（计划错了、做不到、不安全）/ **重要** / **细节**；
- 所在层：目标 / 边界 / 实现；
- 位置（计划里哪一节）；
- 证据：阻断级必须附实际读过的 `文件:行号` 或实际跑出的输出，没有证据不收；
- 建议。

规则：

- 每位评审每轮**最多 5 条阻断加重要**，按严重程度排。名额有限，评审自己会挑重要的说。
- **细节不进讨论**，直接写进计划末尾的「执行注意事项」，交给执行。
- 实现层的问题一律降为细节。

### 3.4 两轮收口

- 第一轮：自由提。
- 第二轮：只核对第一轮的问题改好没有；**不提新问题**，除非是带证据的阻断级。
- 第二轮之后剩下的：
  - 有分歧的 → `ffpane_request_decision` 交 Tony 拍板（每次一件事，现有规则）；
  - 细节 → 执行注意事项；
  - 新想法 → 计划末尾「以后再说」。
- 两轮后还有阻断级：说明任务太大或信息不够。**不继续讨论**：拆小，或先派一个执行做只读调研或小原型，拿到结果再定。

回合数限制因此不会造成「细节没讨论全」：细节本来就不在这一步讨论，而且都有记录、有去处。

### 3.5 问题台账

每份计划一个台账：`.ffpane/reviews/<计划名>.md`，由平台按评审提交生成，不靠模型手写格式。

每条：编号、级别、所在层、提出者、轮次、状态（待定 / 采纳 / 否决 / 延后 / 交拍板）、处理说明。**否决过的不许重提**；同一条再提，平台直接退回并指向原编号。

计划定稿时**整体重写**计划（cc-pane 的做法），不在末尾追加「修改纪要」；否决项在计划顶部「已评审决议」记一笔。

## 4. 工具（规则靠代码）

### 4.1 新工具 `ffpane_submit_review`

评审窗口用它交评审，不用 `ffpane_report` 写散文。

- 参数：`planPath`（`.ffpane/briefs/` 内）、`findings[]`（每条含 level、layer、location、evidence、suggestion、可选 `refersTo` 编号）、`verdict`（可以开工 / 改后开工 / 不能开工）。
- 平台校验，不合格就退回并说明原因：
  - 阻断级没有证据；
  - 阻断加重要超过 5 条；
  - 第二轮出现新的非阻断问题；
  - 第三轮（同一计划同一评审已交两轮）；
  - 重提已否决的问题。
- 实现层的问题自动降为细节。
- 轮次由平台按 `planPath` 加评审窗口计数。
- 通过后写台账，并把摘要投给管理者。

### 4.2 新工具 `ffpane_resolve_review`

管理者逐条处理：采纳 / 否决（必须写理由）/ 延后 / 交拍板。交拍板的条目直接带进 `ffpane_request_decision` 的计划 brief。

### 4.3 完成汇报带检查结果

借 superset 的「worker 结束必须交固定格式」。`ffpane_report` 现在已有 `files`、`detailPath`，再加：

- `checks[]`：每条一个命令和结果（通过 / 不通过 / 没跑），可附一行说明。
- 执行窗口报 `done` 时：`detailPath`、`files`、`checks` 必填；确实没有可跑的检查时，填 `noChecksReason`。缺了就退回。
- 检查窗口报结论时同样要 `checks`。
- 管理者和监管者看汇报时，「改了哪些文件、跑了什么、结果如何」一眼就能看到，不用读正文猜。

## 5. 说明书

- `planner.md`：用三层模板写计划，必须有「反驳项」。
- `reviewer.md`：加「计划评审」一节，讲分级、限量、证据、两轮规则，说明用 `ffpane_submit_review`。
- `manager.md`：加「什么时候必须评审」和收口规则；注意 2KB 上限。说明书放不下的长模板，等[按需手册](./按需手册计划.md)落地后挪进去。
- `worker.md`：done 必须带检查结果。

## 6. 验收

1. 单测：`ffpane_submit_review` 的五种退回；实现层自动降级；台账生成；否决项重提被拦。
2. 单测：执行报 done 缺 `checks` 被退回；有 `noChecksReason` 放行。
3. e2e：规划写计划 → 两个评审（一个 Claude、一个 Codex，e2e 用假 CLI）交两轮 → 管理者处理 → 一条交拍板 → Tony 点选 → 计划重写 → 派执行。
4. 真项目试一次（《海上生存日记》里挑一个跨多个目录的任务）：记录轮数、每轮问题数、交拍板数、执行阶段报 blocked 的次数，和以前不评审的同类任务对比。

## 7. 风险

- 模型不按格式交：工具退回时写清楚怎么改，退回两次就报给管理者。
- 评审变成形式主义（每轮都凑满 5 条）：台账里统计「被采纳率」，长期偏低就调规则。
- 成本：一份计划多一到两个评审窗口、最多两轮。只在 §3.2 的情况下做。
