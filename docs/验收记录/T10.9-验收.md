## 2. A · 测试解析走 src 还是 dist

### 2.1 现在怎么解析

根 `vitest.config.ts` 用 `test.projects` 扫 `packages/*` 和 `apps/*`，没有 `resolve.alias`，也没有把 workspace 包指到 `src`。`apps/desktop/vitest.config.ts` 同样没有 alias。根 `tsconfig.base.json` 和各包 `tsconfig.json` 都没有 `paths`。

五个 workspace 包的 `package.json` `exports` 都是 `types` + `default` 指向 `./dist/...`。没有 `development` 条件，没有指向 `src` 的入口。`electron.vite.config.ts` 的 main 段用 `externalizeDepsPlugin()`，桌面应用运行时同样 `require` 这些包的 dist，不是源码。

同包测试大多写 `from "../src/index.js"`，vitest 直接变换 TypeScript，改 src 立刻能看见。跨包写 `from "@ff-pane/core"` 这类包名时，Node 和 vitest 都落到 dist。

本单相关的两处：

- `packages/core/tests/workbench-can-set-role.test.ts` 从 T10.6 提交 `7e789ee` 起就 `import { canSetRole } from "@ff-pane/core"`。本单加的清洗锁用例走的是这条，不是 `../src`。
- `apps/desktop/tests/workbench-sanitize-role.test.ts` 导入的是桌面自己的 `set-role.ts`（源码）。这个文件再 `import { canSetRole } from "@ff-pane/core"`，裁决仍在 dist。

在 `packages/core` 目录执行 `import.meta.resolve`：

- `@ff-pane/core` → `packages/core/dist/index.js`
- `@ff-pane/shared` → `packages/shared/dist/index.js`

### 2.2 三个问题

**① 干净检出、没有 dist，直接 `pnpm test` 会不会失败。** 会。`dist/` 在 `.gitignore` 第 5 行，`git check-ignore` 认 `packages/core/dist/index.js`。根 `package.json` 的 `test` 只有 `vitest run`，没有 `pretest` / `postinstall` 构建。`pnpm-workspace.yaml` 的 `allowBuilds` 也不构建这些包。exports 指向一个克隆之后不存在的文件，跨包 import 会 `ERR_MODULE_NOT_FOUND`。

本轮没有删除仓库里的 dist 再实跑（验收不能改工作区，也不能 checkout）。依据是 exports、gitignore，以及 CI。`.github/workflows/ci.yml` 在 Test 之前有 Build，注释写着「Build 必须先于 Test：workspace 包的 exports 指向 dist/」。这条是提交 `b1b7493`（2026-08-29，`fix(ci): build before test — cross-package tests resolve workspace deps via dist exports`）放进去的。

**② 改了 src 但不构建，测试会不会仍拿旧代码。** 会。包名 import 执行的是 dist 里的 JS。旧 dist 若仍满足断言，测试通过，src 里的改动没有被跑到。这就是假通过。

反过来：断言已经改成新行为、dist 还是旧的，测试会失败。执行者说「单测前要先构建 core」，属于这一种，是假失败，逼人先构建。危险的是另一方向：src 里把清洗锁判断删掉、忘了构建，dist 里判断还在，`workbench-can-set-role` 和 `workbench-sanitize-role` 都会继续绿。

**③ 是本单引入的，还是既有约定。** 既有约定，不是本单引入。CI 从 2026-08-29 就这么写。T8.3a、T8.4、T8.7 的验收记录都写过：desktop 单测经包名吃 dist，同包测试吃 `../src`。`canSetRole` 单测从包名导入是 T10.6 留下的。本单新增的清洗锁断言沿用了这个入口，所以这条安全规则的单测不读 src。

### 2.3 这次绿能不能信

能信这一次，不能信下一次。

扫描 `packages/core`、`shared`、`adapters`、`storage`、`rag`：没有 `src` 的 `.ts` 比对应 `dist` 的 `.js` 更新。`can-set-role.ts` 的修改时间是 2026-10-01 09:20，编译产物是 09:31，产物里有 `sanitizeLocked` 判断。

`%TEMP%` 探针把 src 和 dist 的 `canSetRole` 对同一棵「`openedBy=user`、`sanitizeLocked`、`parentClosed`」的树各跑一遍。自设 `manager` / `worker` / `planner` / `reviewer` / `none` 两边都是 false。界面用户设 manager 两边都是 true。

所以本次 `pnpm test` 的 2631 项，对当前这棵树不是假通过。应用侧 `externalizeDepsPlugin` 同样用这份 dist，e2e 跑到的也是带清洗锁的 `canSetRole`。

### 2.4 建议修法

优先给 vitest 加 alias，把 `@ff-pane/core`、`shared`、`storage`、`adapters`、`rag` 指到各包 `src`。这样改 src 不构建，测试看见的就是新代码，假通过消失。只把 `workbench-can-set-role.test.ts` 改成 `../src` 不够：desktop 的 `set-role.ts` 仍从包名进 dist。

次选是把根 `test` 改成先 `pnpm -r run build` 再 `vitest run`，与 CI 对齐。这能避免「没 dist 就炸」和「忘了构建就测旧文件」，但测的仍是编译产物。构建若被跳过或增量编译没跟上，假通过还在。

桌面应用自己仍要构建 core 才能在 Electron 里跑到新代码。alias 解决的是单测，不是 `pnpm dev` / `electron-vite build`。

## 3. B · 路径、Markdown、打开文件

只读 IPC 用 `projectId` 在主进程 `listProjects()` 里找 `rootPath`，不采用渲染进程传来的项目根。`lexicalFfPanePath` 拒绝空路径、控制字符、绝对路径（含盘符和 UNC）、`..` 和 `.`。相对路径若不以 `.ffpane` 开头，会收进该项目的 `.ffpane`。`resolveFfPaneFile` 从真实项目根逐段 `lstat`，任一段 `isSymbolicLink()` 就拒绝；`realpath` 之后还要落在 `.ffpane` 里面。项目根本身是符号链接或 junction 时直接「项目根不可用」。

`%TEMP%` 探针（没有写应用数据目录，用完删除）：

| 路径 | 结果 |
|---|---|
| `../other/.ffpane/briefs/a.md`、`.ffpane/briefs/../../outside.md`、`C:/...`、UNC | 词法拒绝 |
| 兄弟目录 `proj` 与 `proj-evil`（名字前缀相同） | `readBriefFile` 拒绝，读不到对方的 `secret.md` |
| `.ffpane` 下的子目录 junction 指到外部目录 | `resolveFfPaneFile` 失败，错误含「符号链接或 junction」 |
| 项目根本身是 junction | 「项目根不可用」 |
| `.ffpane/briefs/CON.md` | 2 秒内返回「文件不存在」，没有挂住 |
| 256KB + 50 字节的 `big.md` | `ok`，`truncated: true`，返回字节数不超过 256KB |
| `.ffpane/threads/` 下的 `payload.exe`、`.bat`、`.cmd`、`.lnk` | `resolveFfPaneFile` 全部 `ok: true` |

文件符号链接在本机 `symlinkSync(..., "file")` 返回 `EPERM`，没有建成。单测 `workbench-panel.test.ts` 的「符号链接和 junction」在第一次 `symlinkSync` 抛 `EPERM` 时 `return`，junction 那段也不会跑。实现上 junction 和文件符号链接都走 `isSymbolicLink()`。junction 已由探针拒绝。文件符号链接没有在本机实证，建议把单测拆开，见文末。

**必须修复 ①：`shell.openPath` 能打开可执行文件。**

`handlers.ts` 的 `workbench:open-ffpane` 只调用 `resolveFfPaneFile`，成功后就把绝对路径交给 `shell.openPath`。没有 `.md` 判断。`readBriefFile` 倒是限制在 `briefs/*.md`。打开这条没有。

记录页按钮把 `.ffpane/threads/${record.threadFile}` 交给这条 IPC。`parseThreadLine` 把 JSON 整行收成记录，不检查 `threadFile` 是不是单个 `.md` 文件名。主进程写索引时用的名字以 `.md` 结尾；有编辑权限的窗口可以直接改 `index.jsonl` 并在 `.ffpane/threads/` 放一个 `.exe` / `.bat` / `.lnk`。用户点「打开」时，路径仍在 `.ffpane` 内，`resolveFfPaneFile` 放行，`shell.openPath` 按系统关联打开。在 Windows 上 `.exe`、`.bat`、`.cmd` 会执行，`.lnk` 会跟着快捷方式走。

计划页的「在系统中打开」目前只传列表里的 brief，列表本身只收 `.md`。边界仍应在主进程：渲染进程可以自己 `invoke` 任意相对路径。

建议修法：`workbench:open-ffpane` 在 `resolveFfPaneFile` 之后只接受真实文件、扩展名是 `.md`（大小写不敏感），拒绝 `.lnk` 以及任何其它扩展名。记录行的 `threadFile` 在解析时就要求是单个 `.md` 文件名，不要把索引里的字符串原样拼进打开路径。

**必须修复 ③：brief 超大文件先整读。**

`readBriefFile` 在确认路径之后执行 `readFile(resolved.absolute)`，再 `cutUtf8` 到 256KB。返回给界面的内容是截断的，探针也看到了 `truncated: true`。读的过程没有上限。计划页签打开时会自动选修改时间最新的一份并读取。窗口若把一份很大的 `.md` 写进 briefs，主进程会先分配整份 Buffer。索引那条已经用文件句柄只读尾部最多 1MB。brief 应按同样方式只读前 256KB。

**Markdown。** `apps/desktop/src` 下没有 `dangerouslySetInnerHTML`。`SafeMarkdownView` 把 `parseSafeMarkdown` 的块渲染成 `<p>` / `<pre>` / `<ul>` / `<blockquote>` 的文本子节点。解析器不建链接、不建图片。图片语法只留下方括号里的文字，URL 丢掉。链接语法变成「文字 (url)」纯文本，`javascript:` 也只是文字。标题和段落里的 `<script>`、`<img onerror>` 保持为文字。探针把这四段喂进去，结果里没有 `href` 或 `src` 字段。不加载远程资源，不执行脚本。

## 4. C · 移交两项，以及失败后能否再试

**连启。** 续接和重新开始的按钮在确认通过之后只调用 `onResume` / `onRestartFresh`。这两个回调只改 `resumeNext` 并 `setLaunchNonce(n => n + 1)`，不再自己调用 `relaunchWith`。`TerminalView` 里唯一跟着 nonce 走的是 `useEffect`：nonce 从 0 变成新值，或和上次不同，才 `relaunchWith`。渲染端 `createRelaunchGuard` 在持有期间第二次 `tryEnter` 返回 false。点击一开始就把 `relaunchBusyRef` 设为 true，同一次点击循环里第二个按钮进不去。取消确认走 `finishSensitiveLaunch(false)`，按钮的 `finally` 只在未接受时清忙，不会启动。权限「应用并重启」也只在窗口仍在运行时递增 `launchNonce`。

主进程 `launchCliWindow` 经 `createWindowLaunchGate` 按 `windowId` 复用进行中的 Promise。第一次结束后 `finally` 删掉表项。探针：第一次 `reject(new Error("boom"))`，第二次真正再执行并得到 `"ok"`，`started === 2`。失败不会把窗口卡死。进行中的第二次不会另开 PTY；失败或成功结算之后，下一次点击可以再启动。

单测覆盖的是「进行中复用、成功结束后可以再启动」和「闩持有期间拒绝」。失败后重试是探针补的，仓库单测里还没有这一条，见建议。

**清洗锁。** `canSetRole` 在调用者就是目标窗口时，若树上该节点 `sanitizeLocked === true`，直接 false，不看角色是不是 manager。探针覆盖了五种角色。界面用户分支在这之前返回 true。`workbench-sanitize-role.test.ts` 还看了注册表：自设 manager 得到 `forbidden`，角色仍是 worker，没有 `userRoleSet`，没有管理权；用户设回去会授予。MCP `setRole` 先用当前树调用 `canSetRole`，不允许就不调用 `deps.setRole`。

自设非 manager 本来就会被 T10.6 的规则拒绝（自设只可能是 manager）。本单补上的是「被锁住的顶层、`openedBy=user` 也不能自设 manager」。祖先设定后代不走这条自设拒绝。被清洗的窗口父级已经摘掉，通常没有还能设定它的祖先。

## 5. D · 抽屉与旧页面

抽屉 store 初始 `open: false`。没有侧栏或工作台工具条上的常驻按钮。呼出只有三处：MCP `workbench:open-panel`、命令 `workbench-open-plan` / `tasks` / `runs`。没有当前项目时，命令面板提示并 `navigate("/projects")`。Esc 和遮罩关闭。

`WorkbenchPanelBridge` 挂在路由里面，任何页面都收事件。`open_panel` 先 `setActiveProjectId(payload.projectId)`，再 `navigate("/workbench")`，再 `openPanel`。工作台页按当前项目挂 `WorkbenchDrawer`。人不在工作台时，会先切到该窗口的项目再打开抽屉。E2E「隐藏面板」和「打开任务页」开始时人已经在 `/workbench`，没有单独断言「先停在会话页再被呼出」。这段是读 `WorkbenchPanelBridge.tsx` 得到的。

计划：`listBriefFiles` 只收 briefs 里的 `.md`，按 mtime 倒序。未选中时选列表第一份，也就是最新的。预览走 `SafeMarkdownView`。超过 256KB 有截断提示。

任务：`columnOf` 优先用最近汇报的 `progress` / `blocked` / `done` / `failed`。没有汇报但 `running` 为真，进进行中。两者都没有，不进任何列。`running` 来自主进程未退出且 `metadata.windowId` 有值的 PTY。分组锚点是链上最上层的 manager；没有 manager 就用最顶上的窗口。管理者自己有列时会作为卡片放进自己的组，组标题仍是他的标题。E2E 点了 blocked 列里的「前端板」，窗口 `data-focused` 变成 true。卡片含标题、角色、权限、上级、汇报摘要；brief 链接只在路径以 `.md` 结尾时出现，点了是切到计划预览，不是 `shell.openPath`。

记录：索引只读尾部最多 1MB，半行丢掉，每页最多 40，倒序。筛选在已加载的记录上做：团队比 `threadFile`，窗口比 `from` / `to` 的 `windowId`，类型是 `message` / `report` / `system`。正文是纯文本。E2E 把类型选成 report 之后，「缺接口」还在，「开始吧」消失。

旧页面：`PAGE_SHORTCUT_ORDER` 是项目列表、工作台、会话、记忆、知识库。`LEGACY_PAGE_KEYS` 是 plan / tasks / runs，不进 `NAV_ITEMS`，所以没有侧栏项，也没有 Ctrl+N。`ALL_NAV_ITEMS` 仍包含它们，`AppRoutes` 仍挂 `PlanPage` / `TasksPage` / `RunsPage`。命令仍是 `nav-plan` / `nav-tasks` / `nav-runs`。中文标题是「转到计划页（旧版）」等，英文是 `Go to plan (legacy)` 等。`commandShortcutDisplay` 对 `nav-plan` 为 undefined。E2E 断言侧栏没有 Plan / Tasks / Runs，Ctrl+1~5 落到上述五个路由，Alt+← 回到记忆页。E2E 没有点开「旧版」那三条再看计划页内容；路由表和页面组件还在，本单没有改这三个页面的实现。
