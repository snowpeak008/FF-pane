#### A.4 对抗性探针（验收指令点名：合法字段夹带密钥形状值）

| 探针 | 结果 |
|---|---|

### B2. permissionPreset 缺省哨兵语义安全性复核（交付方备案 2，验收重点）

**口径：** Profile 草案 permissionPreset 缺省 → 解析器填哨兵 `PRESET_FROM_GLOBAL_DEFAULT`（config-tool.ts:481）→ 主进程识别（引用相等）替换为全局 `defaultPermissionPreset` 再校验（index.ts:402-406）。

**复核结论：口径安全，无静默权限放大路径。** 逐层论证：

1. **哨兵本体是最保守一侧**（config-tool.ts:494-500）：空读写 + 禁 shell + 禁网络 + 危险操作恒确认。即便主进程漏替换（哨兵漏进落盘），得到的是一个**过窄**而非过宽的 Profile——错误方向是「Agent 干不了活」，不是权限放大。单测 `mcp-config-tool.test.ts:195-200` 四维钉死；反向探针⑦证实（哨兵改宽松语义 → 该单测恰红，§3）。
2. **替换后再校验的顺序有保证**：index.ts:402-406 先替换（`draft.permissionPreset === PRESET_FROM_GLOBAL_DEFAULT` 引用相等判定——同进程内解析器产物直达 prepare，无序列化边界破坏引用，成立）→ `:407-410` **替换后的 draft** 走 `validateProfileDraft`。§7 清单在校验器内不可绕过：`dangerousOpsRequireApproval !== true` 即违规（core validate.ts:262-267）+ 预设 ⊆ 角色默认信封（`collectPresetViolations` `:91-128`，读/写/shell/network 四维逐一收窄检查）。
3. **落盘时二次校验**：apply 走 `profiles.createProfile(parsed.draft, validate)`（index.ts:461-470），validate 回调再跑一遍 validateProfileDraft——即便 prepare 与 apply 之间有任何状态漂移（如全局默认预设被并发修改），落盘前仍有一道。且 apply 消费的是 **normalized**（已替换哨兵的）草案（hub 存 pending 的是 prepared.normalized，`:202-206`）。
4. **显式给的 preset 也无放大口**：解析器把 `dangerousOpsRequireApproval` 无条件纠正为 true（config-tool.ts:397-398「模型给什么都不采信」，schema 声明 `const: true` `:188-192`，单测 `:202-217` 钉死）；宽于角色默认的预设被 validateProfileDraft 拒绝（invalid 回 Agent）。
5. **缺省 = 全局默认的语义等价性**：与设置页新建 Profile 预填全局默认（§4.4）同一语义——全局默认本身宽窄由用户自管，Agent 缺省提交得到的不多于用户自己新建会得到的。**无「缺省导致比显式提交更宽」的路径**。
6. 对话框呈现的是**替换后**的真实预设（hub publish 的 payload.draft 即 normalized.draft）——用户裁决时看到的就是将要落盘的权限，不是哨兵占位（ConfigDraftDialog `:86-89` 四维全渲染）。

**唯一理论缝隙（如实登记，不构成缺陷）**：哨兵识别用引用相等而非结构比较——若未来重构让草案跨序列化边界（如 hub 移进别的进程），引用会断、哨兵漏替换。但漏替换的兜底语义就是哨兵本体（最保守），且过窄的空读预设大概率触发「预设 ⊆ 角色默认」比较中 canonical 化后可见的行为差异（Worker 拿到空写权限干不了活），用户可感知。方向安全，登记备查即可。
