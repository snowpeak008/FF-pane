# 1.0.10 重开项目后续接不失忆、终端应答不再打断 Codex：改动与验收办法

**日期：** 2026-10-23
**状态：** 已提交（2026-10-23，版本 1.0.10），尚未单独验收。
**真机：** Claude Code 2.1.302、codex-cli 0.162.0（Windows 11 22631）。

## 1. 用户报的问题

团队因限流停下后，用户退出软件，第二天再打开项目：

1. GPT（Codex）监管窗口里的对话堆在一起，输不进去，像是差一个回车。
2. 窗口都还在，但管理者不会自己醒；用户手动让它继续以后，工作质量也明显变差。
3. 用户自己发现：监管者接的是自己在别处的对话，不是这个窗口原来开的那个。

## 2. 查到的原因（全部来自本机现场记录）

读了 `~/.aiworkbench/workbench-layouts.json`、项目 `.ffpane/threads/`、管理者的 Claude 记录（`afd1af3e…`）、监管者的两个 Codex 会话（`01a160eb…` 和 `01a1684d…`），以及 Codex 的 `state_5.sqlite`。

### 2.1 监管者原来的会话被 Codex 桌面版接走、归档

- 监管者原会话 `01a160eb` 由 FF-pane 开（`originator: codex-tui`，第一句是「你是 监管者 窗口，由 Claude 1 开启」）。
- 10-22 21:14:48 会话里出现一条 `thread_settings_applied`，带的是桌面版的设置（friendly 语气、桌面版协作模式）。1 秒后 `state_5.sqlite` 里它被标成 `archived: 1`，文件移进 `~/.codex/archived_sessions/`。
- FF-pane 和 Codex 桌面版共用同一个 `~/.codex`。同一个项目下，FF-pane 开的命令行会话会出现在桌面版的会话列表里，桌面版一打开就接管了它。
- 布局里这个窗口没有 `nativeSessionId`，只有 `conversations`。重开后点「续接」，平台走 `codex resume`（不带编号）。这个选择器会列出 `~/.codex` 里的所有会话，包括用户在桌面版的别的对话。
- 结果：10-23 18:28 开了一个什么都不记得的新会话 `01a1684d`。上级随后发来「[继续] 从停下的地方接着做」，它不知道该接什么。新会话每一轮都被打断（见 2.2），notify 从没报出编号，布局里也没记下。
- 核对过：FF-pane 从没往用户桌面版的别的对话里写过消息。被写入过的只有这两个监管者会话。

### 2.2 终端应答打断 Codex，乱码被当成用户消息提交

- 新会话里有三次被提交的「用户消息」：`[?1;2c]10;rgb:e7e7/eaea/f0f0\]11;rgb:0a0a/0d0d/1111\`（18:35、18:38 两份叠在一起、18:50）。每次都伴随 `turn_aborted: interrupted`。
- 这是界面 xterm 对 DA1、OSC 10、OSC 11 查询的应答（颜色正是 `readThemeColors` 的默认值）。窗格每次重新挂载（切标签、最大化、监管者开子窗口时自己的格子被一分为二、平台重启后接回），`TerminalView` 都把回放缓冲写进新的 xterm。回放里 Codex 启动时的查询被 xterm 再答一遍，应答经 `term.onData → terminal:write` 写进 PTY。
- 开头的 ESC 被 Codex 当成 Esc 键，打断正在跑的一轮。余下的字符进了输入框，平台投递时连同正文一起回车提交。
- 投递核对看输入框里是否还留着这条消息时，只比开头 12 个字是否在最前面（`prompt-ready.ts` 旧 171-172 行）。乱码在前时判成「已经提交」，正文其实还卡在框里，这就是「差个回车」。
- 新开、续接窗口时，回放前没清屏，回放期间到的实时输出会写两遍，查询也被答两遍。
- 用 `@xterm/headless` 复现：同一段回放每写一次，`onData` 就吐一次 `ESC[?1;2c`。

### 2.3 管理者重开后不会自己醒

- 10-22 20:31 管理者撞上 429，按 1.0.9 的规则限流暂停、等用户指令。10-23 18:23 软件重开，直到 18:23:52 用户输入「可以继续了」，管理者一直没动。
- 重开后旧窗口不会自动启动（`autoStart` 只给这次运行里新建的窗口），要用户点「续接」。点了以后平台不给它发任何东西：暂停记录、待处理计数都只在内存里，`[待处理]` 要先有一轮正常结束才发，管理者又没有上级来叫醒它。

### 2.4 管理者醒来后质量差：每到约 90k 就压缩

- 管理者窗口的压缩记录：10-17、10-18 约 490k 才压缩一次；10-18 晚加上压缩滑块（75%）后一律约 90k。这个会话累计压缩 31 次，10-23 18:29 到 20:07 就压了 6 次。每次压完一开工约 50k（系统提示、工具、角色说明），干活只剩约 40k。
- 从 Claude Code 2.1.302 程序里读出压缩点：E = 窗口 − 20000，压缩点 = min(E × 百分比, E × (1 − 缓冲比例))。缓冲比例默认 0.2，服务端可以下发别的值，本机反推是 0.5。
- 平台给 Claude 一律设 `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000`，E = 180k，压缩点 = 90k；不设时 Opus 5.5 窗口是 1M，压缩点 = 490k。两个数都和现场一致。
- T10.20 时「只设百分比往往不生效」，原因是百分比不会比缓冲更晚。为了让它「生效」把窗口设成 200k，等于把 1M 窗口砍到了五分之一。

## 3. 改了什么

| 问题 | 做法 | 代码 |
|---|---|---|
| 旧应答打断 Codex | 主进程闸门：PTY 输出里出现查询（DA1/DA2、光标位置、状态、OSC 10–19 和 4、DECRQM、kitty 键盘、窗口尺寸）就记一个 3 秒的到期时间；界面写回来的应答按种类（OSC 按编号）配对，有没到期的才放行并销掉一个，没有就丢掉。同一个问题答两遍，第二遍丢掉。只管 `terminal:write` 这一路，平台自己写的按键不经过；括号粘贴里的内容不动。应答不算用户输入，不推迟投递、不当成提交 | `terminal/reply-gate.ts`、`terminal/manager.ts` `writeFromView`、`terminal/handlers.ts` |
| 回放写两遍 | 新开、续接、开 shell 时先 `term.reset()` 再写回放（和接回已有终端时一样） | `TerminalView.tsx` |
| 差个回车 | 判断输入框是否还留着这条消息：把折到下面几行的部分拼起来，看里面有没有这条消息的开头，不要求在最前面。认出来就走原有的 Ctrl+U 清掉重打，前面的残留一起清掉 | `prompt-ready.ts` `inputStillHolds` |
| 续接接到别的对话 | 续接时布局里没记编号，就用这个窗口自己记下的最近一次对话，不打开选择器。Codex 一次都没记下就开新对话 | `resume-handoff.ts` `planResume`、`handlers.ts` `workbench:launch-cli` |
| 会话被桌面版归档 | 续接前先看会话文件在不在 `sessions`；在 `archived_sessions` 就用同一个 codex 跑 `codex unarchive <编号>` 放回来，放不回来就开新对话。两处都没有时照旧按编号续接 | `resume-handoff.ts` `ensureCodexSessionActive`、`codex-rollout-watch.ts` `codexArchivedRolloutPathFor` |
| 续接后没人管 | 仍要用户点「续接」（用户定的）。这次运行里第一次续接的窗口，平台补发一句交接：角色、开它的窗口、未读条数、管理者的待处理页；换成了新对话时写明「你不记得之前的事」，先弄清现状再读近况，不再说「从停下的地方接着做」。普通窗口不发。不带 `allowUnknown`，看到输入提示符判空闲后才投递 | `resume-handoff.ts` `resumeHandoffText`、`handlers.ts` `sendResumeHandoff` |
| 管理者 90k 就压 | Claude 窗口只传百分比，不传窗口，由 Claude Code 按它自己认得的模型窗口算。DeepSeek 经 Claude Code 连接、命令行不认得它的模型，仍按真实窗口设 | `compact-launch.ts` |

没做：限流暂停状态不写到磁盘。重开后旧窗口都停着，平台和监管者本来就叫不醒；用户点「续接」就是用户的指令，按规则这时就该解除暂停。续接上的对话自己的记录里也有那次 429。

## 4. 自动验收

在仓库根目录跑：

```
pnpm lint
pnpm --filter @ff-pane/desktop run typecheck
pnpm test
cd apps/desktop
npx electron-vite build
npx playwright test
```

2026-10-23 本机结果：lint、typecheck 通过；单测 170 个文件 2638 条通过（1 条原本就跳过）；e2e 28 个文件 60 条全过。

新增和改的测试：

- `tests/terminal-reply-gate.test.ts`：问过才放行；没问过、过期、重复的丢掉；OSC 按编号配对；问题切成两块也认得；Esc、方向键、焦点、括号粘贴不受影响；光标位置和 DECRQM。另有一条用真的 `@xterm/headless` 重演现场：CLI 启动时的应答照写；5 分钟后重新挂载，xterm 对回放再答的那一遍一个字节也不进 PTY，也不算用户输入；用户打的字照写。
- `tests/workbench-prompt-ready.test.ts`：输入框前面有乱码、正文折到下一行时仍认出没提交；只有乱码时不算这条消息。
- `tests/workbench-resume-handoff.test.ts`：取最近一次对话；会话在 sessions、在归档里放回来、放不回来、两处都没有；Codex 没编号不走选择器；同一次运行里再续接不补交接；交接是一行，新对话时不说「从停下的地方」。
- `tests/compact-launch.test.ts`：Claude 只带百分比、不带窗口；DeepSeek 仍带窗口。

## 5. 真机验收（要用户操作）

1. **监管者接回原对话**：重开 FF-pane，点「监管3」的「续接」。期望：`~/.codex/archived_sessions/` 里的 `rollout-2026-10-22T08-03-40-01a160eb…` 回到 `~/.codex/sessions/2026/10/22/`；窗口里是 10-22 的监管对话；稍后收到一句「[交接] 软件重启过，用户刚把你续接上。你是「监管3」，监管者，由「Claude 1」开启……」。
2. **管理者续接后收到交接**：点「Claude 1」的「续接」。期望：出现输入框后收到「[交接] 软件重启过……收件箱有 N 条没读……」，不用自己打字。
3. **切标签、开子窗口不再打断 Codex**：监管者干活时切到别的标签页再切回来，或让管理者开一个子窗口。期望：Codex 这一轮不被打断，输入框里不出现 `[?1;2c]…`。
4. **管理者压缩**：管理者续接后跑一段时间。期望：会话记录里的 `compact_boundary` 的 `preTokens` 在 490k 左右，不再是 90k。
5. **不碰桌面版的对话**：续接前后，桌面版里别的对话的会话文件没有新增 `codex-tui` 写入的内容。

## 6. 风险与没核对的

- 闸门按「问题发出后 3 秒内」算。界面卡住超过 3 秒才答（比如窗口刚开、页面还没画出来）时，CLI 拿不到应答，按它自己的超时走默认值（颜色、终端类型）。现场这种迟到的应答正是捣乱的那种，所以宁可丢。
- Shift+F3 一类按键在 xterm 里也是 `ESC[1;2R`，和光标位置应答长得一样，没问过时会被丢掉。Claude Code、Codex 都不用这些键。
- `codex unarchive` 改的是 Codex 自己的会话状态，只对这个窗口自己记下的对话做。
- 防不住桌面版再次接管：两边共用 `~/.codex`，在桌面版里点开 FF-pane 开的会话仍会被接管、归档。下次续接时会放回来，但中间如果在桌面版里继续聊过，那部分也在同一个对话里。要彻底隔开得让 FF-pane 用单独的 `CODEX_HOME`，牵涉登录信息，没有做。
- 压缩的缓冲比例由服务端下发，本机反推是 0.5，以后可能变。滑块对 Claude 现在基本不起作用（50% 以上和不指定一样），使用说明已写明。
- 交接只在这次运行里第一次续接时发。平台或管理者重启窗口（换模型、`ffpane_restart_window`）不发，和以前一样。
