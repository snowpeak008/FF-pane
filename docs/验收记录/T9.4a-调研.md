## 2. API 路线结论

**今天不存在「openai_compatible / anthropic → 独立 HTTP 下发面」来派发模型行为参数。**

读码事实：

1. `PROVIDER_TYPES` 含 `openai_compatible` / `anthropic`，那是 **Provider 类型**，不是 Runtime。一轮 `startTurn` 永远走 `profile.runtime` 对应的 CLI 适配器（`registry.resolveForProfile`）。
2. 编排器对 API 型 Provider 只做两件事：`resolveRuntimeEnv` 按 Runtime 注入密钥/baseUrl；`resolveRuntimeConfigOverrides` **仅当 runtime===codex 且 type===openai_compatible** 时写 `model_providers.ffpane.*`。没有 `reasoningEffort`、没有 Anthropic `thinking` / `budget_tokens` 请求体字段。
3. HTTP 客户端在仓内的用途：`provider-probe`（测连通 / 拉模型）、RAG 嵌入、OpenCode **本地** `serve`（仍是 CLI 拉起的进程）。**没有**「工作台自己 POST Chat Completions / Messages 跑 Agent 轮」的适配器。
4. 因此：用户把 anthropic Provider 绑到 `claude-code`，effort 只能走 `--effort`；绑到 `openai_compatible` + `codex`，effort 只能走 `-c model_reasoning_effort`。把行为参数画在「Provider 类型」上会下发到不存在的面。

T9.4b：**不要**为 API 路线单开一套 HTTP 透传。条件显示按 **Runtime** 来。

## 5. 给 T9.4b 的实现建议（可当合同要点）

1. **领域字段只收一条主参数 + 可选隐藏预算，不要做「任意 argv 袋」。**  
   建议 `AgentProfile` 增：
   - `reasoningEffort?: string`（空 = 不传，走 CLI/模型默认）  
   - 第一期 **不**收 `maxThinkingTokens` / `thinkingVisible` / `thinkingBudget`。  
   校验：按 Runtime 白名单；不在白名单的 Runtime 带了该字段 → 拒存（与「不塞进不支持的家」硬门槛一致）。

2. **Runtime → 下发映射（只做有缝的）：**  
   - `codex`：并入既有 `configOverrides`，键 `model_reasoning_effort`，值用 TOML 字符串（与现单测 `'"low"'` 同款）。不要另开旗标。  
   - `claude-code`：`buildClaudeCodeArgs` 增第一类 `--effort`（不要靠 extraArgs）。非法值 FF-pane 先拦，因 CLI 会静默回退。  
   - `grok-build`：把 Profile 值传进已有 `createGrokBuildAdapter({ reasoningEffort })` / 或改为逐轮 `ctx`——注册表零参是唯一缺口。ACP 仍挂在 `agent` 层。  
   - `opencode`：Server `promptAsync` 的 model 对象补可选 `variant`（OpenAPI 已有字段）。**不要**把 `--thinking` 当第一期 Profile 项。  
   - `gemini-cli` / API Provider 类型 / qwen-code / generic-exec：**不下发、UI 不画。**

3. **条件显示按 Runtime，不按 Provider 类型。**  
   Profile 编辑器：`runtime ∈ {codex, claude-code, grok-build}` 显示 effort 下拉；`opencode` 仅当能读到该模型 `reasoning_options.effort` 时显示（读不到就隐藏，宁可少画）。`gemini-cli` 及其他隐藏。换 Runtime 清空或不序列化该字段。

4. **取值枚举第一期用「规范档 ∪ 按模型收窄」，不要把 raw 字符串当默认 UI。**  
   规范档建议：`none | minimal | low | medium | high | xhigh | max`（grok 文档 ∪ claude help ∪ codex 目录的主体）。`ultra`（codex 部分模型）与 grok 的 menu id（如 `deep`）第一期不进下拉，除非该模型目录明确列出。用户裁定见 §6。

5. **派发注入 + 执行记录。**  
   实际传给 CLI/HTTP 的档位写入 Run 记录（与 model 并列，可追溯）。未传则记缺省/未设置，不要事后猜。codex 用户全局 `config.toml` 已有 `model_reasoning_effort` 时：Profile 未设则 CLI 会吃到用户全局值——T9.4b 须在 UI 或记录里如实说「未设则跟随 CLI 用户配置」，或对 codex 显式 `-c` 覆盖以得到确定性（推荐后者，与「按 Profile 隔离」一致）。

6. **上下文窗口第一期只展示。**  
   复用 T9.8 `resolveContextWindow(model, runtime)`（`packages/shared/src/domain/context-window.ts`）。落点：Profile 编辑器模型行附近只读一行「约 N token（来路：model/runtime/fallback）」；会话页已有 `ContextUsageBanner`，不必再做干预。**不要**把 context window 当行为参数下发。

7. **能力声明与实测一致。**  
   适配器不要新增「supportsReasoningEffort: yes」却对 gemini 也返回 yes。矩阵 §1 即第一期声明表。升级 CLI 后：claude 用「缺值 → argument missing」复验隐藏参；codex 用 `debug models` 复验档位；opencode 复验 `/doc` 的 `variant`。

## 6. 未决问题（需用户裁定）

1. **取值 UI 暴露 raw 还是只暴露规范档？**  
   本调研倾向：第一期只暴露规范档 + 按模型收窄。raw（codex `ultra`、grok `deep`）等目录/菜单明确给出再进下拉。若用户要「高级：原样字符串」，须接受 CLI 静默忽略（claude / opencode 已实证）。

2. **codex 未设 Profile effort 时，要不要强制 `-c` 盖住用户 `config.toml`？**  
   推荐：显式下发（含「跟随默认」时写下目录 `default_reasoning_level`）以免同一 Profile 在不同机器行为不同。代价是多一次目录读取（`codex debug models` 体量 300KB+，T9.2 已登记）。

3. **opencode 第一期做不做 variant？**  
   Server 字段在、适配器未接、取值按模型且非法不拒。最小合规则做法是「有能力位才显示 + 只发 enumerated values」。若不想碰 Server client，可整家隐藏，留 T9.4c。

4. **iflow `--thinking` 是否纳入后续单？**  
   本单范围外。CLI 有旗标、ACP 适配器没传。若做，须先探 ACP 有无等价协议字段，禁止只在 headless 加旗标却继续走 ACP。

5. **claude `--max-thinking-tokens` 要不要进「高级折叠」？**  
   调研建议第一期不做。若用户坚持，须当能力探测点（升级后缺值探测失败则藏）并写 R3。
