### 2.2 为什么双击打不开

- 卡死的主进程还活着，**占着单实例锁**（T11.0d 加的「只开一份」）。
- 新双击的那份拿不到锁，按设计直接退出，指望旧的那份在 `second-instance` 里把窗口拉到前面。旧的那份主线程卡死，收不到这个事件，所以什么都没发生。
- 现有的兜底都跑在主线程上，主线程卡死就全部失效：
  - 退出看门狗（5 秒强退）是主线程的 `setTimeout`，而且装在 `before-quit` 里。关窗路径是先关窗、全关了才 `before-quit`，这次卡在关窗那一步，看门狗还没装上。
  - 「界面 30 秒没响应」弹框也靠主线程弹。

### 2.3 卡在哪（两份完整 dump，存在 `logs/diag/`，git 忽略）

当时没有调试器，用 Python 读 dump、扫线程栈上落在各模块里的地址（没配符号，只看得出模块和最近的导出函数）：

- **主进程主线程**：停在 `win32u.dll!NtUserDestroyWindow`（正在销毁一个窗口，内核调用不返回）。同一段栈上有 **`SogouPY.ime`（搜狗输入法）** 和 `msctf.dll`（Windows 文字输入框架）的地址。主进程里还挂着搜狗注入的 `SoPY_Comp`、`SoPY_Status`、`SoPY_Hint`、`SoPY_UI`、`Sogou_TSF_UI` 几个窗口，同样被判挂起。
- 结合「主窗口不可见」：Chromium 关窗时先把窗口藏起来，再 `DestroyWindow`。最可能的经过是：窗口被关（或界面卡住后被重载、弹框被关）→ 销毁窗口时卡在搜狗输入法里 → 主线程永远不返回。
- **界面进程主线程**：停在 `WaitForSingleObjectEx`，在等另一个进程的同步回应（FF-pane 自己的代码里没有同步 IPC，是 Electron/Chromium 内部的）。等的是谁、为什么 18:30 开始等，要配符号才看得出。

旁证：

- 别人报过几乎一样的现象：另一个 Electron 应用在 Windows 上关窗后主进程一直不退，进程里只剩搜狗的 `Sogou_TSF_UI`、`SoPY_*` 窗口（[hermes-agent #116376](https://github.com/NousResearch/hermes-agent/issues/116376)，作者也没定论，建议换掉搜狗输入法验证）。
- 1.0.21 时全量 e2e 在应用收尾时也出过搜狗（`SogouPY.ime` / `PicFace64.dll`）相关的崩溃 dump，当时判为环境问题。

### 2.5 配上符号以后（§4.0，2026-11-12 当晚）

用 1.0.15 的工具（`test-results/scripts/dump_stack.py` 的 call 指令核对 + `remote_pdb.py` 按需取 Electron 44.0.0 的 `electron.exe.pdb`，共下载约 7MB）：

- **主进程主线程**：`api::WebContents::Destroy` → `WebContentsImpl` 析构 → `api::BrowserWindow::WebContentsDestroyed` → `BrowserWindow::CloseImmediately` → `NtUserDestroyWindow` 不返回。也就是**关主窗口时销毁原生窗口卡住**。栈上更早的位置有经过 call 指令核对的 `user32` → `SogouPY.ime` → `msctf.dll` → `SogouPY.ime` 一段；进程里另有 **4 个搜狗自己的线程**，都在等待。销毁窗口要同步通知其他线程的窗口（搜狗的 `SoPY_*` 窗口），对面在等，就互相卡住。和 hermes-agent 那份报告一致。
- 最可能的经过：18:30 界面先卡住 → Tony 约 19:27 点关窗 → 关窗卡在搜狗那里，主进程从此冻住。
- **界面进程主线程**：`RenderThreadImpl::SharedCompositorWorkerContextProvider` → `CommandBufferProxyImpl::Initialize` → `GpuChannelProxy::CreateCommandBuffer` 同步调用，一直等 **GPU 进程**回话。和搜狗无关。日志里 GPU 进程没有退出记录，是 GPU 进程没回话。11-06 至 11-12 的日志里界面卡住只有这一次（11-11 那次是界面内存爆了、自动重载已恢复）。

## 3. 结论

1. **「崩溃」其实是卡死**：主进程没退出，卡在销毁窗口的系统调用里，最可能是被搜狗输入法卡住（未配符号，§4.0 确认）。
2. **打不开**是因为卡死的旧进程占着单实例锁，新的一份按设计退出了。这一条和卡死的原因无关，不管什么原因卡死都会这样，要单独兜住（§4.2）。
3. 现有的看门狗和弹框都在主线程上，主线程卡死时全部失效（§4.1）。
4. 界面 18:30 先卡住是另一件事，原因未明（§4.4）。
5. 有几类临时文件和崩溃记录没人清，会越攒越多（§4.5）。

## 4. 做法

### 4.0 先查清（只读，不改代码）

- 用 1.0.15 时写的工具（`test-results/scripts/dump_stack.py`、`remote_pdb.py`，Electron 44.0.0 符号按需下载）给两份 dump 配符号：
  - 主进程：确认 `DestroyWindow` 销毁的是哪个窗口（主窗口还是弹框），确认搜狗那几帧是真调用链，不是栈上的旧值。
  - 界面进程：确认在等谁（GPU 进程，还是主进程）。
- 结论写进验收记录。查完删 dump（§4.6）。

### 4.1 主线程看门狗挪到工作线程

- 主进程起一个 `worker_threads` 工作线程，主线程每 2 秒给它发一次心跳。工作线程不依赖主线程，主线程卡在系统调用里它照样能跑。
- 工作线程判断（规则写成纯函数，放 `diagnostics/policy.ts`）：
  - **平时**：60 秒没心跳 → 自己往日志文件写一行「主线程冻住 N 秒」，不杀进程（写堆快照之类可能合法地卡一阵）。之后每分钟补一行，恢复时写「恢复」。
  - **在关窗或退出过程中**（主线程在关窗 `close` 事件里就通知工作线程，不等 `before-quit`）：10 秒没心跳 → 写日志，然后 `taskkill /F /T` 结束本进程和它的整棵子进程树。
- 原来主线程上的 5 秒退出看门狗保留，仍在 `before-quit` 装（提前到关窗时装，加上关窗和退出各一次布局 flush、终端收尾 3.5 秒，可能把正常收尾掐断）。关窗到 `before-quit` 之间卡住由工作线程兜。

### 4.2 再双击时能自救（不改 `FF-pane.exe` 启动器）

- 工作线程每 10 秒写一次 `%APPDATA%\FF-pane\instance.json`（和单实例锁一样按 userData 算）：`{ pid, startedAt, lastBeat }`，`lastBeat` 是**最后一次收到主线程心跳**的时间，所以它反映的是主线程活没活着。开始关窗后删掉、不再写。
- 新的一份拿不到单实例锁时，不再直接退出，先读这个文件：
  - `lastBeat` 在 30 秒内 → 旧的正常，照旧退出，由旧的一份把窗口拉到前面（窗口藏起来了也会 `show()`）。
  - 超过 30 秒、且该 pid 还在、还是同一个可执行文件（进程号会被复用）→ 再等 13 秒重读一次（电脑刚睡醒时心跳时间也是旧的，醒来后 13 秒内会刷新），还是旧的才弹框：「上一个 FF-pane 已经 N 分钟没有响应。结束它并重新打开吗？终端里的 AI 窗口会一起结束，重开后自动续接，正在回复的那一轮会丢。」按钮「结束并重新打开」「取消」。
  - 选结束 → `taskkill /F /T` 旧 pid，等锁释放（最多 10 秒）后继续正常启动。
- 冒烟自检模式不拿锁，不受影响。

### 4.3 绕开输入法卡点（不做）

> **2026-11-12 定：不做。** 符号确认卡点就在关窗销毁原生窗口这一步，§4.1 的看门狗已经保证这时 10 秒内整个进程结束；而每次正常退出都跳过 Chromium 的收尾直接结束进程，会丢还没写盘的东西（界面 localStorage 里的设置等），得不偿失。下面是原来的想法，留作记录。


- 关窗退出时：存布局、走现有退出收尾（PTY 收尾、删临时 MCP 目录、同步删技能挂载目录）都做完之后，**直接结束进程**，不再走 Chromium 原生销毁窗口那一步。关窗卡死的那一步就不会被执行到。
- 如果 §4.0 查出卡的是「界面卡住后弹框 / 重载」那条路，改那条路，这条做法照样保留。
- Tony 那边可选的临时办法：用 FF-pane 时切到微软拼音；或者搜狗设置里关掉对 FF-pane 的高级功能（皮肤、表情、云输入）。单是换默认输入法不够，搜狗的钩子下次启动还会注入（见 hermes-agent 那份报告）。

### 4.4 界面先卡住（18:30 那次）

- 界面 30 秒没响应时，日志里记一行 GPU 进程的状态（pid、内存、CPU）。
- 弹框里选「重新加载界面」时，**先结束 GPU 进程（Chromium 会自己重开），再重载界面**。光重载界面还会卡在同一个没回话的 GPU 进程上。
- 窗口最小化或藏起来时，弹框不挂在窗口上（挂上去会跟着看不见，18:30 那次 Tony 可能就没看到弹框）。

### 4.5 残留自动清理

启动后 1 分钟（避开启动高峰）做一次，只认本应用的前缀，只删超过 1 天的：

- `Crashpad/reports`：只留最近 5 份，且不超过 14 天。
- 临时目录清扫（启动时，超过 1 小时，和 MCP、钩子目录同一套）加上 `ff-pane-knowledge-audit-`：核对下来每开一个窗口建一个、工作台不读回、从来不删。
- `ffpane-digest-*`、`ffpane-aider-session-*`、`ffpane-grok-prompt-*` 查清都是**单测**留的（Aider / Grok 旧适配器已不被应用使用）。不逐个改测试：根 `vitest.config.ts` 加 `globalSetup`（`vitest.temp-setup.ts`），跑测试期间把 `TEMP/TMP/TMPDIR` 指到专用目录，跑完整个删。
- e2e：`_launch.ts` 加 `e2eTempDir()` / `removeE2eTempDirs()`，漏删的 4 个 spec（workbench-mcp、project-config、model-effort、supervisor-watch）改用它，每个测试跑完删。

## 7. 2026-11-13 又卡住（查明，未改代码）

### 7.1 现场

- 卡住的这份 FF-pane 是 **11-12 19:58 启动的**，比 1.0.31 提交（20:54）早，1.0.31 的看门狗、重载前重开 GPU 进程都**没生效**（`instance.json` 不存在可印证）。
- 主进程一直活着，日志每 5 分钟一行没断；**卡的是界面进程**。
- 时间线（本地时间）：

| 时间 | 发生了什么 |
|---|---|
| 07:58 起 | 界面进程内存从 790MB 一路涨，10:13 到 1956MB；JS 堆一直只有 40–70MB，DOM 节点数稳定 |
| 10:08 | 界面最后一次报内存 |
| 10:09:21 | Windows 记「虚拟内存不足」（Resource-Exhaustion-Detector 2004）：Unity.exe(54488) **46.9GB**、FF-pane 界面 2.0GB、explorer 1.6GB。提交上限 67.8GB（C 盘页面文件封顶 4GB，D 盘 32GB） |
| 10:15:50 | `window unresponsive`，之后界面一直没恢复 |

- 那份 47GB 的 Unity 是团队「集成」窗口开的（当天线程里 Blender 一直因为空闲内存不到 8GB 在排队），约 10:00 随旧集成会话关掉了。

### 7.2 卡在哪（11:0x 抓的线程栈小 dump，`logs/diag/`，配了 Electron 44.0.0 符号）

- **GPU 进程主线程**：`PartitionRoot::OutOfMemory` → `TerminateBecauseOutOfMemory` → `RaiseException` → `UnhandledExceptionFilter` → 崩溃处理 → `SleepEx` 一直睡。也就是系统提交内存耗尽时 GPU 进程分配失败、准备自杀，却**卡在崩溃处理里不退出**。FF-pane 的 crashpad-handler 进程此时也已经不在了（多半同时被内存不足带走），崩溃处理等不到它。
- **界面进程主线程**：`OnContextLost` → 重建 `LayerTreeFrameSink` → `GpuChannelProxy::DestroyCommandBuffer` 同步调用，**等 GPU 进程回话，永远等不到**。
- GPU 进程不退，Chromium 就不会重开它，界面就一直卡着。和 11-12 那次是同一类：界面同步等一个不回话的 GPU 进程。

### 7.3 结论

1. 直接原因：Unity 把整台机器的提交内存吃光，FF-pane 的 GPU 进程分配失败后卡在崩溃处理里不退，界面跟着卡死。
2. 1.0.31 的「30 秒没响应弹框 → 重新加载界面」会先结束 GPU 进程，正好能解开这种卡法，但这份没跑上 1.0.31。
3. 另一件事：界面进程两小时涨了约 1.2GB，涨的不是 JS 堆（11-11 那次界面内存爆了也是这样），让内存不足来得更早。2026-11-13 已查明，见 [界面内存增长修复计划](./界面内存增长修复计划.md)（T11.14）。

### 7.4 改法

> 2026-11-13：Tony 定先重开到 1.0.31，再做 A；B、C 未定。A 已开发为 1.0.32（T11.13），见 [验收办法](./验收记录/1.0.32-界面卡住自动解卡-验收办法.md)。和下面写的不同：GPU「不动」按这段时间累计 CPU 不到 0.5 秒判；自动结束后再等 15 秒才弹框。

- **A. 自动解卡**：界面没响应满 30 秒时，如果 GPU 进程 CPU 是 0（卡在崩溃处理里就是这样），不等点弹框，直接结束 GPU 进程并记日志；界面若随后恢复，弹框自动收起。代价：界面只是忙（不是等 GPU）时被误判，最多闪一下重画，终端不受影响。
- **B. 查界面原生内存**：`[renderer-mem]` 里加上界面进程总私有内存与 JS 堆的差值、xterm 实例数和 WebGL 上下文创建/销毁累计数，先定位涨在哪，再决定改法。
- **C. 机器侧（Tony 自己定）**：C 盘页面文件封顶 4GB，可以调成系统管理，提高提交上限；团队规则里给 Unity 加内存上限或空闲内存门槛（现在只有 Blender 有）。
