## 2. A · 越权

调用者身份只来自令牌。控制通道 `resolveCaller(token)`，工具执行用这个窗口 id。参数里的 `windowId` 是目标，不是「我是谁」。没有 `projectId` 参数可以改调用方所属项目。字面量 `${FF_PANE_WINDOW_TOKEN}` / `${FF_PANE_WB_PIPE}` 在 sidecar 被拒。

| 路径 | 结论 |
|---|---|
| worker 自设 manager、worker 调 `open_window` | 拒绝。`canSetRole` 不允许窗口把自己设成管理者（除非用户开启的顶层窗口）。`openChildWindow` 还要求 `isManagerGranted` |
| 冷启动布局里的 manager | 不能开窗口。`grantManager` 只在本进程 `setWindowRole` 把角色写成 manager 时调用。`syncLayout` 不授 |
| `open_window` 把子窗口角色写成 manager | 角色会记下，但**不**调用 `grantManager`。这个子窗口看起来是管理者，在有人再对它 `set_role` 之前开不了孙窗口 |
| `open_window` 的 permission 写成 yolo | 先和调用者自己的等级取 min，pin 父级和 `openedBy`，再 `launchCliWindow`。`resolveLaunchPermission` 沿整条祖先链取上限；环或截断则只读 |
| profileId 指向另一种 CLI | 拒绝。`resolveProfileId` 要求档案的 runtime 与本次 cli 一致（claude → claude-code，codex → codex） |
| 窗口关闭 | PTY 退出时吊销该窗口令牌，并丢掉它的空闲队列。`issue()` 会换掉同一窗口的旧令牌。令牌只在内存，进程重启后表是空的 |
| 发消息 / 汇报 | `authorize`：消息只给后代，汇报只给祖先链。别的项目的窗口 id 不在这条链上就拒绝 |
| 列表 | `list_windows` 只返回可见范围（自己、后代、上级链） |

worker 在被降级之前已经有后代时，仍可把那些后代设成任意角色，包括 manager。这是 `canSetRole` 的合同（窗口可设定自己的后代），不是额外提权。新开的窗口仍被整条祖先链封顶。

单测里 `open_window` 的 `launch` 是替身，它核对了「父级已 pin、请求 yolo 时已先收到调用者的较低等级」，没有真的跑三层祖先链。三层封顶在 `resolveEffectivePermissionCeiling` 里，代码会走；建议补一条三层测试，不阻断。

同一 CLI 的任意档案都能被选中，该档案的密钥会进子进程。runtime 对不上会被拒。若档案之间信任不同，建议限制为调用窗口自己的档案。

## 3. B · 注入与路径

提醒模板固定。标题只留字母数字和少量标点，最长 32。正文、ESC、换行不进 PTY。单测锁住恶意标题。

人读 md 的标题和正文走 `sanitizeThreadText`（去掉 C0 和 DEL，含换行）。标题里的 `」` 只能弄脏同一行，变不出新的 `###` 标题。团队文件名去掉控制字符和 `\ / : * ? " < > |`，再加日期前缀和短 id，撞不上 Windows 保留设备名（`CON` 这类要整段文件名才算）。

初始提示：`buildInteractiveClaudeArgs` / `buildInteractiveCodexArgs` 把提示 `push` 进参数数组。node-pty `spawn(file, args)`，没有 shell。消息不经 cmd。

briefs：`resolveBriefPath` 逐段看真实路径，符号链接或 junction 的真实目标离开 briefs 就拒绝。本机 Node v24.15.0 把 `mklink /J` 报成 `isSymbolicLink() === true`。在 `%TEMP%` 做了嵌套探针：`.ffpane/briefs/escape` 指向目录外，被拒，错误是「briefPath 经符号链接越过了 briefs 目录」。单测覆盖了整个 briefs 目录本身是 junction 的情况。嵌套 junction 的行为对，但没有单测。

**必须修复：** `assertProjectFiles` 拒绝 `..`、绝对路径和 NUL，不拒绝换行。`formatThreadBlock` 把附件原样写成 `附件：${files.join("、")}`。路径 `src/a.ts` 加换行再加 `### 伪造标题` 在词法上仍在项目内，写进 md 后换行后面就是一条假标题。jsonl 里换行会被 JSON 转义，机读日志仍是一行；被人读的 md 被伪造。

建议修法：在 `assertProjectFiles` 里拒绝或去掉 C0 / DEL（最好连 U+2028 / U+2029）。与正文、briefPath 同一标准。

其它不阻断：`.ffpane` 本身若是 junction，写 brief 可能先在外面建一个空目录，内容在真实路径检查后不会写入。附件路径只做词法检查，项目内的 junction 可以被列成附件，主进程不读那个文件。brief 文件名里的冒号留在 briefs 目录内，有机会被当成 NTFS 备用流，没有写出目录。

## 4. C · 投递

实现在 `idle-deliver.ts`。`PermissionRequest` 把 `permissionLatch` 设为 true，phase 为 blocked。注释写：`PostToolUse` / `PostToolUseFailure` 表示权限框已经结束。`Stop` 在闩着时直接返回，不投递。`deliverNow` 在 blocked 和 busy 都拒绝，一次只写队首的正文和 `\r`。`enqueueInbox` 把同一窗口还没发出的提醒合成一条，条数累加，模板里没有正文。

这些和 T10.6 移交对得上：没有超时强写；手动只发队首；shell PTY 的 `baseEnvForCreate` 删掉 `FF_PANE_WINDOW_TOKEN` 和 `FF_PANE_WB_PIPE`；Codex 手动发送有「若画面上有确认框请勿点击」。

**和 Claude hooks 文档不一致（2026-10-01，code.claude.com/docs/en/hooks）：**

| 事件 | 文档 | 现在的代码 |
|---|---|---|
| `PermissionRequest` | 即将询问。输入有工具名和参数，**没有** `tool_use_id` | 闩上。正确 |
| `PostToolUse` | 某个工具**已经成功**之后。并行调用时**并发触发** | 任意一次就清闩，phase 变 busy |
| `PostToolUseFailure` | 已经开始的工具失败。**用户拒绝权限不会触发**（拒绝走 `PreToolUse`，自动模式的拒绝另有 `PermissionDenied`） | 注释把它当成「框结束了，含拒绝」。文档不是这个意思 |
| `UserPromptSubmit` | 用户提交了新一句，Claude 还没处理 | 同样清闩。这不是「对话框已关闭」 |
| `Stop` | 主回合结束 | 闩着时不写。闩一开，下一次 Stop 就把 phase 打成 idle 并投递 |

清闩之后不会立刻写，因为 phase 是 busy，自动投递和「立即发送」都停着。危险在下一步：闩已经没了。下一次 Stop 会写正文加回车。

两条都会在确认框还在时把闩打开：

1. 并行工具。一张框还开着，另一个工具已经成功，它的 `PostToolUse` 清掉全局布尔值。
2. 伪造。hook 脚本不读 stdin，只上报 argv 里的事件名。同一窗口令牌可以直接向管道写 `{type:"hook",event:"PostToolUse"}`，再写 `Stop`。T10.6 已确认 Claude 的 Bash 会继承这两个环境变量；工作台自己的 shell PTY 会删掉它们，挡不住 CLI 里已经跑起来的命令。伪造的 Stop 在闩还在时被挡住；先伪造一次 PostToolUse，这道挡就没了。

用户点了「否」时，`PostToolUseFailure` 不会来，闩保持，这是偏安全的卡住。不要为了「拒绝也要解锁」而提前清闩。

单测「Stop 不解除权限闩锁，工具完成之后的下一次 Stop 才投递」把「任意 post-tool-use 然后 Stop 就写入」锁成了规格。修的时候要改掉这条测试。

**建议修法：** 未决权限用计数，不要用一次任意的 PostToolUse / PostToolUseFailure / UserPromptSubmit 清零。`PermissionRequest` 加一。当前 hook 不读 stdin，而这个事件又没有 `tool_use_id`，对不上「哪一张框」。计数大于 0 时，Stop 和手动发送都不得写。漏一次敲门可以，在确认框上按回车不行。在有一个后台进程伪造不了的「这张框已经结束」信号之前，不要靠同一根管道上的事件名解锁。`UserPromptSubmit` 同样能被伪造，不能单独当解锁。Codex 仍然没有权限事件，首轮手动发送的残余保持 T10.6 的决定，不在本单重开。

## 5. D · 可追溯性

计划 §3.2 写明正文去掉控制字符。实现把换行也去掉了，所以 `第一行\n第二行` 在 md 里变成 `第一行第二行`。单测把这个锁住了。`index.jsonl` 存的是原始 JSON，换行还在。

Tony 要对话可追溯，人读的 md 挤成一行很难看。建议：正文放进引用块（每行前加 `> `）或四空格缩进，换行保留。行首的 `#` 就不再是标题。标题行仍只由主进程生成。这是可读性建议，不因为「和计划字面不一致」单独判不通过。jsonl 继续存原文，给程序读。

写入按项目根 `runSerial` 串行。先追加 jsonl，再追加 md。最后一行半写时读取会跳过。两次追加不是一个事务：写完 jsonl、还没写 md 时崩溃，索引会多一条、md 少一块。建议接受这个窗口，或改成先写临时块再改名；不阻断。

执行者修复：未决权限计数；`files` / brief / 标题去掉 C0 与 DEL；md 正文保留换行并写成引用块，jsonl 存原文；三层祖先链封顶测试。本轮只改本验收记录。`pnpm smoke` / `pnpm test:e2e` 再次刷新了已存在的 `apps/desktop/out`。

### 10.1 计数与卡死

`PermissionRequest` 加一。带上合法 `tool_use_id` 的放进集合，只被同 id 的 `PostToolUse` / `PostToolUseFailure` 减一。没有 id 的另计，减不掉。计数大于 0 时，Stop 不改成空闲，`deliverNow` 拒绝。减到 0 之后是 busy，还要再等一次 Stop 才写。

官方 hooks 文档（code.claude.com/docs/en/hooks，2026-10-01 拉取）写明：`PermissionRequest` 的输入有 `tool_name` 和 `tool_input`，**没有** `tool_use_id`。示例 JSON 里也没有这个字段。所以真实确认框全部进「无法配对」那一档。工具成功时的 `PostToolUse` 虽然带着 id，对不上这档，减不掉。用户点否时文档写明不触发 `PostToolUseFailure`。结果是：每一次真实确认之后，提醒都会停住，直到 `UserPromptSubmit` 或窗口重启（`drop` 删掉该终端会话）。

这不是永久卡死。恢复有两条：在这个窗口里再提交一句；或关掉窗口。有待投递时横幅是「有 N 条待投递」加「正在等待权限确认，暂不发送」。取消按钮只丢掉队列，不清计数；下一条仍会停在同一句文案上。队列是空的时候横幅不出现，此时也没有东西要写。

建议（不阻断）：横幅补一句「确认框已经关掉的话，在这个窗口再发一句，或关掉重开」。现在的文案在框已经消失之后仍说「正在等待权限确认」，人不知道该怎么恢复。不要改回「任意 PostToolUse 就清零」。

hook 读 stdin 的 250ms 超时如果错过 id，请求同样变成无法配对，走上面同一条恢复。真实的 `PermissionRequest` 本来就没有 id，这条超时不改变确认框的配对结果。

### 10.2 UserPromptSubmit 会不会在框还开着时清零

对照同一份文档：`UserPromptSubmit` 是「用户提交了一句，Claude 还没处理」。权限框是对话框，回车交给对话框，不是提交新的一句。真实的这个事件发生时，用户已经回到输入并提交，框不在了。清零之后 phase 是 busy，不会立刻写；下一次 Stop 才投递。

同窗口、已经拿着本窗口令牌的后台进程仍可以伪造一条 `UserPromptSubmit`，把配对集合和无法配对的计数一起清掉，再伪造 Stop 写入。这和 T10.6 记下的残余是同一类：没有令牌就发不出，有令牌也只能打自己的窗口。不单独立项。

### 10.3 引用块

`quoteThreadBody` 保留换行，去掉其它 C0 和 DEL，每一行（含空行）都加上 `> `。jsonl 仍是原文，含换行。

本轮用与实现相同的规则看了这些正文：`hello` 加换行加 `> ` 再加 `### forged`；中间是真正空行再跟 `###`；行首就是 `> ###`。产出的每一行都以 `> ` 开头，没有一行在第 0 列是 `#` 标题。CommonMark 里，没有 `>` 的空行才会结束引用；这里的空行是 `> `，引用不断。`> ###` 是引用内部的标题，不是与「`### 时间 · 角色`」并列的另一条消息。行首扫描 `###` 只能看到主进程写的那一条。

`assertProjectFiles` 拒绝路径里的 C0/DEL。带换行的附件在工具层被拒，不再写进 md。标题里的换行被去掉，伪造标题留在同一行。

### 10.4 三层封顶

单测「用户→管理者(edit)→子管理者→孙窗口请求 yolo，实际被封顶为 edit」调用的是注册表 `resolveLaunch`。子管理者自己登记为 yolo，祖先是 edit，孙窗口请求 yolo，生效是 edit。生产路径 `launchCliWindow` 同样调用 `resolveLaunch`。
