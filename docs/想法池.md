## 1. 分层管理：总管理者下面挂组长，带黑板（2026-11-13）

- **状态**：Tony 定暂不做，风险高，滞后考虑，保留方向。
- **起因**：Tony 问管理结构能不能做成类似行为树：每个节点不只是执行者，也可以是次级管理者，带一定的黑板值，自行安排下级的开发任务和验收（Tony 说和 Hermes 集群的规则有点像；具体规则手上没有资料）。

**现状**

- 代码已半支持嵌套管理者：管理者能把下级窗口设成管理者（`packages/core/src/workbench-role/can-set-role.ts`），冷启动后子管理者的管理权随上级继承（`apps/desktop/src/main/workbench/manager-grant.ts` 的 `inherit`）。
- 规则上 Tony 10-24 定过「一个项目只有一个管理者」（[改进计划总览](./改进计划总览-2026-10.md)），不让多个管理者指挥同一批文件。

**好处**

- 总管理者的上下文是瓶颈，现场出过：未读汇报没人看、自己盯监管、频繁压缩（1.0.13、1.0.22 修过）；管理者曾两天偷开 62 个子 agent、改 212 个文件（[子 agent 管控计划](./子agent管控计划.md) §1）。组长分担后每个窗口只装自己那棵子树。
- 验收就近，总管理者只看汇总。
- 贴合真实分工（如「岛屿精修 I05」分 A–G 段、「集成」带一轮轮大跑）。
- 黑板由平台保存，比聊天可靠，压缩、重开不丢；和「项目状态归本地工作台所有」一致。

**风险**

- 层层转述失真，错误被汇总藏住。
- 组长自己派活自己验收，同一个模型给自己打分。
- 决定在组长那里就定了，Tony 看不到，拍板权被层级吞掉。
- 每个组长是一个完整 CLI 窗口：上下文、额度、几百 MB 内存；同时最多 12 个窗口。
- 自主排活的节点多了，抢锁、改同一文件更多；Unity 只能开一个编辑器，几个组长都要跑大跑就是 11-13 内存爆掉的放大版。
- 一个组长卡住整棵子树停；重开后子管理者要等上级恢复（`pending`）。
- 行为树的比喻不贴切：真行为树控制流确定、tick 便宜；这里每个节点是不确定、调一次很贵的大模型，更像组织架构。能借的是**平台**按黑板上写好的流程（顺序、并行、重试、验收）推进，而不是让模型自己定流程。

**和核心的关系**

- 不冲突：组长也是看得见的窗口；权限按上级封顶；锁和黑板归平台。
- 要改规则：「一个项目只有一个管理者」→「一个总管理者 + 地盘不重叠的组长」，地盘要由平台卡住（可扩展 1.0.25 的写入守卫，按组长地盘限写入目录）。
- 会击穿的情况：层级不设限、管理者再开管理者。等于「62 个隐藏子 agent」换成看得见的形式回来。

**如果以后要做，先这样试**

- 只做两层：总管理者 → 组长；组长不能再开管理者；每个组长有窗口数上限，全局 12 个不变。
- 每个组长一块平台保存的黑板：目标、地盘目录、验收标准、预算（窗口数、时间）、已定的决定；上级写，下级只更新状态；界面看得见。
- 组长和手下只能写自己地盘里的目录。
- 组长只做阶段验收；向上报「做完」要带平台能核对的证据，由检查角色或上级验。
- 要 Tony 拍板的事直接送 Tony，不经层层转交。
- 拿一个真实场景试点（如 I05 那几段），看总管理者的未读积压、压缩次数是否下降，返工是否增加。

**可以和哪些想法碰撞**：平台按流程推进（把计划拆成可执行的步骤由平台调度）、计划评审与结构化汇报（T11.4，[计划评审计划](./计划评审计划.md)）、按需手册（T11.6）。
