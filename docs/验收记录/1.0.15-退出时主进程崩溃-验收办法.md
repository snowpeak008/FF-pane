# 1.0.15（T11.0d 续）退出时主进程崩溃：原因、改动与验收办法

**日期：** 2026-10-27
**状态：** 已提交（2026-10-27，版本 1.0.15），尚未验收。
**计划：** [主进程内存与白屏修复计划.md](../主进程内存与白屏修复计划.md) §2.3 第 2 条（「崩溃本身还没找到原因」）、§4.0 最后一条（给 dump 配符号）。

## 1. 原因

10-20 至 10-27 Windows 应用程序日志里 electron.exe 崩了 160 多次，绝大多数是 `0xc0000409`，偏移都是 `electron.exe +0x3043d85`。

**怎么查的（都是只读）：**
- 8 份 Windows 留下的 dump，按崩溃线程的栈逐个找返回地址，看落在哪个模块里，并核对前面是不是一条 call 指令（`test-results/scripts/dump_stack.py`）。
- node-pty 自带的 `conpty.pdb`，用自己写的小解析器给函数起名（`pdb_funcs.py`）。
- Electron 44.0.0 的 `electron.exe.pdb` 有 4.1GB，用 HTTP Range 只取用到的块，一共下了 5MB（`remote_pdb.py`）。

**8 份 dump 的栈一模一样：**

```
conpty.node  Napi::details::WrapVoidCallback<ThreadSafeFunction::CallJS ...>   ← conpty 的「进程退出」回调回到 JS
conpty.node  Napi::Error::ThrowAsJavaScriptException                          ← 回调失败，想抛回 JS，也失败
conpty.node  _CxxThrowException                                               ← 变成 C++ 异常
electron.exe __scrt_unhandled_exception_filter → terminate → abort            ← 没人接，整个主进程 abort
```

抛出的对象是 `Napi::Error`，里面的 `_env` 是空的。node-addon-api 只有一种情况会这样：**JS 环境已经在拆、不能再跑 JS 了，这时 conpty 的「进程退出」回调才送到。** 也就是退出时的竞态：FF-pane 退出，主进程开始拆 JS 环境，某个终端的退出回调这时才到。

**对得上的地方：**
- 崩溃时间一簇一簇的，几乎都落在每次提交前跑全套 e2e 的时候（10-21、10-22、10-23、10-24、10-25 都是），每个用例结束时关应用，里面还有终端。
- Tony 那 3 次（10-26 07:52、10-27 07:57、11:39）都是白屏之后点关闭：崩的那一刻主进程只有 300–500MB，界面进程已经没了。
- 1.0.14 打开了 Electron 自带的崩溃记录以后，崩溃改由它接住、写进 e2e 临时目录，不再进系统日志，所以今天系统日志里没有新的。为了看见，这次给 e2e 的收尾加了检查：删临时目录前找 dump，拷到 `apps/desktop/test-results/e2e-crash-dumps/` 并报出是哪条用例。改之前跑全套：**14 条用例留下了 dump，其中 10 份就是这个 conpty 退出竞态**。

**另外两种（不用改）：**
- `0xc0000005`，`electron.exe +0x3cf0fa3`：在 `node::inspector::InspectorSocket::Write` 里，是 Node 调试器的连接。Playwright 的 e2e 通过调试器连着主进程，只有跑 e2e 才会有；10-25 11:15 那次也在 e2e 期间。
- 「界面进程没了自动重载」那条用例故意让界面进程崩溃，留下的是界面进程的 dump，本来就该有。

## 2. 改动

- `PtyHandle.exitDelivered()`（`terminal/types.ts`、`factory.ts`）：conpty 的原生退出回调是不是已经送到 JS。看 node-pty 内部 `_agent._exitCode`（回调里写入）；还没连上过（`connect` 没调成）的不会有回调，算已送到；认不出内部结构也算已送到，不卡退出。
- `PtyManager`：记下建过的每个终端，直到它的回调送到为止（关掉、已经从列表里删了的也记着）。新增 `hasUnsettledExits()` 和 `settleForQuit(上限)`：杀掉全部终端，每 25ms 看一次，都送到了就返回，最多等上限。
- 退出流程（`index.ts` 的退出协调器，原来空着的「关停常驻资源」一段）：有终端或还有回调没到时，先 `settleForQuit(3 秒)`，再让 Electron 退出。加上布局 flush（0.8 秒），仍在 1.0.14 的退出看门狗（5 秒）之内。超时没到的个数写进日志。
- e2e 收尾（`tests/e2e/_launch.ts`）：删临时目录前找崩溃 dump，有就拷出来并报出用例名。

## 3. 已验证

- 单测：新增 `terminal-quit-settle.test.ts`（等回调都到才返回；之前关掉的也等；一直不到按上限放行并报个数；不报告状态的当作已到）。全部单测 2710 条通过，typecheck、lint 通过。
- e2e 全套 64 条通过。**改后再跑：conpty 退出竞态 10 份 → 0 份**，只剩 2 份调试器连接的（只在 e2e 里）和 1 份故意让界面崩的。

## 4. 验收办法

| # | 做法 | 应该看到 |
|---|---|---|
| 1 | 开几个 Claude / Codex 窗口，让它们在跑，然后关掉 FF-pane | 几秒内正常退出；`~/.aiworkbench/logs/` 当天日志最后有 `[quit] runtime resources present; closing before quit`，没有 `still pending` |
| 2 | 关掉后看 Windows「事件查看器 → Windows 日志 → 应用程序」，或 `%APPDATA%\FF-pane\Crashpad\reports\` | 没有新的 electron.exe 崩溃 |
| 3 | 重新打开 | 窗口照常续接，没有残留进程（任务管理器里没有上一份的 electron.exe） |
