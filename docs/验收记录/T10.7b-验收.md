## 2. A · 越权

调用者身份只来自令牌。`read_output` 与 `close_window` 走 `authorize` 的控制类动作，只允许后代。`close_window` 在调用 `authorize` 之前再拒绝「目标就是自己」或 `isDescendantOf` 为假。`open_panel` 按合同任何窗口都能调，同一窗口间隔 3000ms，过频不发事件。

`%TEMP%\t107b-probe.mjs` 用当前源码的注册表和 `authorize` 构造了这些树（没有写应用数据目录）：

| 路径 | 探针结果 |
|---|---|
| 跨项目，没有父子链接 | `read-output` / `close` 都是 `not-descendant` |
| 目标窗口不在树上（已关闭、id 不存在） | `target-not-found`。读输出的实现里，终端已退出只返回 `running:false` 和状态句，不把回放缓冲交出去 |
| 关掉中间窗口 W 之后，祖父 M 读/关孙窗口 C | 两者都拒绝。C 仍标着 `parentClosed`，`parentWindowId` 仍是已经不在树上的 W。非祖先 U 同样拒绝 |
| 读自己 / 关自己 | `read-output` 自己：`control-self-denied`。工具层关自己：在 `authorize` 之前就返回「只能关闭自己的后代窗口」。`authorize` 对 `close` 自己却返回 `ok: true`，见建议 |
| 父级还在，子窗口磁盘权限 yolo | 冷启动后权限是 `edit`，`resolveLaunch(child, yolo)` 为 `{ effective:"edit", capped:true }` |
| 子窗口角色改成 manager，父级未在本进程被授予 | `decideManagerGrantRestore` 为 `pending`，`isManagerGranted` 为 false |

`close_window` 会杀 PTY、丢掉投递队列、吊销令牌、`closeRegistered`（直接子级标 `parentClosed`）、从布局摘掉窗口，并写 `kind:"system"`。未读统计只计 `message` / `report`，系统行不计。人读 md 的标题用清洗过的标题，正文进引用块。

**`read_output` 与敏感信息：** 先按字节取尾（默认 8KB，硬顶 32KB，截断点落在 UTF-8 续字节上会向后挪），再去 ANSI / C0（保留 TAB、LF、CR）。它返回的是该后代终端回放里的明文。子窗口若在终端里把环境变量或 `FF_PANE_WINDOW_TOKEN` 打出来，祖先的模型会在工具结果里看到。这是「管理者读后代终端」本身，不是把祖先抬到高于自己的等级，也不让非祖先读到。工作台自己的 shell PTY 会去掉令牌和管道名；Claude 的 Bash 仍可能从 CLI 进程环境里读到本窗口令牌（T10.6 已记的残余）。可选加固是在返回前涂掉本进程已知的令牌值，不阻断。

关掉中间父窗口之后，祖父不再出现在孙窗口的祖先链上（走到缺失节点就停）。这是能力变少，不是非祖先获得了操作权。

## 3. B · 冷启动与管理权

`workbench:get-layouts` 对每个项目：注册表里还没有这个项目就 `restoreColdLayout`，已经有了就 `syncLayout`。`restoreColdLayout` 采用磁盘上的父子，再 `sanitizeWorkbenchAuthTree`（断环、子不超过父）。`grantManager` 不在这条路上调用。

父级还在时，下面几条和合同一致，单测也锁住了：

- 子窗口手改 yolo：封到父级，并标 `permissionNeedsDowngrade`。
- 子窗口手改 manager：只显示「管理权待恢复」，不授予开窗口。父级当前已是被授予的 manager 才 `inherit`。
- 成环：第一次恢复去掉父级、权限 `read-only`、`parentClosed`。
- 顶层且 `openedBy=user`、角色是 manager：冷读当时不授予；用户续接或重新开始才走 `setWindowRole`（用户身份，`deliver:false`）。
- 断环之后 `openedBy` 不是 user：`decideManagerGrantRestore` 返回 `none`，不重新授权。

**必须修复 ①：父级不在了，高权限仍能启动。**

探针（第一次 `restoreColdLayout`，没有第二次 sync）：

- 删掉子窗口的 `parentWindowId`，`openedBy` 仍是 `{ windowId: "parent" }`，权限 yolo，角色 manager。恢复后权限仍是 **yolo**，父级为空。管理权动作是 `none`（不会开窗口）。`resolveLaunch(child, "yolo")` 为 `{ effective:"yolo", capped:false, cycle:false }`。
- 父级 id 写成树上没有的 `"missing"`，权限 yolo。恢复后权限仍是 **yolo**，`parentWindowId` 还在。`resolveLaunch` 同样是 yolo 且 `capped:false`。缺失祖先在 `resolveEffectivePermissionCeiling` 里直接 `break`，上限退回窗口自己的等级。

界面续接把布局里的 `permission` 交给 `launch-cli`。无父级时 `resolveLaunchPermission` 直接采用请求值，不再看注册表里是否本该只读。用户点续接，这个窗口会以 yolo 拉起 CLI。它不是管理者（`openedBy` 不是 user），但等级已经高于被删掉的祖先。这和 §3.3「不得把冷读到的权限当成顶层用户授权」不一致。断环会降成只读；单纯删掉父级或把父级指到不存在的 id，没有同一条处理。

建议修法：`openedBy` 不是 user，且父级缺失或父级 id 不在本棵树上时，与断环相同，权限降为 `read-only`。`resolveLaunch` 对这种窗口返回 `read-only`，不要采用渲染端传来的请求值。

**必须修复 ②：断环的只读盖不住下一次 sync。**

探针：磁盘上 A、B 互为父级，权限都是 yolo，`openedBy=user`，角色 manager。

- 第一次 `restoreColdLayout`：A 的权限 `read-only`，父级空，未授予。
- 紧接着对**同一份未写回的磁盘**调用 `syncLayout`：A 的权限变回 **yolo**，父级仍空，`resolveLaunch(A, "yolo")` 为 yolo 且不封顶。`decideManagerGrantRestore` 变成 **`user-reauth`**。

原因：`mergeRendererLayout` 的父级只认注册表（断环后已经没有），权限却取磁盘上的 `base.permission`。父级没了，sanitize 不再封顶。`permissionNeedsDowngrade` 只在传入布局自己带着这个标记时才保留，磁盘原件没有。

两条正常路径会走到第二次 sync：

1. 冷启动的 `get-layouts` 不把清洗结果写回磁盘。渲染端 `hydrate` 也不落盘。主进程注册表已经 `hasProject`。渲染进程重载会再要一次布局，这时走 `syncLayout(磁盘原件)`。
2. 用户续接一个冷读的顶层 manager 时，`setWindowRole` 用 `readLayouts()` 的磁盘窗口组对象，再 `saveLayout` → `syncLayout`。写回去的是磁盘上的 yolo，不是注册表里的只读。同时 `applyManagerGrant` 会授予管理权。

建议修法：冷启动清洗之后把结果写回磁盘；已经断环或标了降级的节点，后续 sync 不得用磁盘上更高的权限覆盖。`setWindowRole` 保存时用清洗后的窗口，不要把读出来的原始磁盘窗口原样写回。

**伪造的「顶层 + openedBy=user + role=manager + yolo」（建议，不阻断）：**

探针：冷读当时 `isManagerGranted` 为 false，权限保持 yolo，`decideManagerGrantRestore` 为 `user-reauth`，`resolveLaunch` 为 yolo。用户点续接会调用 `setWindowRole`（用户身份）并授予开窗口，CLI 按 yolo 启动。

这和用户自己建的顶层管理者是同一种形状。布局文件没有签名，有应用数据目录写权限的程序可以在重启前改成这样。合同写明：顶层、`openedBy=user`、角色 manager，续接视为重新授权。所以不把「能写数据目录」单独判成实现错误。

风险：用户以为是在续接自己的窗口，一次点击就同时拿到管理者工具和 yolo CLI。建议下一单在续接或重新开始 yolo 窗口、以及冷启动后第一次授予 manager 时弹确认（沿用新建窗口 yolo 的那句确认）。确认之前不要 `grantManager`，也不要按磁盘里的 yolo 启动。本单可以先把①②修掉；那条确认是给「看起来合法的顶层用户窗口」用的，①②修不掉这个形状。

E2E「重启后子窗口仍被封顶，续接管理者可以再开窗口」覆盖的是父级还在、子窗口被封成 `edit`、用户续接顶层管理者后能再开窗。它不覆盖删父级、悬空父级、成环后的第二次 sync。

## 4. C · 权限配对

2026-10-01 拉取 `https://code.claude.com/docs/en/hooks`：

| 事件 | 文档 | 现在的代码 |
|---|---|---|
| `PermissionRequest` | 有 `tool_name`、`tool_input`，**没有** `tool_use_id`。示例 Bash 输入是 `command` + 可选 `description` | 没有 id 时按摘要多重集 +1，phase 为 blocked |
| `PostToolUse` | 工具已经成功。`tool_input` 是实际交给工具的参数，另有 `tool_use_id`。用户或钩子改过输入时，这里是改后的对象 | 有 id 且这个 id 在未决集合里，只按 id 减。否则按摘要减 1 |
| `PostToolUseFailure` | 已经开始执行之后失败。**权限被拒绝不会触发** | 与 PostToolUse 同样只减配对上的那一笔。对不上就保持闩住 |
| `UserPromptSubmit` | 用户提交了新一句 | 清掉全部未决（id、摘要、无法配对的计数）。合同用来解开「批准时改了输入、摘要对不上」 |
| `Stop` | 回合结束 | 未决计数 > 0 时保持 blocked，不写入 |

规范化在 hook 进程里做：`JSON.parse` 之后按键名排序再 `JSON.stringify`，再对 `toolName + NUL + 规范化 JSON` 做 SHA-256。只上报工具名和摘要，正文不进管道。探针：键序不同、JSON 空白不同，摘要相同；字符串值里多一个空格，摘要不同。数组顺序保留。两边用同一个函数，所以 Claude 若把同一对象以不同键序或无关空白送进来，摘要稳定。一边多一个键或用户改了命令，摘要不同，继续闩住，直到 `UserPromptSubmit`。这是偏安全的卡住。

文档没有写 PermissionRequest 与 PostToolUse 的 `tool_input` 会多出或少掉字段。示例都是工具参数本身（Bash 为 `command` / `description`）。若某一侧多了字段，摘要对不上，结果是闩住不放，不会误开。

两次都弹出确认、输入相同：探针里连续两次 `permission-request`（同一摘要），一次 `post-tool-use` 之后 phase 仍是 `blocked`，随后的 Stop 也不写。单测「两次同摘要请求只结束一次时仍闩住」锁的是这条。

**残余（不阻断）：** 只有一次确认，却来了一次**没有对应 PermissionRequest** 的同摘要 `PostToolUse`（例如同一次输入里，另一条调用被自动允许并先跑完）。多重集会被减到 0，phase 变成 `busy`。探针里下一次 Stop 写入了 `hello` 和 `\r`。真实 Claude 在确认框还开着时通常还不发 Stop；伪造的 Stop 要等这次同摘要的结束事件先到，才能写进还开着的框。两次都在等确认的交错不会这样。没有 `tool_use_id` 时，合同选择的就是多重集，分不出「这是框对应的那一次」和「另一次相同输入」。建议保持现状，不要为了这一条退回「任意 PostToolUse 都清零」。

`UserPromptSubmit` 会清掉包括真实未关确认在内的全部计数。合同要它来解开摘要对不上的情况。同窗口若能伪造这个事件再伪造 Stop，仍可能在确认框上写入。这是产品决定留下的恢复口，不在本单重开。取消按钮只丢队列，不清这些计数。

stdin 等待 250ms。错过摘要时这笔请求变成无法配对，Post 减不掉，直到用户再提交一句。方向是卡住，不是误开。

## 5. D · flush 与关闭

点窗口 X 走 `BrowserWindow` 的 `close`：第一次 `preventDefault`，`requestFlush` 与 800ms 超时赛跑，然后 `allowClose` 再 `close()`。flush 抛错也继续关。连点时 `closing` 挡住第二次进入。渲染端先落盘再 `flush-ack`。`before-quit` 仍会再 flush 一次，预算也是 800ms，超时记日志后继续退出。两段是先后发生的，不是互相等待的环。`requestFlush` 只有一个 pending，重叠时前一个靠自己的定时器结束，不会把退出挂死。

没有单独的「close 超过 800ms 仍退出」单测（T10.2 曾建议补）。代码路径是超时放行。本单不因此阻断。

## 6. E · 徽章

`workbench:inbox-badges` 在 hydrate 时每个项目读一次 `index.jsonl` 尾部：最多 256KB，从中间切开时丢掉第一段残行，再最多保留 400 行。系统记录不进未读。游标 id 在这份尾部里时，只数它之后的消息和汇报；游标比整段尾部还旧时，尾部里的都算未读（这些确实还没读）。更老、已经滑出尾部的未读会少计，和产品决定一致。单行超过 256KB 且其中没有换行时，这段尾部会被当成空，徽章暂时没有。正常一行一条 JSON，不会这样。

最近汇报状态只看尾部里的 `kind:"report"`。E2E 重启后未读徽章和 `data-report-status=done` 还在。

## 8. 建议清单（非阻断）

1. 续接或重新开始「顶层 + openedBy=user」的 yolo / manager 窗口时弹确认，确认前不授予、不按磁盘 yolo 启动。见 §3。这挡的是能写应用数据目录的改写，①②修的是父级不在或断环没保住的情况。
2. 同摘要的额外 `PostToolUse`（这次调用本身没弹确认框）会把多重集减穿。见 §4。两次都弹框的交错是安全的。
3. `authorize` 对 `close` 自己返回允许。工具层已经拒绝。把纯函数改成拒绝，避免以后另有调用方只信 `authorize`。
4. 中间父窗口关掉之后，祖父不再能读或关孙窗口。非祖先也不能。若产品要保留祖父的控制，得在父节点已删除时继续向上走；那是能力，不是本单的越权。
5. `read_output` 会带回后代终端里已经打出的令牌和环境变量。给祖先看不构成提权。若要收紧，返回前涂掉本进程登记过的令牌。
6. 工具在没有父子链接时不跨项目。某一项目的布局若把 `parentWindowId` 指到另一个项目里存在的窗口，sanitize 只看本布局，全局注册表仍可能把它们连上。这同样要能写布局文件。①的修法若要求父级必须在同一棵已清洗的树里，顺手按项目隔离开。
7. 点 X 的 800ms 预算没有专测。行为在 `index.ts` 的 `close` 处理里。
8. 索引尾部单行超过 256KB 且没有换行时，徽章会空。见 §6。

## 10. 复验（2026-10-01，提交前最后一轮）

执行者声称已修：父级缺失或不在树上且 `openedBy≠user` 时只读并锁住；同会话再次 `syncLayout` 只留更低权限和原 `openedBy`，清洗结果写回磁盘，被清洗窗口续接不重新授权，只有界面 `workbench:set-permission` 或改角色能抬；续接/重新开始 yolo 或 manager 先确认，每窗口每次启动问一次，取消不启动；`authorize` 拒关自己；同摘要减穿仍登记为遗留。规则与首轮相同：只改本记录。

### 10.1 两个必须项（同一支探针，进程 cwd 为 `apps/desktop`）

| 情形 | 结果 |
|---|---|
| 删掉 `parentWindowId`，`openedBy` 指向原父窗口，磁盘 yolo + manager | 第一次恢复只读、父级摘掉、`openedBy` 仍是该窗口、`sanitizeLocked`。启动只读。管理权 `none`。再拿磁盘原对象 `syncLayout` 两次，仍只读、原 `openedBy`、不授权 |
| 父级 id 悬空（树上没有） | 同上：只读、锁住、`openedBy` 仍是那个悬空 id。再同步一次仍只读 |
| A↔B 成环，两边 `openedBy=user`、yolo、manager | 第一次只读、父级摘掉、锁住、管理权 `none`、启动只读。再同步磁盘原对象（对应渲染重载或续接写回之前那份）仍只读、`openedBy` 仍是 user、不重新授权 |
| 父级还在，子窗口磁盘 yolo | 封成 `edit`，不锁。父级管理者仍是 `user-reauth` |
| 真实顶层、`openedBy=user`、yolo、manager | **不锁**，启动仍是 yolo，管理权 `user-reauth`。这条靠确认框，不靠只读锁 |
| 清洗之后，渲染进程拿着 yolo + `openedBy=user` 再保存（没有走 `applyUserPermission`） | 仍只读，`openedBy` 留在原窗口，管理权 `none` |
| 界面路径 `applyUserPermission(child, edit)` 后再同步磁盘上的 edit | 锁解开，`userElevated`，权限 edit，启动 edit |
| `authorize` 关自己 | `{ ok: false, reason: "control-self-denied" }` |

冷启动第一次 `workbench:get-layouts` 会把清洗后的布局 `saveProject` 写回。同进程渲染重载时项目已在，走 `syncLayout(readAll())`。即便磁盘或内存里还是清洗前的 yolo，合并也只取更低权限和注册表里的 `openedBy`。

### 10.2 `workbench:set-permission` 的调用面

生产代码里唯一的调用是窗口权限编辑器的「应用」按钮。MCP 没有这个工具。布局保存、冷启动、`syncLayout` 都抬不了权限（见上表「没有走 `applyUserPermission`」那一行）。主进程处理函数不带操作者参数：同一渲染进程里的其它脚本如果直接 `invoke` 这条通道，主进程认。AI 子进程到不了这条 IPC。

改角色有一条界面之外的口子，不抬权限等级：`registry.setRole` 一律写 `userRoleSet`。成环被摘成顶层、`openedBy=user` 的窗口，`canSetRole` 允许它经 `ffpane_set_role` 把自己设成 manager，从而 `applyManagerGrant`。探针里 `selfSetManager` 为 true。启动权限仍被 `sanitizeLocked` 压成只读，而且要先通过确认框，CLI 才存在、才能调这个工具。见建议。

### 10.3 确认框取消不启动

`needsSensitiveLaunchConfirm`：本进程还没记住的窗口，权限是 yolo 或角色是 manager 时要问。记住只发生在点「启动」。取消和关掉对话框走 `finishSensitiveLaunch(false)`，不记住，下次再问。

续接、重新开始两个按钮都先 `await beforeUserRelaunch()`，返回 false 就 return，不会跑 `onResume` / `onRestartFresh`，也不会 `relaunchWith`。恢复出来的窗口 `autoStart` 为 false，挂载不拉起。出错横幅上的再启动只在已经启动过并失败之后出现；取消不会进入那条路径。

点「启动」会记住并放行。放行之后按钮自己 `relaunchWith`，同时 `onResume` / `onRestartFresh` 再加一次 `launchNonce`，可能连启两次。这是确认之后的事。
