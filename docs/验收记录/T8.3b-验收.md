### G. E2E（`task-parallel.spec.ts` 3 条）

**假 CLI 走 PATH 前置的全真实链路属实**：`_launch.ts:72-79` `pathPrepend` 就地改写 env 的 PATH 键（大小写不敏感查键，Windows 现实），`delimiter` 拼接前置；spec `beforeAll` 生成挂起替身（Windows `.cmd` ping 计时 / POSIX sh sleep 86400）+ 真实建项目/Provider/Profile（runtime=codex）+ 预写两个相交任务。链路：`session:start` → 编排器真裁决 → codex 适配器 spawn 假 CLI → 登记 → `sessions:active-turns` → 页面呈现——除 CLI 本体外无一处假。

**断言强度逐条评**：
1. **在飞区呈现**（`:119-147`）：**较强**——断言角色徽章、taskId、`writes: src/app`（信封交集产物）逐一可见。一处弱断言如实登记：`getByText("parallel seed task A")` 只证任务卡可见，锁不住「已推进 Running 列」（注释声称计数为 1 但断言未锁列），见 §2-5。
2. **相交被拒呈现**（`:149-162`）：**强**——冲突明细正则（两条路径 + `are nested` 关系词）+ Retry 按钮 + **Dispatch 按钮仍在**（任务保持 pending 的呈现层证据：推进 running 后 Dispatch 会消失）。
3. **取消后重试放行**（`:164-186`）：**强，是真等到了释放而非碰运气 sleep**——`toBeHidden({timeout: 20_000})` 是事件驱动的轮询等待（cancel → 树杀 → end → endedTurnSeq → 重取 → 空快照），上限 20 s 不是固定 sleep；随后 Retry → 拒绝提示消失 + **hash 变 `#/session`**（受理成功走导航的强证据）→ 回任务页断言 task-par-b 在飞。其对释放时序的敏感性经探针②变体证实（释放挪回 publish 后该断言 3/3 确定性红）——这条 E2E 就是钉住 B 项时序修复的用例。

**「真并发 E2E 不可行」落档说明合理性**：spec 头注 `:9-11` 与进度文档 §0 第 5 项同文——两个真子进程输出交错无从脚本化、「证据不串」要读适配器闭包内部状态；并发交错与 Run 隔离由编排器单测覆盖（C 项已核实其为真交错强断言），E2E 只验呈现。**评估：合理**——单测层的可脚本化事件队列是断言交错语义的唯一可控手段，E2E 补呈现层，职责划分与工单预许可一致。

## 2. 抽查发现

**未发现功能缺陷，未发现红线被绕开。** 以下如实登记（均不影响结论）：

1. **（时序细节，不影响结论）Worker 轮的 `startedAt` 与磁盘标记之间隔多个 await。** `admission.startedAt` 在裁决通过时取（`orchestrator.ts:516`），marker / transcript 落盘在其后的 `saveTask` / `registerSession` 等多个 await 之后（`:884-908`）——极端慢盘下 startedAt 与「有子进程在跑」之间有毫秒级窗口，但 marker 仍严格先于 spawn（`:910`），T8.2b 的「有子进程必有标记」不被破坏。
2. **（正面观察）健康 cancel 不误告警的实现比声称更细。** 强制释放的条件是 `outcome === "grace" && parallelTable.has(turnId)`（`:563`）双重判定——即使 grace 先到、只要 drain 已把表删了也不告警，warn 只在真悬挂时出现，单测以 warn spy 精确断言零次误报。
3. **（口径核实）「派发钮不预判禁用」与 §1.5-3「即时反馈」不冲突。** 被拒时冲突提示条同步呈现（ack 返回即 set state），反馈在 100ms 量级；预判禁用反而会因渲染层快照时差而撒谎（交付报告 3② 的裁量成立）。
4. **（边界登记，维持现状合理）`startNewSession` 不清在飞 Map 的一个可观察边界**：本会话无在飞轮但**别会话** Worker 在飞时新建会话，随后该 Worker 的 started 事件会把 `activeSessionId` 切到它的会话（`ingestSessionEvent:395` 维持「派发即进入执行视图」的既有行为）——「新建」的空白视图可能被后台轮的 started 拉走。这是 T4.2 既有行为与多轮并发的交叠，非本单引入；用户主动派发后本就期望进入执行视图，不构成缺陷。
5. **（E2E 弱断言一条，不影响结论）`task-parallel.spec.ts:146`** `getByText("parallel seed task A")` 只证任务卡可见，未锁「Running 列」——「任务已被派发推进 running」的注释声称比断言强。主进程侧的推进已有编排器单测钉住（dispatchTask 后 saveTask），呈现层此处弱一档，成本一行（按列容器 locator 收窄），建议顺手补强，不单独立项。
6. **（flake 定性与登记，不影响结论）E2E 第 3 条「取消后重试放行」在本机负载异常时超时一次**（首次全量跑 25/26，失败于 `:173` `toBeHidden` 20 s 超时；该跑全程 2.8 分钟、单测试半分钟以上，机器负载异常）。定性证据：干净 HEAD 下单文件复跑 3/3 绿 ×2 + 循环 6 连跑全绿 + 全量复跑 26/26 ×2（17.8 s / 51.9 s）；对照探针②变体（释放挪回 publish 后）同断言 **3/3 确定性红**——真缺陷是确定性失败，与负载性超时的表现截然不同。cancel → 树杀（taskkill /T）→ end 的链路在重负载下超 20 s 属环境瓶颈，登记为已知 flake（同 adapters cancel 用例的性质），不构成缺陷。
7. **（正面观察）「归属缺失宁拒勿并」分支的注释自证其可测性**（`orchestrator.ts:479-482`）：明言该分支只在注销点被部分破坏时可观察、是 T8.3a §3-④ 用例的锚点——把「防御码为何测不红」写在防御码旁边，是 T8.2b-b 验收 §3-1 教训的正确内化。
