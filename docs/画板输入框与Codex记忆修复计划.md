## 1. 画板：新图出来，旧图就不见了

### 1.1 查到的原因（2026-10-24，《海上生存日记》）

不是画板自己清图，是执行窗口按说明删的，**连文件一起从磁盘删掉**。

- 管理者写的 `.ffpane/briefs/isl03d-1-执行.md` 第 22 行：「图生成在 `.ffpane/canvas/`，复制到 concept 目录后，用 `ffpane_delete_canvas_file` 删掉画板上的原图。」
- 执行窗口「isl03d-1 礁石滩地点设计」（会话 `a6f7dec0`）18:26–18:35 每出一张图：看一眼 → 复制到 `model/Islands_Delivery/ISL/M_ISL_03_ReefBeach_Terrain/design/concept/` → 删原图。
- 复制出去的有 `00_aerial.png`、`01_north_sea.png`、`02_north_landing.png`。第一张 `gen-3cda862f…png` 被判不合格，**没复制就删了**；会话记录里还留着它读图时的内容（重新压缩过的 JPEG，画质低于原图）。
- 写计划时这个窗口还在跑，18:35 又出了一张 `gen-83004745…png`。

代码里的问题：

1. **删图没有任何限制。** 工具描述写「只有用户明确说要清理时才调用」，`mcp-tools.ts` 的 `deleteCanvasFileTool` 不做任何检查，所有角色都能直接删磁盘文件，删了找不回。
2. **没有「导出」。** 想把图放进项目目录，只能「复制再删」。
3. **生图每次都报假超时。** MCP 控制通道默认 20 秒（`mcp/workbench-server.ts` 的 `CALL_TIMEOUT_MS`），只给 `ffpane_wait_events` 放宽了。生图要 25 到 60 秒，这次 5 次调用全部返回「控制通道超时」，图随后才出来，执行只能 `sleep` 再 `ls` 去找。模型要是以为失败而重试，会重复出图、重复扣额度。
4. **画板数据写入不安全。** 画板目录留着 4 个 `.board.json.*.tmp`，每个都是一次没写成的画板数据：
   - `canvas-files.ts` 的 `writeAtomic` 在 Windows 上改名失败时不重试、不删临时文件；
   - 自动收图（`canvas-watcher.ts`）、删图、放图、改标注、界面保存（`saveCanvasBoard` 整份覆盖）各自「读 → 改 → 写」，不排队，同时写会互相覆盖、丢行。

### 1.2 Tony 定的规则（2026-10-24）

- **AI 窗口可以删图，但只能删 Tony 确认不要的**，不是什么都删。
- **Tony 自己也可以删。**
- **两种删除都进回收站**，不直接删磁盘文件。
- 今天的图要放回画板；放回几张、哪几张，**开发时按当时的情况定**（到开发时还会有新图出来、被删）。

### 1.3 改法

**A. 删除和回收站**

- 回收站：`.ffpane/canvas/.trash/`。每张图带一条记录：谁删的（Tony / 哪个窗口）、什么时候、原因、原来在哪一页哪一行。
- 画板界面加「回收站」：能看、能恢复（回到原来的页和行，行没了就放到页末）、能彻底删除。**彻底删除和清空回收站只有 Tony 能做**，不自动清。
- Tony 在画板上删图 → 进回收站。
- Tony 可以在画板上把图标成「不要」（不删，只打标记）。
- AI 调 `ffpane_delete_canvas_file`：
  - 图已被 Tony 标成「不要」→ 进回收站，返回成功；
  - 没标 → **不删**，在画板这张图上挂一个「某窗口申请删除：原因」，Tony 点「同意」进回收站、点「保留」撤销申请。工具返回「已申请，等 Tony 确认」。
  - 工具参数加必填的 `reason`。

**B. 导出**

新工具 `ffpane_export_canvas_image`：把画板上的图复制到项目内指定路径（不能越出项目根，目标已存在时要显式 `overwrite`），**原图留在画板**，并在这张图上记下「已导出到 …」。画板上能看到每张图被导出到哪里。

**C. 生图不再报假超时**

- 控制通道给 `ffpane_generate_image` 单独放宽到 5 分钟（照 `ffpane_wait_events` 的写法）。Codex 那边 1.0.8 已加 `tool_timeout_sec=600`，Claude 真机核对一次 5 分钟内能返回。
- 成功时返回新图路径和所在页、行；失败时返回原因（1.0.11 已能带上「Codex 说：……」）。
- 同一窗口上一张还没出完时再调，直接返回「上一张还在生成」，不重复出图。

**D. 画板写入**

- 同一个项目的画板写入排队，主进程里一个项目一条队列，所有改动都经过它。
- 写入改用 `packages/storage` 的 `writeTextAtomic`（失败会清临时文件），改名遇到 Windows 的 EPERM / EBUSY 重试几次。
- 界面保存不再整份覆盖：改成提交「改了哪些」，主进程合并；或者带版本号，版本对不上就先重读再合并。
- 启动或打开画板时，清掉超过 10 分钟的 `.board.json.*.tmp`。

**E. 说明书**

- `manager.md`：画板是项目图库。要把图放进项目目录用导出，不要让执行删图。
- `base.md`：删图要写原因，没被 Tony 标「不要」的只会变成申请。

**F. 找回今天的图（开发时做）**

开发时才定张数，所以做成开发时跑一次的「画板找回」：

1. 扫这个项目从 2026-10-24 起的会话记录（Claude、Codex），列出所有 `ffpane_delete_canvas_file` 调用。
2. 每张被删的图，查它被复制到了哪里（同一会话里删之前的 `cp`、`Copy-Item` 命令），核对目标文件还在。
3. 列成表交 Tony：图、什么时候删的、副本在哪 / 没有副本（能否从会话记录导出低画质版）。
4. Tony 勾选后放回画板：有副本的从副本拷回 `.ffpane/canvas/`，按原来的出图时间排进原页；没副本的按 Tony 的选择导出低画质版，或不放。
5. 画板当时还在 `.ffpane/canvas/` 里、却不在画板数据里的图，一并列出来。

### 1.4 验收

1. AI 删没标「不要」的图：图还在，画板上出现申请；Tony 同意后进回收站。
2. AI 删已标「不要」的图：直接进回收站；回收站能恢复到原位置。
3. 只有 Tony 能彻底删除、清空回收站；AI 调用不到。
4. 导出：原图仍在画板，目标文件和原图一致，画板上显示导出位置。
5. 生图：真机 Codex 订阅出一张图，工具一次返回成功和路径，不再报超时。
6. 并发：一边生图、一边在画板上改标注、一边删一张，画板数据不丢行，不留 `.tmp`。
7. 找回：用《海上生存日记》开发时的实际情况跑一遍，表里的每张图都核对过，Tony 勾选的放回原页。

## 2. 输入框：我没打完，就和别的消息一起被提交了

### 2.1 原因

投递代码（`main/workbench/idle-deliver.ts`）只在窗口空闲、**1.5 秒没有按键**、1.5 秒没有输出时，把消息打进输入框再回车。

1. **只看时间，不看内容。** 停下想一想超过 1.5 秒，平台就当打完了，把消息接在半句话后面，一个回车全发出去。
2. **输入法选词时看起来是静默的。** 打拼音、选候选词时终端收不到任何字，选定才发过去；按键时间只在主进程收到终端输入时记（`main/index.ts` 的 `onUserInput`）。
3. **可能把用户的字清掉。** 没提交成功时平台按 4 次 Ctrl+U（`CLEAR_INPUT_KEYS`）清空输入框再重打。框里原本有用户的字，会一起清掉。

### 2.2 定的做法：等用户发完，再按顺序投

不做「绕过用户的输入直接提交」：要先存草稿、清空、发消息、再打回草稿，多行、粘贴（`[Pasted text …]`）、图片都恢复不了；消息发出后 CLI 开始干活，打回的草稿会被排进队列或当成下一句。失败就丢字，比现在更糟。

**A. 输入框有字就不投**

投递前读屏幕上的输入框（`prompt-ready.ts` 已能认出 Claude、Codex 的输入框；在 `inputStillHolds` 旁边加「输入框里现在有什么」）。有字，自动投递一律等着，不管停了多久。

**B. 用户发出后再投**

用户回车 → 这一轮开始 → 回合结束、输入框空 → 按原有排队规则一条一条投。

**C. 输入法和按键算在打字**

渲染端把输入法开始和结束选词（xterm 输入区的 `compositionstart` / `compositionend`）、按键报给主进程，记进 `noteInput`。正在选词时不算静默。

**D. Ctrl+U 只清平台自己的字**

只在投递前输入框为空时投，所以没提交时清掉的只有平台刚打的那条。投递前框里有东西，就绝不按 Ctrl+U。

**E. 看不清输入框时多等**

读不出屏幕（返回「看不出」）时：用户正在这个窗口（有焦点、60 秒内按过键）就不投；否则静默要求拉长到约 10 秒。

**F. 告诉用户在等什么**

窗格上显示「N 条消息等你发完这句」。手动「立即发送」也一样：框里有字时不发，提示先发完或先清空。

代价：用户在某个窗口里打了半句就走开，发给它的消息会一直等，监管者、管理者的提醒会晚到。F 的提示就是为这个。

### 2.3 验收

真机 Claude 2.1.302、codex-cli 0.162.0 各测：

1. 打半句停 5 秒：消息不投；发出后，回合结束再投。
2. 用输入法打中文，选词停顿：不投。
3. 多行草稿、粘贴一大段：不投，草稿不被改动。
4. 投递没提交（模拟回车被吃）：Ctrl+U 只清平台那条，之前框是空的。
5. 「立即发送」在框里有字时被拒绝，并提示。
6. 原有 e2e（提交核对、括号粘贴、Codex 800ms 回车间隔）照样过。

## 3. Codex 窗口带着别的项目的记忆

### 3.1 原因

不是因为开着 Codex 桌面版。是 **Codex 的「记忆」功能**：`~/.codex/config.toml` 里全局开了 `[features] memories = true`、`[memories] generate_memories = true`、`use_memories = true`。FF-pane 开的 Codex 窗口读同一份配置，每个窗口启动都被塞进所有项目的记忆。

- 2026-10-24 16:45 开的监管者「监管4」（会话 `01a16d15`，工作目录正确）：启动时的系统说明 28625 字，**其中 26560 字是 Codex 记忆**，内容是 fuwuqi / CPA、3D--test--youtube 的 ART09、ai_spine、music_and_sound 等别的项目；角色说明只占约 2000 字。
- 记忆存在 `~/.codex/memories/`（`memory_summary.md`、`MEMORY.md`、`raw_memories.md`、`rollout_summaries/`，约 165KB，不分项目）。真正的来源是 `~/.codex/memories_1.sqlite` 的 `stage1_outputs` 表（每个会话一条），那几个文件是合并时生成的。
- 反过来也污染用户的个人记忆：FF-pane 的团队会话会被总结进去。
- 桌面版、VS Code 插件、FF-pane 命令行窗口共用同一个 `~/.codex`，所以全部共用这份记忆。
- Claude 窗口没有这个问题：Claude Code 的自动记忆按项目分开存。

### 3.2 改法

FF-pane 开 Codex 窗口（含续接）时，只对这个会话加：

```
-c features.memories=false -c memories.use_memories=false -c memories.generate_memories=false
```

- 这三个名字在 codex-cli 0.162.0 上核实过（`codex features list` 显示 `memories` 默认开；程序里有另外两个）。
- **不改用户的 `config.toml`**，用户自己用 Codex 时记忆照常。
- 项目自己的规则走角色说明书和 `ffpane_memory_search`，不靠 Codex 全局记忆。

### 3.3 清理用户个人记忆里来自 FF-pane 的部分（修好后马上做）

Tony 定：**过期的清掉；没过期的暂时保留，让 Codex 或管理者能读到。**

为什么修好后才做：修好之前，每个新的 FF-pane Codex 会话都还会被总结进去（今天的监管者会话也会），现在清了还会回来。

2026-10-24 的检查结果：

| 会话总结 | 是不是 FF-pane 的 | 结论 |
|---|---|---|
| `2026-09-29…ow56-player_drifter_lowpoly_quick_sample` | 不是：Tony 在 profile_3d_workbench 里自己用 Codex，只是提到海上生存的模型目录 | 保留，不碰 |
| `2026-10-07…yhw7-ui_formal_clean_delivery_export` | 不是：Tony 在海上生存 UI 目录里自己用 Codex（来源 vscode） | 保留，不碰 |
| `2026-10-23…tlDd-supervise_dgc02_dgc09_recovery` | 是：FF-pane 监管者窗口 | **过期**：写着「DG-C09 仍在忙、没完成」，项目记录里 DG-C09 检查已于 10-23 通过（阻断 0），DG-C02 早已提交；里面的经验（服务端错误后不要盲目 nudge、只能读自己后代或挂在名下窗口的输出）已经写在监管者说明书里，`nav` 本地化的裁定在项目提交和修复单里 |

步骤：

1. 关掉 Codex 桌面版和 VS Code 的 Codex（它们会占着这几个数据库）。
2. 备份：`~/.codex/memories/` 整个目录、`memories_1.sqlite`、`state_5.sqlite`（含 `-wal` / `-shm`）复制到 `~/.codex-memory-backup-<日期>/`。
3. 找出 FF-pane 的 Codex 会话：`state_5.sqlite` 的 `threads` 里来源是 `cli`、工作目录在 FF-pane 项目里、第一句是「你是 X 窗口」「[新消息]」「[继续]」这类平台固定开头的。
4. 每个有记忆的会话判断过没过期（任务已完成或被取代、经验已写进说明书或项目文档 = 过期）。
5. 过期的：
   - `threads.memory_mode` 设为 `polluted`。这是 Codex 自己用来把会话排除出记忆的状态（程序里的查询带 `memory_mode != 'polluted'`），比只删文件可靠；
   - 删掉 `memories_1.sqlite` 里 `stage1_outputs` 的对应行；
   - 从 `MEMORY.md`、`memory_summary.md`、`raw_memories.md` 删掉对应段落，删掉 `rollout_summaries/` 里的对应文件。
6. 没过期的：留在个人记忆里；有用的项目经验整理成 `ffpane_memory_add` 的待审核记忆，Tony 在记忆页通过后，管理者用 `ffpane_memory_search` 能查到（FF-pane 的 Codex 窗口修好后不再读个人记忆）。
7. 开一次 Codex，确认合并后被清的内容没有回来；没过期的、非 FF-pane 的都还在。
8. 把清了哪些、留了哪些写进这一批的验收办法。

### 3.4 验收

1. 新开 FF-pane Codex 窗口：系统说明里没有 `## Memory` 段；续接后也没有。
2. 用户自己开 Codex：记忆照常；`config.toml` 没变。
3. FF-pane Codex 会话结束后，`stage1_outputs` 里没有它的新记录。
4. §3.3 清理后，再开一次 Codex，被清的不回来。

## 4. 风险

- 回收站会越来越大：画板上显示回收站占了多少空间，由 Tony 决定什么时候清。
- 「输入框有字就不投」读屏判断错：判成有字只会多等；判成空才会出事，所以看不出时按「有字」处理（§2.2 E）。
- 改 Codex 数据库：先备份；只在 Codex 全关的时候改；只改 FF-pane 的会话。
