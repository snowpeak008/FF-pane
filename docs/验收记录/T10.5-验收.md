## 2. A · 令牌泄露与越权（最高优先级）

威胁模型：一个 edit 或 edit-exec 的子窗口，其 AI 能读文件或跑命令，试图拿到父窗口（管理者）的 `FF_PANE_WINDOW_TOKEN`，再向主进程冒充管理者。yolo 本身无限权限，不纳入。

### 2.1 令牌实际落在哪

- 签发：`createWindowTokenRegistry` 用 `crypto.getRandomValues` 生成 32 字节（64 hex），只放主进程内存 `Map`。同窗口再次 `issue` 会删掉旧令牌。
- 送达 CLI：`launchCliWindow` 把令牌放进 PTY 子进程环境 `FF_PANE_WINDOW_TOKEN`。`assertTokenAbsent` 检查 argv，不含该值。
- Claude **且** `mcpServers` 非空（当前即项目开启了知识库工具）时：`injectTokenIntoMcpServers(..., "claude-file")` 把令牌写进 MCP 规格的 `env`，再 `writeWorkbenchClaudeMcpFile` 落到临时 JSON。注释写明「Claude MCP 文件允许含令牌」。
- 知识库工具关闭时不写这份文件，令牌只在 CLI 进程环境里。T10.7 一旦给每个窗口挂工作台 MCP，这条路径会变成默认。
- Codex：只把变量**名**放进 `mcp_servers.<name>.env_vars`，并从 `env` 表删掉令牌值，避免 `buildCodexMcpOverrides` 把值写进 `-c`。这条是对的。

### 2.2 ① 临时文件是否可预测、可枚举

| 点 | 事实 |
|---|---|
| 目录 | `os.tmpdir()` + 前缀 `ff-pane-wb-mcp-` + `mkdtemp` 随机后缀 |
| 文件名 | 固定 `ff-pane-mcp.json` |
| 可预测性 | 完整路径不可猜（后缀随机） |
| 可枚举性 | **可以**。前缀固定，同用户 `Get-ChildItem $env:TEMP -Filter ff-pane-wb-mcp-*` 即可列出。本轮在 `%TEMP%` 按同一写法建过一份探针，枚举命中后已删除 |
| 寿命 | 窗口整个存活期都在；正常退出/关窗才 `release`。崩溃残留要等启动清扫（默认 1 小时）。清扫前文件还在，但进程已死、内存表已空，残留令牌解析为 null |
| 命令行 | argv 含 `--mcp-config <绝对路径>`。同用户可读其它进程的命令行，随机目录名因此也会暴露 |
| 谁能读 | 见下表 ACL |

本机对探针文件执行 `icacls`（继承自用户 Temp，应用自己没有收紧 ACL）：

- `SNOWPEAK\admin`：完全控制
- `NT AUTHORITY\SYSTEM`、`BUILTIN\Administrators`：完全控制
- `SNOWPEAK\CodexSandboxUsers`：修改（继承）
- 另有多条继承的「修改」项

同用户的子窗口读这份文件不需要提权。Claude 的 `read-only` 只拒绝 `Edit Write NotebookEdit MultiEdit Bash`，**不拒绝 Read / Glob**。plan 模式本身允许读。因此最低一级的只读窗口，在知识库 MCP 开着时，就可以按前缀枚举并读出**所有**正在跑的 Claude 窗口令牌，包括管理者。edit / edit-exec 同样可以。含活令牌即构成越权路径。

### 2.3 ② Claude 是否把自身环境变量继承给 stdio MCP

**不继承任意变量。** 证据：

1. 本机 `claude.exe` 2.1.220（265,720,480 字节）内嵌了 MCP SDK 的继承白名单，紧挨 `process` / `stream` / `win32`。Windows 列表为：`APPDATA`、`HOMEDRIVE`、`HOMEPATH`、`LOCALAPPDATA`、`PATH`、`PROCESSOR_ARCHITECTURE`、`SYSTEMDRIVE`、`SYSTEMROOT`、`TEMP`、`USERNAME`、`USERPROFILE`、`PROGRAMFILES`。另有 Unix 列表 `HOME`、`LOGNAME`、`PATH`、`SHELL`、`TERM`、`USER`。`FF_PANE_WINDOW_TOKEN` 不在其中。
2. 该形状与 `@modelcontextprotocol/sdk` 的 `getDefaultEnvironment()` 一致：只拷贝白名单，再叠上配置里的 `env`。配置里给了 `env` 也不会因此把父进程的其余变量带上。
3. 官方 MCP 文档（code.claude.com/docs/en/mcp）说明 stdio 服务器的环境由客户端装配，并单独注入 `CLAUDE_PROJECT_DIR`；没有「父进程全部环境变量原样继承」的承诺。
4. 本仓 `docs/adapters/claude-code.md` 未记载这条继承规则。既有知识库 MCP 的做法是把路径写进配置 `env`（`apps/desktop/src/mcp/server.ts` 头部已写明：claude 的 env 会落进临时 JSON），与「密钥不能进这个文件」是同一条纪律。令牌现在违反了这条纪律。

因此：删掉文件里的令牌之后，MCP 子进程**不会**从 Claude 进程环境里看到 `FF_PANE_WINDOW_TOKEN`。知识库 MCP 今天并不读这个变量；T10.7 的工作台 MCP 若依赖它，必须另开通道。

**替代方案（必须按这个方向修，不要只加 ACL）：**

1. 临时 JSON 的 `env` 里只放一次性引用码（高熵、数秒有效），**不放**长期窗口令牌。
2. 主进程起一个本机兑换口（命名管道或已有的本机通道）。我们自己启动的 MCP 进程在起来后立刻用引用码兑换，主进程把该连接绑定到窗口，然后**立即作废**引用码并删掉文件。
3. 兑换须核对调用进程的父进程是刚拉起的那个 CLI（同用户的兄弟窗口父进程不是它）。只靠「谁先读到文件谁兑换」仍有竞态。
4. 「把文件 ACL 收成仅当前用户，并在 CLI 启动后删除」**不能**当作修复：攻击者就是同一用户；本机 Temp 上当前用户本来就是完全控制，`CodexSandboxUsers` 甚至能改。启动后删除只能缩短窗口，命令行里的路径在删除前仍然指向那份文件。

Codex 的 `env_vars` 白名单可以继续用：值留在 CLI 进程环境，`-c` 里只有名字。

### 2.4 ③ edit-exec 读取其它进程环境变量的难度（评估）

令牌留在管理者 CLI 的进程环境里，是比临时文件好的主通道，但不是操作系统隔离。

- `Get-Process` / 任务管理器默认不显示环境块；WMI `Win32_Process` 也不带环境块。
- 同用户、同一完整性级别下，对非保护进程 `OpenProcess` 后读 PEB 环境块是公开技术，需要一小段本机代码，不是一条现成命令。
- Claude `edit-exec` 的 Bash 仍由 CLI 询问，用户能看见可疑命令。
- Codex `edit-exec` 是 `approval_policy=never`，且计划已说明 Windows 上 `workspace-write` 不是 OS 隔离，这条不能当安全边界。
- 难度：**中等**。比「Glob 一下 `%TEMP%` 再 Read」高一个数量级。修掉文件泄露之后，残余风险接受为「Windows 非 OS 隔离」的已知边界，不单列必须修复。yolo 不纳入。

### 2.5 ④ 日志 / 报错 / `terminal:list` / IPC

| 通道 | 判定 |
|---|---|
| `workbench:launch-cli` 响应 | 只有 terminal、kind、session id、profile 名、model。无 args、无令牌 |
| `terminal:list` 的 `TerminalInfo` | 无 `env`。metadata 为 windowId / projectId / kind / profileId / nativeSessionId |
| argv | `assertTokenAbsent` 拒绝令牌出现在参数里。E2E 断言 argv 中无 64 位 hex，且环境变量为 `present` 而非明文 |
| 抛错文案 | 「窗口令牌出现在命令行参数或落盘内容中」不含令牌值 |
| 临时 MCP 文件 | **例外被写进代码**：允许含令牌。这就是 §2.2 的洞 |
| PTY 输出 | 本产品不把令牌写进终端。CLI 若自己打印环境变量则另说，当前路径没有 |

### 2.6 ⑤ 比较是否常时、吊销是否及时

- 比较：`byToken.get(token)`，V8 的 Map 字符串键，**非常时**。没有 `timingSafeEqual`。比较只发生在主进程内存，令牌 32 字节。经 IPC 计时去爆破 256 bit 不现实。列为建议：T10.7 入口若要做字符串比较，用常时比较；现状不单列必须修复。
- 吊销：
  - 启动失败：`revoke`
  - 终端退出 / `kill`：`onTerminalExit` → `releaseMcpForTerminalMetadata` → `revoke`，并删临时目录
  - 同窗口再次启动：`issue` 先删旧令牌
  - 应用 `will-quit`：`tokenRegistry.clear()`
  - 进程重启或崩溃：注册表在内存里，旧令牌全部失效
- 活着的窗口在退出前，文件里的令牌一直有效。这是 §2.2 的问题，不是吊销迟到。

## 4. C · 授权函数

### 4.1 纯函数在正常树上是收紧的

`authorize` / `canDelegate` 对样例树（用户开的 M → W → G，兄弟 S，无关 X）覆盖了：用户可调任意窗口；不能调自己、不能调祖先；对祖先只能 `report`；对子孙可控制和调权且不能超过自己；`send-message` 只允许子孙，兄弟与无关拒绝；已关闭的**直接**父级仍可 `report`；`open-child` 超过父级拒绝；降级给后代打 `permissionNeedsDowngrade` 并写下封顶后的等级；关父级保留子节点并标 `parentClosed`。

没有「窗口调用方默认允许」的末尾分支。未知动作返回 `unknown-action`。用户分支按合同恒允许（缺目标、缺新等级除外）——这是「用户最高」，不是漏洞。

### 4.2 覆盖缺口与环

单测没有穷尽：

- `canDelegate` 只断言了 4 对，不是 4×4
- 没有环
- 没有「链中间缺节点」
- 没有「窗口替别人开子窗口」（`authorizeOpenChild` 会拒，但穷举段未写）
- 孙辈向**已从树中删除的祖父** `report`：实现走 `target-not-found`。特例只认直接 `parentWindowId`。与「含已关闭父级链路」相比偏窄，列为建议

环的行为（必须修）：`listAncestorIds` 用 seen 防死循环，但 A↔B 时双方都会出现在对方的祖先列表里。`isDescendantOf` 因此双向为真，`send-command` / `close` / `adjust-permission` 双向放行。干活窗口一旦和管理者形成环，就可以反过来控制管理者。

### 4.3 parentWindowId 能否被伪造

| 入口 | 能否伪造 | 后果 |
|---|---|---|
| CLI / `workbench:launch-cli` | 契约**没有** `parentWindowId` | 不能靠这个 IPC 声称自己是某窗口的子窗口 |
| 同一 IPC 的 `permission` | **能**。主进程 `isWorkbenchPermissionLevel` 之后原样使用，默认 `edit`，不看父级 | 渲染端传 `yolo` 就会带 `--dangerously-skip-permissions` 拉起 |
| 渲染端 `createTabWithWindow` / `splitWindow` | **能**。`parentWindowId` 与 `permission` 原样写入，不调用 `canDelegate` | 当前新建对话框和 `WorkbenchPage` **不传** `parentWindowId`，界面上新开的都是「由你开启」的顶层，用户选任意等级符合「用户最高」 |
| 布局文件 | **能**。`parseWindow` 接受任意 `parentWindowId` 字符串和任意合法等级，不查环、不查子≤父 | 下次启动渲染端把存盘的 `permission` 再交给 launch |

伪造 `parentWindowId` **不会**自动继承父窗口的 CLI 等级（等级是另一个字段）。反向把高权限窗口的 `parentWindowId` 指到低权限窗口，会让 `authorize` 把低权限窗口当成祖先。今天应用里还没有人调用 `authorize`（留给 T10.7），所以这条还没变成在线控制面。但布局已经会把这棵树存下来。

edit 级 Claude 的拒绝名单里没有 Write。布局文件在用户数据目录（代码注释：`~/.aiworkbench/workbench-layouts.json`；本验收未打开该目录）。Windows 上 `acceptEdits` 不是 OS 沙箱。子窗口若能写到该文件，就可以把自身 `permission` 改成 `yolo` 或改写父子关系，下次启动主进程会照做。

`effectiveLaunchPermission` 已导出但全仓无调用；有上限时两个分支都是 `min`，`needsDowngrade` 不影响结果。渲染端 `setWindowPermission` 会把超限后代的**存盘等级**先改低并打「需重启」。诚实的界面路径因此会在下次启动带上较低参数。主进程自己不复核。

**必须修复：** 主进程在 launch 与读布局时持有封顶（子级 ≤ 开启它的窗口，拒绝环）。渲染端传入的 `permission` 不得超过该窗口已登记的上限。用户对顶层窗口的任意设定仍走「用户」这个调用方，不要做成窗口也能改自己的祖先。

### 11.1 A · `--mcp-config` 是否展开 `${FF_PANE_WINDOW_TOKEN}`

官方文档把「环境变量展开」写在 `.mcp.json` 一节（`command` / `args` / `env` / `url` / `headers`；`${VAR}` 与 `${VAR:-default}`；变量缺失时保留未展开原文并警告）。文档没有单独写「`--mcp-config` 文件同样展开」。

本机 Claude Code **2.1.220** 的安装包里，`--mcp-config` 走的就是这条展开。启动时对每个参数先尝试当 JSON 解析，失败则当文件路径读入；两条都调用同一解析函数，并且 **`expandVars` 为真**（作用域 `dynamic`）。警告文案前缀就是 `--mcp-config:`。stdio 条目的 `env` 值经 `${…}` 替换，数据来自 Claude 进程自己的环境。展开发生在内存里，不把展开结果写回文件。

因此生产路径（临时文件 + `--mcp-config`）与执行者用项目级 `.mcp.json` + `claude mcp list` 验证的是同一套展开，不是另一条不展开的通道。

没有再用对话复现探针：`claude mcp list` 不接受 `--mcp-config`（该选项会把后面的子命令吃成配置路径）。`claude -p` 会打到模型，本轮不跑。展开结论以这台机器上的 2.1.220 二进制为准。

失败模式（仅当未来的 CLI 不再展开时）：sidecar 收到字面量 `${FF_PANE_WINDOW_TOKEN}`。它不是任何窗口的令牌，不能冒充任何人，属于安全失败，但 T10.7 的身份会静默不可用。建议 sidecar 或主进程认出这个字面量并给出明确错误。这是防御，不是本单阻断，也不是当前 2.1.220 的缺陷。

### 11.3 C · 封顶、环、IPC 能不能造父子

在 `%TEMP%\ff-pane-t105b-layout` 用隔离的登记表喂了四份布局 JSON（不碰 `~/.aiworkbench`）。4 条探针全部通过。

| 构造 | 结果 |
|---|---|
| 冷登记 + 子窗口自称父级是管理者、权限 yolo | 父级被丢掉，**权限仍是 yolo**。没有父级可封顶。`resolveLaunch` 对登记里不存在的窗口直接采用请求权限 |
| 主进程已 `upsert` 父（edit）与子（父级指向该父）后，布局把子改成 yolo，并伪造另一个父级 | 父级保持已登记的那个；权限封顶为 edit；`resolveLaunch(..., "yolo")` 为 `{ effective: "edit", capped: true }` |
| 两边都已登记成环（A↔B，权限 yolo）后再 sync | 断父、`parentClosed`、权限变成 read-only。之后 `authorize` 控制对方为拒绝 |
| 冷登记 + 文件里就是 A↔B 环 | 父级先被丢掉，环看不见，权限保持文件里的 yolo / edit，**不会**收成 read-only |

渲染端不能通过 IPC 建立父子：

- `workbench:launch-cli` 拒绝 `parentWindowId` 和 `openedBy`。合同类型里没有这两个字段。
- 唯一写入登记父级的产品代码是启动成功后的 `upsert`，而且只复制登记里**已经有**的父级，不采用本次 IPC。
- `get-layouts` / `save-layout` 都经过 `syncLayout`：渲染端或文件里的 `parentWindowId`，除非该窗口在登记里已经有父级，否则一律不采用。
- 全仓库没有别的 IPC 处理函数去 `upsert` 一个新父级。

同一次运行里，伪造父级、抬过已登记祖先、成环，这三件事都做不成。

冷启动是另一回事。登记表是空的，盘上的父级链接会被全部丢掉（包括以后 T10.7 正当写进去的父级），盘上的 `permission` 会原样留下。应用自己 `save-layout` 时，若当时父级已在登记里，写出的是封顶后的值，正常保存不会抬权。进程外改布局文件再重启，可以把一个曾经的子窗口变成「无父 + yolo」。`save-layout` 只返回 `{ ok: true }`，不把清洗结果退回界面；渲染端内存里仍可以暂时显示一个伪造父级，直到下次 `get-layouts`。那只影响界面，不影响启动权威。`remove-layout` 不从登记里删窗口，方向是多留一道封顶，不是放大权限。

冷读还会接受盘上的 `openedBy`（只要对象里有非空 `windowId`）。没有父级时这不构成控制权，但标题可能显示伪造的「由谁开启」。
