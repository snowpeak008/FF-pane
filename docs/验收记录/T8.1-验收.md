## 4. 抽查发现

**未发现真实功能缺陷，未发现红线被绕开，未发现回归失败。** 以下五条如实登记，均不构成不通过理由：

1. **「判据与代码注释均按实测改写，不留错误归因」不完全属实（陈述精度，不影响结论）。**
   交付报告与提交说明都写明开工前预判「会跳两次」经实测不成立、注释已按实测改写。`AppLayout.tsx:41-45` 与 `command-palette.spec.ts:65-72` 确已改写，但**同一提交新增/改写的另四处文字仍写着旧归因**：
   `command/index.ts:15`「两处都监听会让一次按键跳两次」、`layout/shortcuts.ts:6-7`「两处都监听会让一次按键跳两页」、`tests/command-ipc.test.ts:850` 用例标题「否则一次按键跳两页」、`tests/ui-components.test.ts:399` 注释同句。
   读到这四处的人会得出与 `AppLayout.tsx` 相反的事实判断（一处说「会跳两次」、一处说「实测不会」）。删除本身正确、删除理由（同一组键位不该有两个实现）也成立，只是**同一提交内两种归因并存**。建议并入文档口径小工单统一为 `AppLayout.tsx` 的表述。

2. **合同 ① 的「注入 `handlers`」在 `App.tsx` 中字面上未发生（口径差异，目的已达成）。**
   `App.tsx:81-88` 只传了 `navigate` / `projects` / `onSelectProject`，`handlers` prop 缺省为空表。交付方以 ③ 的 `registerCommand` 页面自报通道接通两个命令，并在交付报告中说明了结构性原因（对话框状态住在 `Composer` 内部，挂载方拿不到），**未声称传了 handlers**。合同的目的（命令有 handler、可执行）达成且路径更合理；登记只为让合同文字与实现对得上——今后若有「挂载方本就知道怎么做」的命令，`handlers` prop 这条路仍在（`CommandPaletteProvider.tsx:33`）。

3. **单测子项计数：分项之和为 17，总数 +13 无误（口径）。**
