# 监管者职责计划

> 状态：Tony 2026-10-24 要求写计划。未开工，未改版本。总览见 [`改进计划总览-2026-10.md`](./改进计划总览-2026-10.md)。
>
> 和 [子 agent 管控](./子agent管控计划.md)（T11.1）放在一起做：调研小窗本来就是在 T11.1 里交给监管者的。

## 1. 起因

Tony 觉得监管者只是在点名，很鸡肋；它一汇报就把管理者叫醒，也很烦。

《海上生存日记》的团队消息（`.ffpane/threads/index.jsonl`，截至 2026-10-24 共 679 条）：

- 监管者给管理者发了 33 条汇报，大多是「结论：做完；已跑窗口、锁与终端只读核查，通过；监管窗口没跑项目测试。改了：无。」，等于报平安，每次都叫醒管理者。
- 管理者给执行发了 147 条消息，其中不少是机械活：催执行放锁（10-24 09:13「你拿着 heavy 锁 8 分钟了，Unity 却没在运行」）、把监管者报上来的事故处理办法转给执行（10-24 10:42 内存不足那次）。
- 管理者还手动给监管者发了 29 条「名单更新」。
- 执行超出范围时只能自己写请示（`cloth01-请示-范围外文件.md`），没人主动核对。

## 2. 分工原则

| 层 | 谁做 | 做什么 |
|---|---|---|
| 代码 | FF-pane 平台 | 能写死的规则都拦住：锁、权限、子 agent、删图、汇报格式、名单、谁在线 |
| 查「有没有」 | 监管者（便宜模型，思考强度 low） | 对照现成标准核对，规则固定，不判断好坏 |
| 判断「对不对、值不值」 | 管理者；计划评审时临时开的评审窗口 | 理解 Tony 的意思、派活、拍板、评计划和代码 |

监管者拿不准的不自己判断，写进「要决定」交给管理者。

## 3. 监管者新增的活

| 活 | 怎么做 | 可以直接对执行说什么 |
|---|---|---|
| 核对汇报证据 | 读执行交的详细记录和命令输出，确认「已跑 …，通过」真的有对应的输出 | 「证据不全，请补：…」 |
| 核对范围 | 用 `git diff --name-only` 对照执行说明里「只改这些文件或目录」，超出的列出来 | 「这些文件超出范围，先别提交，等管理者定」，同时报管理者 |
| 盯锁 | 拿着 heavy 锁超过 5 分钟，却没有对应进程在跑（如 Unity），提醒放锁 | 「请放锁，要跑时再拿」 |
| 常见事故 | 按固定清单处理：内存不足被杀 → 别重跑、等 Unity 自己退出；429 限流 → 停下等 Tony；网络临时故障 → 平台自己续 | 清单里写好的那几句 |
| 调研小窗 | T11.1：收到调研请求，开只读的调研窗口，结论交回提请求的窗口 | — |
| 问题台账 | T11.4 落地后：把检查者报的问题记进台账，跟踪哪些还没关 | — |

- 「不给执行下命令」放开的只有上表最后一列那几种。派活、改需求、改范围仍然只有管理者能做。
- 清单写进 `supervisor.md`，每条都是「看到什么 → 说什么」，便宜模型照着做就行。
- 执行说明里「只改这些文件或目录」改成固定格式的一节（如 `## 可改范围`，一行一个路径），方便对照；管理者说明书里同步要求。
- 不变：不写代码，不改项目，权限只读，用便宜模型。

## 4. 平台代码接手的

- **名单自动推送。** 监管者名下新开或关掉窗口时，平台通过 `ffpane_wait_events` 推一条「新开 X（角色、执行说明路径）/ 已关闭 Y」，管理者不用再手动发名单。
- **汇报不再随便叫醒管理者：**
  - 监管者平时只用 `ffpane_write_status` 覆盖写近况，不叫醒任何人；
  - 只有三种情况 `ffpane_report` 会叫醒管理者：「要决定」不是「无」；某个执行做完或失败；按清单处理不了的事故；
  - 其他汇报（比如例行核查通过）平台记进管理者的「待处理」（`team-digest.ts` 已有），管理者下次因别的事醒来时一起看到。

## 5. 谁看着谁

不靠两个 AI 互相汇报，由平台每 30 秒检查一次（`handlers.ts` 的 `checkSupervisors`、`checkTeams`）。

| 情况 | 现在已有 | 本计划补的 |
|---|---|---|
| 监管者掉线（5 分钟没在等事件：出错、限流、回合结束） | 通知管理者；它名下的提醒和汇报改交管理者 | — |
| 管理者停了，又没有在线的监管者 | 管理者窗口上显示「团队暂停」，汇报记进待处理 | — |
| 监管者在线，但收到提醒没处理好 | 无：平台看它在线，不会转交 | 提醒交给监管者后，同一个窗口 15 分钟后还是同一种状态（卡住、等批准、空闲没汇报），平台直接报给管理者一次 |
| 管理者在线，但监管者报上去的「要决定」一直没人管 | 无 | 30 分钟没处理，在管理者窗格上标出「有 N 件待你拍板」（复用 1.0.8「待你拍板」） |

## 6. 验收

1. 例行核查通过时，管理者不被叫醒；之后管理者因别的事醒来，能在待处理里看到。
2. 「要决定」不是「无」、执行做完或失败时，管理者被叫醒一次。
3. 执行改了范围外的文件：监管者列出文件，告诉执行先别提交，报管理者。
4. 执行拿着 heavy 锁 5 分钟以上没跑 Unity：监管者提醒放锁，不经管理者。
5. 模拟内存不足、429：监管者按清单直接告诉执行，管理者只在待处理里看到。
6. 新开和关掉执行窗口：监管者自动收到名单变化，管理者没发名单。
7. 让监管者收到提醒后故意不处理：15 分钟后管理者收到平台的直接提醒。
8. 关掉监管者：5 分钟内管理者收到「掉线」，之后提醒照常交给管理者（回归）。
9. 监管者用便宜模型、low 强度，把 1–5 各跑一遍，行为正确。

## 7. 风险

- 便宜模型核对范围时误报：只报不拦，最终由管理者定；误报多了就把核对改成平台代码做（列表对比本来就能写成代码）。
- 放开对执行说话后越权：只放开清单里的几句；`supervisor.md` 写明其余一律报管理者；验收时检查它没派活。
- 汇报攒进待处理后管理者看漏：做完、失败、要拍板这三类照常叫醒，不攒。
