# 1.0.22（T11.0e）管理者未读与界面内存：改动与验收办法

**日期：** 2026-11-06
**状态：** 已提交（2026-11-06，版本 1.0.22），尚未验收。
**计划：** [管理者未读与界面内存修复计划.md](../管理者未读与界面内存修复计划.md)（现场证据、原因都在里面）

## 1. 改动

### 界面内存

- 新模块 `renderer/src/pages/workbench/webgl-pool.ts`（不碰 DOM）和 `terminal-webgl.ts`（真 addon 的装卸）。所有终端的 WebGL 由它统一装卸：图集超过 64MB 把所有终端的 WebGL 一起卸掉重装；合并掉的页、释放后的图集画布当场清成 0×0；卸载时主动释放 WebGL 上下文；终端在 WebGL 装完前就销毁（开发模式 `StrictMode` 每次挂载都会这样）的不再装上去。
- `TerminalView` 改用它，删掉 `tryLoadWebgl`。
- 界面每 5 分钟写一行 `[renderer-mem] jsHeap=…MB terminals=… webgl=… atlas=…MB atlasRecycles=… dom=…`，图集重装时写 `[renderer-mem] webgl atlas recycled at …MB`；主进程（`diagnostics/index.ts` 的 `forwardRendererReports`）收进 `main-日期.log`。
- 日志不再写 `[wb-control] accepted`（每个钩子、每次工具调用一行），只记出错的。

### 批准权限、回答提问后提醒自动恢复

- `idle-deliver.ts` `notePromptReady`：等批准、但只剩按摘要记的或无法配对的未决（按 `tool_use_id` 配对的不动），输出安静 8 秒、屏幕上是空闲输入框时清掉未决、判为空闲，排着的提醒照常投。
- `prompt-ready.ts`：监视器也看等批准的窗口，同样要安静 8 秒。确认框不算输入框。
- 横幅：「正在等待权限确认，暂不发送。确认框关掉、窗口安静几秒后会自动接着发。」

### 用户发话时附一句未读

- `mcp-tools.ts` `peekInboxNotice`、控制通道 `inbox-peek`、`workbench-hook.ts`：用户自己在 Claude / DeepSeek 窗口里发的话，附「[平台] 你的收件箱另有 N 条未读（来自 …）……回应完调用 ffpane_read_inbox 看完再结束这一轮」。不读正文、不标已读；没有未读不附。平台的 `[新消息]` 提醒照旧附正文。

### API 出错暂停时

- `remind`：用户本人的拍板结果照常打进终端，不记进待处理。别人的汇报照旧记进待处理。
- 运行状态加 `apiPaused`；标题栏显示黄色「已暂停：原因，等你发话」。

### 记住 Claude 里换过的对话

- `workbench-hook.ts` 上报 SessionStart、UserPromptSubmit 的 `session_id`；`handlers.ts` 对 Claude / DeepSeek 窗口记下变了的编号（`claudeSessionOf`）、发认领，改模型和重启时续接用它；Grok 的编号核对只对 Grok 窗口。
- `WorkbenchFlushBridge` 收认领写进布局（窗口不显示也记），`TerminalView` 只换自己续接用的编号。

## 2. 已验证

### 图集实测（独立小实验，`test-results/atlas-exp/`，不进 git）

同版本 Electron 44 + xterm 6.0 + addon-webgl 0.19，4 个终端，80ms 一帧仿 Claude 的输出（渐变的「Thinking…」、计数、输入框，夹中文行）。

| 输出 | 渲染 | 时长 | 图集 | 界面进程 | 显卡进程 |
|---|---|---|---|---|---|
| 颜色连续变化 | DOM | 3 分钟 | — | 稳在约 99MB | 约 95MB |
| 颜色连续变化 | WebGL | 3 分钟 | 0 → 41MB | 46 → 179MB | 103 → 629MB |
| 几种颜色 | WebGL | 3 分钟 | 不涨 | 回收后 58MB | 约 110MB |
| 6000 个汉字 × 36 种颜色 × 3 种底色 | WebGL，不修 | 4 分钟 | 0 → 268MB | 42 → 540MB | 1.5–2GB |
| 同上 | WebGL，64MB 重装 | 4 分钟 | 4–64MB 来回，重装 9 次 | 260–420MB | 200–700MB |

最后一组是极端负载，约 40 秒重装一次；平时的输出应该远少于这个。

### 单测和检查

- 新增 `webgl-pool.test.ts`（8 条：装完前销毁不装、没超上限不重装、超上限一起重装并清画布、连着加页只量一次、合并掉的页当场清、最后一个关掉全清、上下文丢了只卸一个、重装途中关掉不留）。
- `workbench-prompt-ready.test.ts`：摘要记的权限闩在屏幕回到空输入框且安静很久时放开并投递；监视器看等批准的窗口要安静够久、确认框不算空闲。原来的「按 id 配对的在等批准时不清」不变。
- `workbench-mcp.test.ts`：未读提示只说条数和来源、不含正文、不标已读，读过之后为空。
- `workbench-hook-digest.test.ts`：普通输入上报后取 `inbox-peek`，没有未读不写 stdout；有未读输出附加上下文。原来的「普通输入不取任何东西」改成这条。
- `workbench-hook-notify.test.ts`：只在 SessionStart、UserPromptSubmit 取 `session_id`，格式不对不要。
- 全仓库单测 2783 条：一起跑时有 8 条超时（`opencode`、`planner-report`、`compact-launch`、`project-config-bind`、`terminal-pty.integration`，都不在本次改动里，耗时都卡在超时上限，机器当时负载高），单独重跑后只剩 `terminal-pty.integration` 的「Git Bash 连续 8 次关窗都不留」仍超时（180 秒，连开 8 次新控制台窗口，清临时目录时 `EPERM`）。这条测的终端圈禁代码本次没动，没有在改动前的代码上重跑对照；其余 2774 条一起跑就通过。typecheck、lint（biome、check-i18n）通过。e2e 这次没跑。

## 3. 验收办法（《海上生存日记》真项目，dev 模式）

先关掉 FF-pane 再双击 `FF-pane.exe`（改的是主进程、界面和钩子程序）。正在跑的 Claude 窗口要重启或续接，钩子程序才换成新的；内存那部分重启 FF-pane 就生效。

| # | 做法 | 应该看到 |
|---|---|---|
| 1 | 正常开着团队用一天 | `main-日期.log` 里 `[memory] … renderer=` 不再一路涨到几 GB（以前每小时约 1GB）；有 `[renderer-mem]` 行，`atlas=` 不超过约 64MB，偶尔有 `webgl atlas recycled` |
| 2 | 切几次标签、最大化再还原几次 | `[renderer-mem]` 里 `webgl=` 不多于正在显示的终端数 |
| 3 | 管理者用提问框问你，你回答；这期间让执行交一条汇报 | 管理者这一轮结束约 8–10 秒后收到「[新消息]」，不用你再发一句；标题栏不会一直显示「等批准」 |
| 4 | 提问框开着不答，期间来汇报 | 提醒不打进提问框；答完、这一轮结束后才送达 |
| 5 | 管理者有 2 条未读时，你在它窗口里随便说一句 | 它先回应你，接着调用 `ffpane_read_inbox` 看那 2 条 |
| 6 | 没有未读时你说一句 | 没有多出的未读提示 |
| 7 | 管理者因 429 或连续 503 暂停时，在「待你拍板」里点一个选项 | 标题栏是黄色「已暂停：…，等你发话」；你的选项马上作为新消息打进管理者窗口，它接着干活；别的窗口的汇报仍只记进待处理 |
| 8 | 在管理者窗口里 `/resume` 到另一段对话，再关掉 FF-pane 重开（或让它改一次模型） | 续接回 `/resume` 之后的那段，不再回到启动时那段；窗口不在当前标签页时也一样 |
| 9 | 在 Claude 窗口里 `/clear` 后重开 | 续接到 `/clear` 之后的新对话 |
