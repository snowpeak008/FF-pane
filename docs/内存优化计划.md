## 1. 现状

2026-10-24 本机实测（dev 模式，3 个 CLI 窗口，完整表见总览 §4.2）：

- **界面进程 1256MB，是单个最大的进程。** 窗口只有 3 个，不正常。切走的标签本来就会卸载 xterm（`live-terminals.ts`），终端回滚用默认值，都不像是原因。
- **Claude 窗口每个约 900MB**（920、884）。照这个数，10 个 Claude 窗口光 CLI 就要约 9GB。Codex 窗口约 260MB。
- dev 专用约 430MB（electron-vite、两个 pnpm），打包版没有。Tony 选择继续用 dev 测试，这部分不动。

已有的：

- 每个窗口的进程数和内存：`terminal/manager.ts` 已经在量，`ffpane_list_windows` 给管理者看。
- 开窗门槛：`workbench/resource-guard.ts`，可用内存低于设置值就拒绝开新窗口（默认 1GB）。
- 续接：Claude `--resume <编号>`；Codex `resume <编号>`，会话被桌面版归档时先 `codex unarchive`（1.0.10）。

jcode 省内存，是因为一个后台进程托管所有会话。Claude Code、Codex 的进程模型我们改不了。我们能改的是：**同时活着的 CLI 进程少一点，界面进程瘦一点。**

## 2. 第一步：剖析（不改功能）

先查清界面进程的 1.25GB，再决定怎么改，不猜。

1. dev 和打包版（`out/`）各开同样的 3 个窗口，记界面进程内存。差值就是 dev 自身的开销。
2. 抓渲染端堆快照（DevTools Memory），按构造函数看大头：xterm 缓冲、WebGL、React 状态里的大数组、画板图片、markdown 渲染。
3. 数 WebGL 上下文：每个终端一份（`TerminalView.tsx` 的 `tryLoadWebgl`）；GPU 进程 192MB 也一起看。
4. 切换标签十次、开关画板十次，看内存回不回落（查泄漏）。
5. 主进程：每个窗口 1MB 输出缓冲（`terminal/types.ts` 的 `DEFAULT_OUTPUT_BUFFER_BYTES`），确认关窗后释放。
6. Claude 窗口：同一窗口开新会话时、聊 2 小时后、压缩后各记一次内存，看是否随会话长度涨。

产出：`docs/验收记录/内存剖析-<日期>.md`，列出前三个大头和各自的改法，再按结论排第 4 步。

## 3. 第二步：空闲窗口休眠（收益最大）

10 个窗口里同时干活的通常只有三四个。空闲的先关掉进程，窗口留着，要用时续接回来。

### 3.1 什么窗口能休眠

全部满足才休眠：

- 状态空闲（不是忙、等批准、出错待处理），且空闲超过设定时间（默认 15 分钟，设置里可改、可关）；
- 收件箱没有未读；
- 没拿着 `ffpane_lock` 的锁；
- 不在在线监管（`ffpane_wait_events` 挂着的不算空闲）；
- 角色是执行、检查、规划、普通。**管理者、监管者不休眠**（他们靠等事件干活）；
- 运行时支持按编号续接：Claude、Codex 支持；Grok 没核实前不休眠；
- 有原生会话编号（没聊过的窗口直接关进程，唤醒时冷启动）。

### 3.2 休眠和唤醒

- 休眠：先确认输入框空（`prompt-ready.ts`），再结束 CLI 进程树（现有 Job 圈禁）。窗口、标题、角色、上级关系、会话编号都留着。窗格显示「休眠中」和一个「唤醒」按钮，终端区显示最后一屏（回放缓冲）。
- 唤醒的时机：
  - 有消息投给它（`send_message`、`report`、`broadcast`、`nudge`、拍板结果）；
  - 用户点「唤醒」，或在窗格里打字；
  - 管理者调 `ffpane_restart_window`。
- 唤醒走现有续接路径。消息等到输入提示出现再投递，并照常核对提交（1.0.9 的机制），保证不丢。
- `ffpane_list_windows` 多一个状态「休眠」；管理者说明加一句：休眠的窗口照常发消息，平台会叫醒它。

### 3.3 代价（写进设置说明）

- 唤醒要几秒（Claude 启动慢于 Codex）。
- 休眠久了提示词缓存过期，唤醒后第一轮多花一些 token。
- 所以默认 15 分钟，不设得更短。

## 4. 第三步：开窗排队

现在内存不够就直接拒绝开窗。改为：

1. 不够时，先挑可休眠的窗口（§3.1）里空闲最久的休眠掉，再量一次；
2. 够了就开，返回里写明「为开这个窗口休眠了 X」；
3. 还不够才拒绝，原因照旧。

界面上每个窗格显示内存（数据已有），超过 1.5GB 标黄，方便 Tony 看出谁最占内存。

## 5. 第四步：界面进程瘦身

按第一步的结论做，候选：

- WebGL 只给看得见的终端；看不见的退回 DOM 渲染或直接卸载。
- 参考 cc-pane：看不见的终端 5 分钟后撤 WebGL，30 分钟后把画面存下来、销毁 xterm，切回来再恢复。
- 画板图片用缩略图，看大图时再载原图。
- 修第一步发现的泄漏。

## 6. 第五步：推荐配置

只读角色（监管者、规划）推荐用 Codex，约是 Claude 的三分之一。监管者已经这样。管理者说明里补一句，不强制。

## 7. 验收

1. 剖析记录写完，前三个大头有数据。
2. 开 10 个窗口（4 个在忙、6 个空闲）：15 分钟后 6 个空闲的进入休眠；记录前后总内存。
3. 给休眠的执行发消息：唤醒后接上原会话（记得之前的内容），消息只投一次、已提交。
4. 拿着锁的、有未读的、在线监管的窗口不休眠。
5. Codex 窗口休眠期间被 Codex 桌面版归档，唤醒仍接回原会话。
6. 可用内存不足时开新窗口：先休眠空闲窗口再开，返回写明休眠了谁。
7. dev 和打包版各过一遍。

## 8. 风险

- 误杀正在干活的窗口：只看平台给的真实状态，不看终端文字；进程结束前再查一次状态。
- 唤醒时续接失败：走 1.0.10 已有的退路（找不到就开新对话，交接里写明），并提示 Tony。
- 休眠后用户以为窗口挂了：窗格上写清「休眠中，收到消息会自动唤醒」。
