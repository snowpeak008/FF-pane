# 1.0.9 重启后收消息、改模型立即生效：改动与验收办法

**日期：** 2026-10-21
**状态：** 已提交（2026-10-22，版本 1.0.9），尚未单独验收。
**真机：** Claude Code 2.1.302、codex-cli 0.162.0（Windows 11 22631）。

## 1. 两个问题的原因

### 1.1 重启过的窗口收不到消息

1. 平台要先收到「回合结束」（Claude 的 Stop，Codex notify 的 agent-turn-complete），才把窗口判为空闲、替它按回车。重启后的窗口还没跑过一轮，没有这个信号，状态一直是「未知」，消息只排队等手动确认。
2. 上一轮被 Esc 打断时，Claude 不触发 Stop，Codex 的 notify 也不报，状态一直是「忙」。
3. `ffpane_send_message` 当场把文字打进去就回「已送达」。核对提交要 4 到 8 秒，没提交时再另发一条「投递失败」。所以会先看到送达，过一会儿才报失败。
4. 「继续」提醒在状态未知时也只排队，不按回车。

### 1.2 改 Codex 推理强度没法立刻生效

1. `ffpane_open_window` 没有模型和强度参数，Codex 开出来读的是用户 `~/.codex/config.toml`（当时是 ultra）。
2. `ffpane_set_model_effort` 对没有对话编号的 Codex 窗口只回「无法续接，待下次重启」。Codex 的编号要等第一轮做完、notify 报上来才有，监管窗口第一轮被打断，所以一直没有编号。
3. 管理者没有重启别的窗口的工具。

### 1.3 dgc04 为什么排队 5 分钟没重启

读本机 `~/.aiworkbench/workbench-layouts.json` 和 dgc04 自己的 Claude 记录（会话 `054ba9d8…`）查到：

- dgc04（`win-bc329399-114`）在第二个标签页「团队：Claude 1」，当时当前标签页是 Tab 1。
- 工作台只渲染当前标签页的窗口。改模型的「续接」由渲染端的窗口组件收到 `workbench:model-effort` 事件后才做；dgc04 的组件没挂载，事件丢了。
- 主进程那边已经把它记成「正在续接」，之后的请求一律回「已排队，空闲时自动续接」，永远等不到结果。
- 旁证：同时改的 imp6、dgb05 在 Tab 1，布局里都记上了新的 `routeModel`；dgc04 没有。dgc04 对话的 `lastActiveAt` 也一直等于开始时间，因为「对话有活动」事件同样只在组件挂载时才处理。

## 2. 改了什么

| 需求 | 做法 | 代码 |
|---|---|---|
| 重启后看到提示符判空闲，清掉旧状态 | 主进程每秒检查状态是未知或忙的窗口，在输出安静后读渲染后的屏幕：空闲输入框（Claude 是两条横线夹着的 `❯`，Codex 是 `›` 加状态行），且没有 `esc to interrupt`、`Working`、`Waiting for startup`、选择器、更新提示，就判空闲。未知状态安静 0.8 秒就判；忙着要安静 8 秒才清（干活时加载动画每秒都刷新）。Codex rollout 的 `turn_aborted` 也当成一轮结束 | `prompt-ready.ts`、`idle-deliver.ts` `notePromptReady`、`codex-rollout-watch.ts` |
| 按回车后核对，没提交重试，再不行直接返回失败 | 所有 CLI 窗口都核对提交（有回合信号的看信号，没有的看终端有没有开工输出），没提交补一次回车。`ffpane_send_message`、`ffpane_report`、`ffpane_nudge` 当场打进去的，等核对完才返回；没提交返回 `not-submitted`，不再先说送达。广播不逐个等 | `idle-deliver.ts` `onSubmit`、`handlers.ts` `awaitSubmit` |
| 状态未知时「继续」也按回车 | `ffpane_nudge` 的条目带 `allowUnknown`，状态未知也自动投递，仍要求输入、输出都静默 | `idle-deliver.ts`、`handlers.ts` |
| 开窗直接带模型和强度 | `ffpane_open_window` 新增 `model`、`reasoningEffort`，写进启动参数（Claude `--model`/`--effort`，Codex `-m`/`-c model_reasoning_effort`），也记在窗口上，以后重启照用。返回实际写进参数的值；没指定就写明 CLI 读用户自己的配置 | `mcp-tools.ts`、`open-child.ts` |
| 改模型由平台自己生效 | 主进程自己重启，不再靠渲染端：没聊过天直接冷重启；聊过、有编号就带新参数续接；Codex 没编号就在窗口里用 `/model` 只改本会话（第二屏按 `s`，不按回车，不写 config.toml）。忙就排队，空闲（含看到提示符）后自动做，做完给要求的管理者发「[模型]」提醒。渲染端收到 `workbench:terminal-replaced` 后改接新终端；窗口不在当前标签页时，下次显示再接上。重启期间界面显示「平台正在重启」，不给重启按钮 | `handlers.ts` `relaunchWindow` / `runModelEffort`、`codex-model-switch.ts`、`model-effort.ts`、`TerminalView.tsx`、`WorkbenchFlushBridge.tsx` |
| 至少能重启自己开的只读窗口 | 新工具 `ffpane_restart_window`：只有管理者能用，只能重启自己开的只读窗口；在等批准时不重启。能续接就续接，`fresh` 或没法续接就开新对话 | `mcp-tools.ts`、`handlers.ts`、`workbench-tools.ts` |
| 结果写明已生效还是仅记录，给出实际值；窗口列表也显示 | `ffpane_set_model_effort` 返回 `status`：已生效 / 仅记录 / 排队中 / 等用户确认；已生效时带 `model`、`reasoningEffort` 和来源（屏幕上显示的 / 启动参数 / CLI 用户配置）。`ffpane_list_windows` 每个 AI 窗口带 `model`、`reasoningEffort`、`modelSource`，有还没生效的设置时带 `pendingModelEffort`。Codex 没带参数时读 `config.toml` 顶层的默认值（只读） | `mcp-tools.ts`、`handlers.ts` `describeModel` |
| 出问题先就地修 | 管理者说明加一条：做偏了发消息纠正，停了叫醒，只读窗口卡死用 `ffpane_restart_window`；纠正两次还错才关掉重开 | `manager.md` |

- 探针过程中一次把 `/model gpt-5.6-sol low` 整句打进 Codex，被当成普通消息发出去开了一轮（临时目录，不到 1 秒就结束了进程）。所以实现里只打 `/model`，不带参数。

请你在真实项目里做：

1. **重启后收消息**：开一个 Codex 执行窗口，点「重新启动」或「续接」，等它出现输入框。让管理者给它发一条消息。期望：`ffpane_send_message` 返回 `delivered`，那个窗口开始干活；`ffpane_list_windows` 里它的状态从「未知」变成「空闲」再变「忙」。
2. **打断后收消息**：让窗口干活时按 Esc 打断，等 10 秒，再让管理者发消息。期望：自动提交，不用点「立即发送」。
3. **结果一次说清**：连着让管理者给几个窗口发消息。期望：每次返回只会是 `delivered`（已提交）、`queued-*`（排队）或 `not-submitted`（打进去了但没提交），不会再先说送达、过一会儿又来一条「投递失败」。
4. **继续**：窗口刚重启、状态未知时让监管者 `ffpane_nudge` 它。期望：「[继续]」被提交。
5. **开窗带强度**：对管理者说「开一个 Codex 监管窗口，模型 gpt-6.1-sol，思考强度 low」。期望：返回 `model`、`reasoningEffort` 是这两个值；Codex 状态行显示 `GPT-6.1-Sol low`；`~/.codex/config.toml` 不变。
6. **改强度立即生效**：
   - 窗口还没聊过天：`ffpane_set_model_effort` 返回 `status: 已生效`、`how: 冷重启`。
   - 聊过、有编号：返回 `已生效`、`带新参数续接原对话`，对话还在。
   - Codex 第一轮被打断、没有编号：返回 `已生效`、`在窗口里用 /model 只改本会话`，窗口里出现「Model changed … for this session only」，`config.toml` 不变。
   - 窗口在忙：返回 `排队中`；忙完后管理者收到「[模型] … 已生效」。
   - 把窗口放到别的标签页再改（dgc04 的情形）：同上，不再卡在排队。
7. **重启只读窗口**：让管理者对自己开的只读监管窗口调用 `ffpane_restart_window`。期望：返回续接或开新对话，以及实际模型和强度；对执行窗口调用被拒绝。

## 5. 补充（2026-10-21 晚）：监管者不作为、消息卡在输入框、越堆越多

用户用 1.0.9 工作区版本跑了一整天（项目2，管理者 Claude、监管 Codex gpt-6.1-sol low、执行和检查 Claude opus），报告三件事。读了当天 90 条消息记录、10 个 Claude 对话记录和监管者的 Codex 记录查清：

**① 堆出来的「[继续]」是管理者发的，不是监管者。** 管理者反复调用 `ffpane_nudge`，返回 `not-submitted`（dgb06、imp7 各连着失败 3 到 6 次）。每次失败的文字都留在执行的输入框里，下一次接在后面，最后一次性提交出去：dgb06 07:31 一条消息里有 5 份「[继续]」，用换行隔开；imp7 06:17 起卡了约 4 小时，直到用户 10:10 手打「继续」。管理者那边同样：05:10 用户发的是「内存够用了，[状态] dgb05 …」，那条「[状态]」一直卡在管理者输入框里。

**原因（真机复现）：** 用真的 Claude Code 2.1.302 加本机假接口（不花额度）复现：平台按「正文、回车」两次写入时，长串中文（这条「[继续]」）被 Claude 当成粘贴，紧跟的回车变成粘贴里的换行；4 秒后单独补的回车也不提交。短中文、长英文、隔 800ms 再回车都能提交。和服务端出错无关，出错只是让管理者频繁叫醒、更容易碰上。

**修复：**

- Claude（含 DeepSeek）窗口的正文用括号粘贴（`ESC[200~ … ESC[201~`）写：真机同一句话、紧跟回车，能提交。
- 回车后核对没提交时，先看屏幕：输入框已经空了就算提交（真机复现过「其实提交了、但核对误判」，不看屏幕就会发两遍）；还留着才按 Ctrl+U 清掉、重打一遍；还不行就再清掉，然后报 `not-submitted`，输入框里不留东西，下一条不会接在后面。Claude、Codex 的 Ctrl+U 都真机核对过。
- 同一句话还排着时不再排第二份（反复叫醒只送一次）。

**② 监管者「在线不作为」是平台没把事件给它。** 监管2 一整天调用 `ffpane_wait_events` 393 次，**每次都是 0 个事件**；消息记录里也没有任何一条抄送给监管者的汇报，连明确用 `supervisorWindowId` 挂上的检查窗口也没有。原因：主进程把界面存回来的布局交给权限登记表同步时，`applyAuthNode` 按字段清单重建窗口，清单里漏了 `watcherWindowId`。界面一存布局（随时都在存），执行就和监管者断开，状态提醒和汇报抄送全落到管理者身上。另外：管理者 05:02 关掉旧监管、开了监管2，早上开的三个执行还挂在已关闭的旧监管上，平台又没有改挂的办法（管理者记的 G6）。

**修复：**

- `applyAuthNode` 保留 `watcherWindowId`；`workbench:save-layout` 只认主进程写下的那份，界面传来的不算（防伪造，也防旧副本冲掉）。
- 管理者新开监管者时，自己名下没有监管者、或监管者已关闭的执行和检查窗口自动改挂过去，开窗结果的 note 里写明。
- 新 e2e `tests/e2e/supervisor-watch.spec.ts`：管理者先开监管者再开执行，界面存过布局后执行汇报 done，核对布局里还挂着、消息记录里有抄送、在线的监管者从等待里拿到了。改之前这条测试失败（布局里 `watcherWindowId` 为空），改之后通过。

**③ 管理者掉线时也堆很多份：** 同 ①，是同一个回车被吃掉的问题，修复相同。

验证：lint、typecheck 通过；单测 167 个文件 2610 条通过；e2e 6 个文件 24 条通过。真机（Claude Code 2.1.302 + 本机假接口）用平台的投递队列连投 3 次「[继续]」：都提交、每次只提交一次；强制退回旧的逐字写法时，也能清掉重打后提交，输入框不留残字。

## 6. 团队暂停与「待处理」（2026-10-22，按用户定的规则）

**错误分两类：**

| 类别 | 哪些 | 怎么办 |
|---|---|---|
| 限流这一类 | 429、额度、计费、认证、模型不存在等 | 开发暂停，等用户的指令。不倒计时、不提醒「可以叫醒」；监管者叫醒它会被拒绝；窗口和锁保留，之后可续接 |
| 网络或服务端临时故障 | 服务端出错（含「Server error mid-response」）、过载（含 Codex「model at capacity」）、说不清的 | 平台 30 秒后自己发固定的「继续」，不用谁思考；连着 3 次还不行就按暂停处理 |

**汇报和状态的去向：** 监管者在线（在等事件）就交给监管者；监管者超过 5 分钟没来等事件算掉线，或因限流暂停，就交给上级，并附一句「监管者不在线，可以叫醒它」；上级也暂停或不在，就不打进任何终端，记进上级的「待处理」。

**监管者掉线：** 平台发现后告诉上级（之前完全发现不了：10-21 监管2 因 Codex 过载掉线 2 小时 11 分钟，没人知道）。掉线前没处理的提醒也交给上级。

**管理者暂停时：** 还有执行或检查在干活，监管者继续在线收汇报；都停了，平台让监管者下线。管理者和监管者都不在线时，管理者窗口盖上半透明提示「团队已暂停，等你叫醒管理者」，可以点「知道了」收起。

**待处理：** `.ffpane/briefs/待处理-<管理者编号>.md`，每个窗口一行、只留最新状态，攒多少事都只有窗口数那么多行。管理者被叫醒、这一轮正常结束后，只收到一句「你暂停期间有 N 个窗口有事，见 …」。它给哪个窗口发过消息、叫醒或关掉它，那一行自动划掉。汇报本身照旧写在 `.ffpane/threads/index.jsonl`，不会丢。

**临时文件：** 每开一个 AI 窗口会在系统临时目录建一个几 KB 的钩子配置目录，应用被强退时留下（10-21 实测两千多个，合计约 5 MB）。启动时清掉超过 1 小时的。

自动验收：`tests/api-error-tracker.test.ts`（两类错误）、`tests/team-digest.test.ts`（待处理）、`tests/workbench-mcp.test.ts`（监管者在线才不叫醒上级、监管者不能叫醒限流窗口）、`tests/e2e/supervisor-watch.spec.ts` 第二条：管理者限流、监管者等一次就不再等，执行汇报 done，核对汇报返回 held、待处理文件里有这一行、管理者终端里没打进汇报、管理者窗口出现暂停提示；模拟用户叫醒管理者后，它只收到一句「[待处理]」。2026-10-22：lint、typecheck 通过，单测 168 个文件 2617 条通过，e2e 7 个文件 26 条通过。

## 7. 风险与没核对的

- 读屏幕判断是按 Claude Code 2.1.302、codex-cli 0.162.0 的画面写的。CLI 改了界面（提示符、状态行、选择器文字）就可能判不出空闲（退回原来的等回合信号，不会更糟），或把干活中看成空闲（消息在它忙时打进去：Claude 会排进输入队列；Codex 在干活时回车会怎样没核对）。
- `/model` 是按键驱动的。每一步先看到预期画面才按，第二屏只按 `s`。Codex 改了选择器，最坏是看不到预期画面、按 Esc 退出，回「仅记录」。
- 续接一轮被打断的对话，「继续」可能让它把半截的命令再跑一次（比如再提交一次 git）。重开新窗口也有同样的问题，只是续接更容易碰到。
