## 3. #4–#11：受阻根因、方案 A 解除、真机证据

验收中曾发现 app 侧装配缺口导致 openai_compatible + codex 无法驱动 DeepSeek；已在本次
**落地方案 A 解除**，并用真机证据验证了核心的"真实 Agent 执行"路径。以下如实记录全过程。

### 3.0 方案 A：装配解除（已实现）✅

- 通用接口 `AdapterTurnContext` 新增逐轮 `configOverrides`（语义由各 Runtime 定义、他者忽略，
  与 `env` 同款"通用通道按 Runtime 解释"）——`packages/adapters/src/adapter.ts`。
- codex 适配器合并"构造级 + 逐轮级"配置覆盖（逐轮 wins）——`packages/adapters/src/codex/adapter.ts`。
- desktop 新增 `resolveRuntimeConfigOverrides`：openai_compatible + codex → 装配 codex 自定义
  `model_provider` 路由（`base_url` + `env_key=OPENAI_API_KEY`，值按 codex `-c` 的 TOML 语义）
  ——`apps/desktop/src/main/session/env.ts`；编排器接线注入 `turnCtx`——`orchestrator.ts`。
- 单测：desktop `resolveRuntimeConfigOverrides`（6 例）+ 编排器透传（1 例）+ codex 合并覆盖（1 例）。

### 3.1 运行时/适配器层——已证明可用 ✅

用本机 codex 直连 DeepSeek（自定义 `model_provider`）真实跑通一轮：

```

  -c model_provider=deepseek \
  -c 'model_providers.deepseek.name="DeepSeek"' \
  -c 'model_providers.deepseek.base_url="https://api.deepseek.com/v1"' \
  -c 'model_providers.deepseek.env_key="OPENAI_API_KEY"' \
  -m deepseek-chat -- "Reply with exactly the word PONG..."
→ {"type":"item.completed","item":{"type":"agent_message","text":"PONG"}}
→ {"type":"turn.completed","usage":{...}}   (exit 0)
```

用**构建后的 codex 适配器**（`@ff-pane/adapters` `createCodexAdapter`）+ 方案 A 解析器同款
overrides + 真实 DeepSeek，在临时 git 仓库跑一轮 Worker 级任务"建 hello.txt"：

```

→ hello.txt 落盘（内容 "hi."）
```

结论：**app 的适配器 → codex → DeepSeek → 真实文件改动**这条链在方案 A 后端到端跑通。

### 3.5 codex 多行提示词 Windows 截断修复（真机走查中发现）

真机走查发现 Phase 2 既有 bug：npm 全局 codex 落地 `codex.cmd` 垫片、经 `cmd.exe` 启动，
**多行位置参数被 cmd.exe 在首个换行处截断** → 模型只收到提示词第一行（`# 角色`）。
影响 Windows 上所有 codex 真机轮次；因单测用假适配器、T4.5 Worker 实证恰用单行提示词而未暴露。
**修复**：codex 提示词改经 **stdin** 下发（首轮 `codex exec` 省略 PROMPT 从 stdin 读；resume
用 `-`），绕开 cmd.exe 参数解析。修复后多行提示词完整送达（§3.4 即修复后实证）。

### 3.2 曾经的 app 装配缺口（方案 A 已修复）

1. **本机 codex 存在 ChatGPT 登录**，会**覆盖** `OPENAI_BASE_URL` 环境变量：仅注入
   `OPENAI_BASE_URL=https://api.deepseek.com` + `OPENAI_API_KEY` 时，codex 仍走 OpenAI 并
   报 `The 'deepseek-chat' model is not supported when using Codex with a ChatGPT account`（400）。
2. **app 的 codex↔openai_compatible 装配只注入 env、不注入 `model_provider` 配置**：
   - `apps/desktop/src/main/session/env.ts` 对 codex 仅注入 `OPENAI_API_KEY` + `OPENAI_BASE_URL`；
   - `apps/desktop/src/main/session/registry.ts` 以 `createCodexAdapter()` 零参构造，未传 `configOverrides`；
   - `orchestrator.ts` 交给适配器的 `AdapterTurnContext` 只含 `cwd/prompt/env/model/resume`，
     无逐轮 `model_provider` 覆盖通道。

   因此 app 无法把一个 openai_compatible Provider 翻译成 codex 所需的 `model_provider` 配置，
   在本机（有 codex ChatGPT 登录）下必然落到 OpenAI 而非 DeepSeek。

3. 其余已注册运行时也不匹配本 key：claude-code 注入 `ANTHROPIC_API_KEY`（无 base_url 覆盖）、
   gemini-cli 注入 `GEMINI_API_KEY`——都不能用 openai_compatible 的 DeepSeek key 驱动。

### 3.3 曾评估的其它路径（存档）

- **方案 B**：改用 env-only 鉴权即足够的环境（无 codex ChatGPT 登录的干净机器 / 其它 env 直连
  运行时）——不需要，方案 A 已在有 ChatGPT 登录的本机把 DeepSeek 跑通。
- **方案 C**：登出本机 codex ChatGPT 依赖裸 `OPENAI_BASE_URL`——脆弱且会动到用户 codex 会话，
  已放弃。
