# 现任管理者与交接计划（T11.22）

> 状态：Tony 2026-11-25 提出。只写计划，未开工，未改版本。和 [想法池](./想法池.md) 里的嵌套管理者无关；本计划不做嵌套，也不做多个管理者同时指挥。

## 1. 起因

开新管理者、关掉旧管理者后，新管理者接不上工作，原因有两处：

1. **没有上下文。** 新开的是全新对话，不记得旧管理者派过什么、定过什么。现有的「[交接]」只在续接同一个窗口时补发（`resume-handoff.ts`），新开的窗口收不到。
2. **看不到旧管理者开的执行者。** `authorize` 的发消息、读输出、关窗口都要求调用者是目标的祖先，`visibleWindowIds` 也只看自己的祖先和后代，新旧管理者是兄弟。执行者汇报默认只送 `parentWindowId`，也只能送上级链（`report`），旧管理者下线后汇报没人接。

## 2. 约定（Tony 2026-11-25）

- 同一时间只有一个「现任管理者」，和 10-24 定的「一个项目只有一个管理者」一致。偶尔会开两三个，但只有一个在处理事情。
- 新开的管理者接任。旧管理者自动下线：失去管理者头衔，保留权限等级。
- 旧管理者成为唯一的管理者时（新的被关掉），可以上线，继续管理。
- 现任管理者对本项目所有执行者都能派活、读输出、收汇报，不管是谁开的。

## 3. 现状（代码）

- 授权按父子链：`packages/core/src/workbench-permission/authorize.ts`，控制类动作要求 `targetWalk.ids.includes(callerId)`。
- 管理权是主进程里的集合 `managerGranted`（`auth-registry.ts`），按窗口记，没有「同一时间只有一个」的限制；设成管理者就授予，改角色才清掉（`set-role.ts` 的 `applyManagerGrant`）。
- 团队范围也走祖先链：`checkTeams`（`handlers.ts`）、`broadcast`、`nudge`、监管者的名单。
- 开窗只看「角色是管理者且已被授予」（`open-child.ts`）。

## 4. 方案：放宽「能管谁」，不改父子关系

不把旧管理者的执行者改挂到新管理者名下：改挂会动 `parentWindowId`、`openedBy` 和权限封顶链，风险大。改成在判断处加一条：

- **管理者组**：同一项目里角色是管理者的窗口（现任加待命）。现任视同每个待命管理者的上级：待命管理者自己和它的整个后代，现任都能发消息、读输出、关窗口、改权限（改权限仍不得超过现任自己的等级）。
- 做成 `core` 里一个纯函数，`authorize`、`visibleWindowIds`、`checkTeams`、`broadcast`、`nudge` 共用，不各写各的。
- **汇报改道**：执行者的汇报目标若是待命管理者，平台改送现任，记录里保留原目标。监管者的汇报同理。
- 待命管理者没有管理权：`isManagerGranted` 为假，不能开窗口，不挂自配置工具；它调用管理者工具会被拒绝，并说明「你已被新管理者接任」。

## 5. 接任与待命

- **谁是现任**：每个项目在 `auth-registry.ts` 里记一个现任管理者编号，只存主进程内存，不落盘。冷启动后沿用 `manager-grant.ts` 的规则：用户续接或新开顶层管理者，视为重新授权，同时成为现任；用户先后续接了几个，最后一个是现任。
- **接任**：用户新开管理者（或把窗口设成管理者）并授予管理权时，项目里已有现任的话，旧现任转待命。转待命只做三件事：撤掉管理权（`clearManagerGrant`）、打上待命标记、保留角色和权限等级。`parentWindowId`、`openedBy`、权限封顶链都不动。
- **待命的样子**：终端不关，对话保留；标题栏显示「待命」；开窗口、自配置、请用户拍板这类管理者工具被拒，回复写明「你已被「X」接任，现在待命」；平台往它的终端发一行通知，说明谁接任、你不再派活。它名下的执行者照常干，汇报改送现任（§4）。
- **复位**：现任被关掉，或用户在界面点「设为现任」，待命的转回现任。只剩一个待命的自动转回；有多个时，选最近活跃的，并在界面提示用户。复位时给它补发交接（§7），因为待命期间的事它不知道。
- **只有一个**：任何时刻最多一个窗口 `isManagerGranted` 为真，这条写成注册表里的不变量，测试直接断言。

## 6. 管理者近况页（方案 A）

新管理者拿不到旧管理者脑子里的东西：已定的决定、没说出口的打算、在等谁。所以现任管理者要把这些落到磁盘。

- **文件**：`.ffpane/briefs/管理者-近况.md`，一页，同名覆盖，不追加；沿用 `ffpane_write_status`（任何角色可写，路径限定在 briefs 内），不新增工具。
- **内容四块**：目标（用户要什么）；已定的决定（一条一行，带原因）；在等什么、在等谁；下一步。
- **不写窗口名单**：谁在干什么由 `ffpane_list_windows` 实时给，不落盘，免得过期。§4 放宽后，现任能看到本项目全部执行者。
- **什么时候写**：做完一个决定、派完一批活、收到要拍板的事之后，覆盖写一次。写进 `manager.md`，一句话；该文件有 2048 字节上限，要先腾字节，再加这句。
- **转待命时再提醒一次**：平台给旧现任发一句「请把近况页更新到最新」，不等它写完，新管理者不被挡住。

## 7. 新管理者自动交接（方案 B）

沿用续接时的「[交接]」那套（`resume-handoff.ts` 的 `resumeHandoffText`），加一种原因 `takeover`，在新现任、以及复位的待命管理者启动后补发一句。

- **内容**：你是「X」，现任管理者；原来的现任是「Y」，已转待命；你不记得之前的事；先读 `.ffpane/briefs/管理者-近况.md` 和待处理页，再看收件箱未读，用 `ffpane_list_windows` 看本项目全部执行者现在的状态；然后接着做，做不了用 `ffpane_report blocked` 说明。
- **时机**：和续接一致，看到输入提示符判空闲后才投递，不带 `allowUnknown`，不往忙着的终端里打字。
- **近况页不在时**：交接句里写明「旧管理者还没写过近况页」。待命的旧管理者终端还开着，现任按 §4 视同它的上级，可以用 `ffpane_send_message` 问它、用 `ffpane_read_output` 读它的输出。

## 8. 改动落点

- `packages/core/src/workbench-permission/`：新增纯函数「管理者组」判断（谁是现任、谁待命、现任对哪些窗口视同上级）；`authorize` 的发消息、读输出、关闭、改权限，以及 `isDescendantOf` 的调用处接入它。不改 `walkAncestors` 的语义。
- `apps/desktop/src/main/workbench/auth-registry.ts`：记现任编号；`grantManager` 时旧现任转待命；`clearManagerGrant`、`remove`、`closeRegistered` 时复位。
- `mcp-tools.ts`：`visibleWindowIds`、`listWindows`、`nudge`、`broadcast`、`closeWindow` 改用管理者组；`report` 的目标若是待命管理者，改送现任并在记录里保留原目标。
- `handlers.ts`：`checkTeams` 按管理者组算团队；`reconcileManagerGrant` 冷启动后按 §5 定现任；接任、复位时补发交接。
- `resume-handoff.ts`：新增原因 `takeover` 和对应文案。
- `manager.md`：加一句写近况页（先腾字节，保持 ≤ 2048）。
- 渲染层：标题栏「待命」标记，窗口菜单「设为现任」。只加标记和菜单项，不弹面板、不抢焦点、不切页面。

## 9. 验收

1. 开管理者 A，派两个执行；再开管理者 B：A 转待命，B 的 `ffpane_list_windows` 看得到 A 名下的两个执行。
2. B 给 A 的执行发消息、读输出、关窗口都成功；改权限不能超过 B 自己的等级。
3. A 的执行交 done 或 blocked：汇报送到 B，记录里保留原目标；A 不被叫醒。
4. A 调用开窗口：被拒，回复写明已被 B 接任。
5. 任何时刻 `isManagerGranted` 为真的窗口至多一个（注册表测试直接断言）。
6. 关掉 B：A 自动复位为现任，并收到交接；有多个待命时选最近活跃的并提示用户。
7. B 上任后收到交接：指向近况页、待处理页和未读；近况页不存在时，交接句里写明。
8. 重启软件：用户续接哪个顶层管理者，哪个是现任；其余不自动授权。
9. 回归：单个管理者的团队行为不变（`checkTeams`、监管者名单、汇报叫醒规则）。

## 10. 风险

- 放宽授权会扩大管理者的范围：只对「管理者组」放宽，且只在同一项目内；监管者、执行者、检查的授权规则不变。
- 汇报改道后，待命管理者名下监管者的叫醒链会变：监管者挂的管理者要跟着改挂现任，单独测。
- 近况页靠管理者自觉写，可能过期：交接句里写明以 `ffpane_list_windows` 的实时状态为准，近况页只记决定和打算。
- 两个管理者同时在忙时接任：旧现任正在一轮中途，转待命只撤管理权，不打断它这一轮，它下一次调用管理者工具才被拒。

## 11. Tony 的决定（2026-11-25）

1. **待命管理者一直占着终端。** 软件关掉再打开后，仍按接任办法处理：用户续接哪个顶层管理者，哪个就是现任，之前的现任转待命；用户先后续接了几个，最后一个是现任。重启后不自动授权、不自动上线（沿用 §5、§9 第 8 条）。
2. **现任关掉后有多个待命的，按最近活跃排序，选最近的一个复位。** 不再让用户逐个点选；界面仍提示一次谁复位了。
3. **现任能关待命管理者的窗口**，和关别的后代一样。
4. **同意只做「一个现任、其余待命」，不做多个管理者同时指挥。** 这条保留。例外只有一种：讨论开发计划时，要不同模型的窗口（如 Claude 和 Codex）一起讨论才作数。这些是只读的评审窗口，不是管理者，不指挥执行，和 10-24 定的评审规则一致（[计划评审计划](./计划评审计划.md)）。

## 13. 派活写不写说明（Tony 2026-11-26 提，说明书已改，下次打包带上）

**起因：** 管理者图省事，常把内容直接贴给执行者，不写 brief。担心这样更费上下文。

**量过的现场数据**（《海上生存》，`.ffpane/threads/index.jsonl` 17340 条，至 2026-11-26）：

| 项 | 数 |
|---|---|
| 管理者→执行类消息 | 3686 条 |
| 其中直接贴内容 | 3520 条，平均 230 字 |
| 其中带 brief 路径 | 166 条，平均正文 252 字 |
| 直接贴且超过 300 字 | 794 条，合计约 32.7 万字 |
| briefs 下的执行说明 | 2196 份，平均 5404 字节 |
| briefs 下的记录 | 1225 份，平均 12567 字节 |

**结论：分两种情况，不能一刀切。**

- **一次性短指令直接说更省。** 写成 brief，管理者要多花一次写文件，执行者还要多花一次读文件，比直接贴的 230–400 字更贵。794 条长贴大多是这种：纠正、补充、催办。
- **要复用的长说明写 brief 更省。** 同一份内容被第二个窗口、换模型、后续修正或验收再提到时，贴一遍就 230 字起，贴五次就超过写一次文件；写成 brief 后每次只要约 60 字路径。
- **真正的大头在执行者读多少。** 一份说明 5.4KB、一份记录 12.5KB，比一堆贴内容贵得多。要盯的是「让执行者读了什么」，不是「管理者贴了多少」。

**改法（已写进 `manager.md` 第 2 条，2044 字节，测试通过）：**

> 派活分两种：要复用、带约束、会再被提到的，用 `ffpane_write_brief` 写成说明，之后只传路径；一次性的补充、纠正、催办直接说，别为它建文件。

为塞进 2048 字节上限，同时压了几处旧句子（不提原意）。

**没做的：** 没做成硬性拦截。`ffpane_send_message` 不检查有没有 brief，因为多数短消息本来就该直接发。要拦的话只能拦「同一段长文本反复发」，先观察，按需再做。
