## 2. 抽查发现

**未发现功能缺陷，未发现红线被绕开。** 以下如实登记：

1. **（正面观察，不影响结论）幂等注销的断言比声称更强。** `unregisterActiveTurn` 对不存在的 turnId 返回原表**同一引用**（`active-turns.ts:68-70`），单测以 `toBe` 断言引用相等（`parallel.test.ts:181`）——既证幂等又证零副本开销，是「值相等」断言的加强形态。
2. **（T8.3b 提示，不影响结论）注销点在 drain 的 `.finally()`，退出路径依赖适配器 cancel 后事件流终结。** 若某适配器 cancel 后事件流悬挂，parallelTable 在进程存活期间不注销——当前唯一后果是 `sessions:active-turns` 快照多一条已死的轮（进程退出即消散，无跨启动脏表；`quit.ts` 3s 预算兜底退出）。T8.3b 把互斥裁决接入 start 受理后，这条「僵尸记录」会**挡住后续相交任务的派发**（拒绝原因指向一个实际已死的轮）——届时建议在 `prepareForQuit` 的 settleInterrupted 后或 cancel 超时分支补一次显式注销，或给记录加存活校验。本单（无裁决接入）不构成缺陷。
3. **（口径核实，不影响结论）「登记在 spawn 之后」但同一同步段内。** 工单问「注册在 spawn 前还是后」：`adapter.startTurn`（`orchestrator.ts:750`）先于 `registerActiveTurn`（`:779`），但两者之间无 await，Node 单线程下不存在「已 spawn 未登记」的可观察窗口；`startTurn` 同步抛错时进 catch 拒绝受理、三表均未写入。与之相对，磁盘侧 inflight 标记刻意在 spawn **之前**落盘（`:723-724` 注释）——内存表无崩溃恢复义务，磁盘标记有，两个顺序各自正确。
4. **（组合行为评估，见 §1-B 专段）两个 Planner 轮、Planner+Worker 轮并行在互斥层面均被允许**，与 T8.3b 合同「相交即拒绝」只约束写-写冲突的预期一致。渲染层今日的单活跃轮模型会忽略非当前轮事件（交付报告第 4 项已清点、归 T8.3b 呈现层），互斥放行 ≠ 呈现就绪，边界划分与工单拆分一致。
5. **（正面观察）审查轮信封刻意不走 `assembleRunEnvelope`**（`orchestrator.ts:576-585` 注释）：避免「靠交集恰好救回来」的可读性陷阱，直接用角色默认 ∩ 预设，「审查者不可写」当场可见——并行表登记到的审查轮 writePaths 因此恒空，与 B 项语义自洽。
6. **（轻微口径，不影响结论）交付报告称在飞表键 = turnId「per-项目」**（进度文档 §0 第 2 项「per-项目，键 = turnId」、`active-turns.ts:24` 注释同文），实际编排器持**单一全局表** + `turnProjects` 旁表过滤实现按项目视图（`orchestrator.ts:1273-1278`）。语义等价（turnId 全局唯一，过滤后快照与 per-项目表不可区分），且 core 层不感知项目概念本就合理；如实登记字面与实现的差异。
7. **（顺带核对）前一提交 `ac3a6e2` 的 fold 守卫补测存在**：`apps/desktop/tests/session-replay-view.test.ts:277-285`「foldEndedTurn 直调：同 turnId 已有 assistant 条目时第二次固化不追加」，直调两次断言 `twice).toEqual(once)`，与 T8.2b-b 验收 §7 裁定 ① 的落档一致。
