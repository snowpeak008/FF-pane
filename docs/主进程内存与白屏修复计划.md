# 主进程内存与白屏修复计划（T11.0d）

> 状态：Tony 2026-10-27 报问题，同日说开工。已提交（1.0.14），待验收，见 [验收办法](./验收记录/1.0.14-主进程内存与白屏-验收办法.md)。实现时和计划不同的：缩略图缓存放 `~/.aiworkbench/cache/canvas-thumbs/`，不放项目里；缩略图只做 256 一档（1024 留给 T11.0c）；终端输出背压没做；现有 8 份 dump 还没配符号看。另外顺手修了终端输出缓冲占住 Node 8KB 池的问题（§3 第 6 条）。改前改后实测见验收办法 §1：打开同一份画板，主进程 3150MB → 240MB，界面 6701MB（卡死）→ 747MB。
>
> 和 [画板无限画布与待检查](./画板无限画布与待检查计划.md)（T11.0c）有重叠：画板加载的那一半是本计划的主因，建议把 T11.0c 拆成两步，先做加载（§4.1）。[内存优化](./内存优化计划.md)（T11.3，暂缓）管的是「少开 CLI 进程、界面瘦身」，本计划只管崩溃和内存暴涨。

## 1. 起因

Tony 2026-10-27 说了两种情况：

1. 卡顿时 FF-pane 同时开着十几个窗口（Claude、Codex 都有），还在大量看图。
2. 长时间运行后疑似内存泄漏。再打开 FF-pane 时已经崩了：整个界面白屏，点不动，只能关掉。

Tony 在任务管理器里看到 Electron 占了 4GB，这还不算 CLI 自己占的。因此想换技术底层，但又怕换了要大量阉割功能。

## 2. 现场证据（2026-10-27 读，只读，没关任何进程）

### 2.1 Windows 的崩溃记录

Windows 应用程序日志（事件 1000）和 `%LOCALAPPDATA%\CrashDumps\electron.exe.*.dmp`（只留最近 8 份）：

| 崩溃时间 | 这次运行从何时开始 | 崩溃时 | 运行期间的峰值 |
|---|---|---|---|
| 10-25 00:05–00:07 | — | 连崩 6 次（只有事件记录，dump 已被覆盖） | — |
| 10-25 11:15 | — | 一次访问冲突 `0xc0000005`（偏移不同） | — |
| 10-25 11:16–11:22 | 每次都是刚启动 | 连崩 5 次，每次工作集只有约 210MB | 约 240MB |
| 10-26 07:52 | 10-25 11:31（约 20 小时） | 工作集 523MB，提交 1071MB | **工作集 3196MB，提交 5238MB** |
| 10-27 07:57 | 10-26 07:52（约 24 小时） | 工作集 377MB，提交 595MB | **工作集 3882MB，提交 5832MB** |
| 10-27 11:39 | 10-27 07:57（约 3.7 小时） | 工作集 310MB，提交 337MB | **工作集 4685MB，提交 6235MB** |

- 崩的都是 **FF-pane 的主进程**：这些进程都加载了 `conpty.node`，而终端（node-pty）只在主进程里跑。
- 除 11:15 那次外，异常码都是 `0xc0000409`，参数 7（`FAST_FAIL_FATAL_APP_EXIT`，进程自己 abort），偏移都是 `0x3043d85`：每次都是同一个地方叫停的。
- 每次都是崩了 Tony 就重开，所以一次运行的开始时间就是上一次的崩溃时间。

### 2.2 当时还在的进程

- **Codex 桌面版**（`ChatGPT.exe`，也是 Electron）：20 个进程，私有内存约 11.4GB，CPU 累计约 17000 秒。任务管理器里看到的「Electron 很大、CPU 很高」，有一部分可能是它。
- **FF-pane 残留两份**：10-24 16:42 和 10-25 00:45 起的 `pnpm dev`。每份都只剩主进程、GPU 进程和网络进程，界面进程和窗口都没了，各占约 410MB，CPU 不再走。

### 2.3 读出来的结论

1. **内存不是慢慢漏到爆的，是一阵一阵冲高的。** 三次长时间运行的峰值是 3.2–4.7GB，可崩溃那一刻只有 300–500MB。高峰最可能来自打开画板（§3 第 1 条）。10-27 上午那次只进了 90 张图，照样冲到 4.7GB：画板一打开就把整个画板的原图全读一遍，和这次加了几张图无关。而且 AI 每次出图都会自动打开画板，三天 1336 次，Tony 不点也会冲高。
2. **崩溃本身还没找到原因。** 崩的那一刻内存不高；10-25 11:16–11:22 刚启动、只有 210MB 时也在同一个地方崩了 5 次。所以除了内存冲高，**还有一个和内存无关的崩溃**，要先给 dump 配上 Electron 的符号才看得出是谁叫停的（§4.0）。
3. **白屏**更像是界面进程先撑不住了：画板的缩略图在界面里也是整张原图的 base64，几个 GB 的字符串加解码后的位图。界面进程崩掉时没有留下 dump。FF-pane 没有处理「界面进程没了」这件事（主进程里没有 `render-process-gone` 的处理），所以只剩一个白窗口；关窗以后主进程有时也退不干净，就是 §2.2 那两份残留。

## 4. 怎么改

### 4.0 先能看见（不改功能）

现在 FF-pane 不写日志，dev 模式下主进程的输出也看不到，崩了只剩 Windows 的记录。

- **日志文件**：主进程的 `console` 同时写进 `~/.aiworkbench/logs/main-YYYY-MM-DD.log`，按天分文件，保留 7 天。
- **内存记录**：每 5 分钟记一行：主进程 `rss`、`heapUsed`、`external`、`arrayBuffers`，界面进程和 GPU 进程的内存（`app.getAppMetrics()`），开着几个窗口、各窗口累计输出多少字节、画板开没开。
- **快爆前抓快照**：主进程 `heapUsed` 第一次超过 1.5GB 时自动写一份堆快照到日志目录（一次运行只写一次，写的时候会卡几秒）。
- **崩溃记录**：`render-process-gone`、`child-process-gone`、`unresponsive` 都写进日志（原因、退出码、当时的内存）。开 Electron 自带的 `crashReporter`（只存本机、不上传），以后崩了有带进程类型的 dump。
- **配符号看现有的 8 份 dump**：用 Electron 44.0.0 的符号（symbols.electronjs.org）看出 `0x3043d85` 是谁叫停的，结论写进验收记录。只读本机文件。

### 4.1 画板读图（主因）

和 T11.0c 的 §4.4 是同一件事。建议**拆成两步**，先做这一步，不等无限画布：

- 缩略图（长边 256 / 1024，Electron 自带 `nativeImage`，缓存在 `.ffpane/canvas/.thumbs/`）；
- `ffpane-canvas://` 协议直接给 `<img>`，不再走 base64，删掉 `workbench:read-canvas-image`；
- 只加载看得见的（现在的界面先用懒加载，无限画布做好后按视口加载）；同时最多读 4 张；
- 出图、交图不再自动打开画板，只更新按钮上的数字；
- `placeImageOnBoard` 查重；现有重复行开发时先备份 `board.json` 再合并，动之前问 Tony。

### 4.2 减少反复的大块读写

- 画板写入：去掉每次写都列目录（清理临时文件改成启动时做一次，加每 10 分钟一次）；同一文件的多次监听事件合并成一次（300ms）。
- 标注图的宽高只读 PNG / JPEG 的文件头，不读整张。
- 提示符检测：只取缓冲的最后 256KB，不把整份 1MB 转成字符串；输出没变的终端直接跳过（现在已经有一部分）。
- 团队消息索引：按文件大小和修改时间缓存，只读新追加的部分。
- 终端输出推送：界面没确认收到之前，同一个终端的输出合并成一批，不一直往外推。

### 4.3 兜底：出事了不白屏、不残留

- **界面进程没了**：主进程记日志，自动重新加载界面。终端在主进程里，不受影响，加载完照常接上。一分钟内连着没了 3 次就不再重载，显示「界面反复崩溃，请重启 FF-pane」和日志位置。
- **界面没响应**（`unresponsive`）：记日志；超过 30 秒弹系统对话框，可以选「重新加载界面」或「等待」。
- **内存警戒**：主进程或界面进程超过 2.5GB 时，工作台右上角常驻一条提示「内存偏高，建议重启 FF-pane」，不弹窗、不抢焦点。重启后窗口照常续接（1.0.10 已有）。
- **只开一份**：加 `requestSingleInstanceLock`，再双击启动时只把已有的窗口切到前面。开工时先请 Tony 关掉现在残留的两份，或者经 Tony 同意后由我来关。
- **关窗退不干净**：关窗流程超过 5 秒还没退出就强制退出（`app.exit`），并记日志。

### 4.4 代码怎么组织

- `main/diagnostics/`：日志文件、内存记录、快照、崩溃记录，一个目录，不依赖别的业务模块。
- 判断「该不该重载、该不该提示」的规则写成纯函数（输入：事件和时间，输出：动作），单测直接测。
- 不加新库。

## 5. 验收

1. 把《海上生存日记》的画板复制到 `test-results/` 下的测试项目（不碰原项目），打开画板、来回拖一分钟：主进程内存涨幅不超过 300MB，界面进程不超过 800MB。改之前同样操作量一次，两次的数字都写进验收记录。
2. 测试项目里开 10 个窗口（脚本持续往终端写输出），连跑 8 小时：主进程内存曲线基本平稳，日志里每 5 分钟一行。
3. 手动结束界面进程：日志里有一行，界面自动重新加载，终端内容还在。连续结束 3 次：显示提示，不再重载。
4. 已经开着 FF-pane 时再双击启动：只把原窗口切到前面，不多出一份进程。
5. 关窗后 5 秒内所有 FF-pane 进程退出。
6. 现有 8 份 dump 的结论写进验收记录：叫停的是谁，是否已经由本计划修掉；没修掉的另列。
7. dev 模式和打包版都过一遍。

## 6. 关于换技术底层（Tony 2026-10-27 问）

建议先不换。理由：

- 这次的峰值主要是**我们自己的代码**一次性把 1.6GB 的图读成好几份造成的。换成 Tauri 或者别的框架，同样的写法照样会爆。
- Tauri 在 Windows 上用的 WebView2 也是 Chromium，终端界面的内存差不多一样，大概只省主进程的 200–400MB；代价是主进程全部用 Rust 重写（终端、MCP、团队消息、生图都在主进程里）。
- 原生界面能把界面降到几百 MB，但等于全部重写，几个月起步，现有功能要重新做一遍。
- 每个 Claude 窗口约 900MB 是 Claude Code 自己的进程，换什么底层都省不掉，只能少开或空闲休眠（T11.3）。

做完本计划后按 §4.0 的日志再看一周：如果 FF-pane 自己（主进程加界面进程）平时还常超过 1.5GB，再专门评估换底层。
