# 1. 计划总则

## 1.1 执行纪律

```text
1. 每个任务是一份合同：目标、产出、范围、验收标准、验证方式在本计划中写死。
2. 任务完成的定义（DoD）：
   代码完成 + 单测通过 + lint 通过 + 验收标准逐条核对 + 一次符合规范的提交。
3. 提交节奏：每任务至少一次提交，提交信息引用任务 ID
   （示例：feat(core): T1.4 Plan/Task/Run 状态机）。
4. 每个 Phase 结束：跑全量测试 → 向用户汇报 → 打版本 tag → 进入下一 Phase。
5. 任何任务不得修改自己范围之外的文件；发现必须跨范围时，先报告。
```

## 1.2 主管理员 / 子 Agent 分工

```text
- 主管理员（本 Agent）：拆解与下发任务合同、审查产出、集成、提交、
  打 tag、向用户汇报。集成类任务亲自执行，不派发。
- 子 Agent：执行具体编码，每个子 Agent 只负责一个任务合同的范围。
- 子 Agent 模型：claude-opus-5-thinking-high（用户 2026-08-29 晚指定，统一使用）。
  沿革：初始 inherit（Fable 5）→ 降本提议 Sonnet 5 → 用户最终定为 Opus 5。
  已派出的工单不变，自 W1.3b 起生效；仅限 Claude 家族模型。
- 标注"并行"的任务组派发给多个子 Agent 同时执行，
  前提：文件范围互不重叠（已在任务范围中保证）。
- 派发时向子 Agent 提供完整任务合同（子 Agent 看不到对话历史）。
- 所有子 Agent 产出由主管理员实际审查：读代码、跑测试、跑 lint，
  通过后才整合提交。"子 Agent 说完成"不等于完成。
```

## 1.3 任务规模标记

```text
S = 小（单文件/单模块，直接做）
M = 中（一个完整功能模块）
L = 大（跨模块或含真机联调）
```

## 1.4 质量标准：非 MVP 红线

本项目不做"最小可用版本"。每个任务交付的是完成品，不是骨架：

```text
1. 禁止占位实现：不允许 TODO 空函数、假数据、stub 页面进入主干；
   任务要么按验收标准完整交付，要么不合并。
2. 严格 TypeScript：strict 模式，禁止随意 any；类型即文档。
3. 边界处理完整：系统边界（用户输入、CLI 输出、API 响应、文件系统）
   的失败路径必须处理，并给出用户可理解的界面反馈。
4. 测试是交付的一部分：core / storage / rag / adapters 的逻辑必须带单测；
   "能跑"不等于"完成"。
5. 性能有底线：万级记忆条目、十万级知识库块、百条消息的会话
   不允许可感知卡顿（虚拟列表、索引查询、流式渲染是标配）。
```

"分阶段交付"仍然成立（如打包先出 Windows 版），但每个阶段交付出去的部分必须是完成品质量。

## 1.5 界面交互质量要求

在"信息密度优先、无装饰"的前提下，交互质量按以下标准执行：

```text
1. 设计系统先行：T3.1 扩充为"设计系统 + UI 骨架"——色板（暗/亮双主题）、
   间距与字号阶梯、组件规范、交互规范先于页面开发定稿。
2. 三态齐全：每个数据视图必须处理 加载中（骨架屏）/ 空 / 错误 三态；
   空态用一句说明 + 下一步动作按钮，不用插画。
3. 即时反馈：所有操作 100ms 内有响应表现；长操作显示进度且可取消；
   Agent 输出流式渲染。
4. 键盘可达：核心流程（切项目、切会话、派发任务、审核记忆）有快捷键；
   提供全局命令面板（Ctrl+K）。
5. 危险操作二次确认；普通操作优先"可撤销"而不是弹窗拦截。
6. 深浅主题跟随系统并可手动切换（实用功能，不属于装饰）。
```

## 1.6 两层任务结构：T 任务 与 W 工单（v1.2 新增）

T 任务直接派发对子 Agent 而言粒度过大。自 Phase 1 起采用两层结构：

```text
计划层：T 任务 = 验收与提交单元
  验收标准、版本关口、提交节奏均以 T 为单位，保持不变。

工单层：W 工单 = 派发单元
  每个 T 拆为 1~5 个 W（编号 W<T号><字母>，如 W1.5a），规则：
  1. 单一职责：一个 W 只交付一个模块或一组同类文件；
  2. 文件范围显式声明，且与同批次并行的其他 W 不重叠；
  3. 每个 W 独立可验证（自带单测或可运行的验证脚本）；
  4. W 完成后不直接提交：同一 T 的全部 W 由主管理员集成、
     跑 T 级验收，通过后一次提交——防止"碎片各自合格、
     拼起来接口对不上"的集成漂移；
  5. 接口先行：T 内被多个 W 依赖的接口/类型，放在首个（串行的）
     基础工单中定稿，后续 W 只实现不改接口。

拆分时机：Phase 1~3 的工单拆分表已在 §16 定稿；
Phase 4 起，每个 Phase 开工前必须先把该 Phase 的工单拆分表
补入本计划（此为 Phase 开工的前置条件，不允许边做边拆）。
集成性质的 T（如 Phase 4 的十步流程串联）可以不拆，
由主管理员亲自执行，在 §16 中标注"不拆分"。
```
