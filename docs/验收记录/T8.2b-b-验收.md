## 2. E2E 断言强度评估（`tests/e2e/session-replay.spec.ts`，3 条）

路径选择核实：预写磁盘现场（`.workbench/sessions.json` + `sessions/<id>/transcript.jsonl`，两完整轮 + 1 坏行 + partial/interrupted 轮）→ 应用真实读回，链路 renderer effect → IPC → 主进程启动修正 + storage 读盘全真实，与 `handoff.spec.ts` 的 seed 款式一致；且预写发生在**应用启动后、项目登记前**（`beforeAll:98-117`），项目经 `projects:create` 登记 + reload 后进会话页——确实检验了「关掉再打开」的磁盘契约（回放不依赖任何内存态）。

| # | 用例 | 断言强度 | 评估 |
|---|---|---|---|
| ① | 自动回放：4 条消息可见 + 横幅 `Resumed last session · Context rebuild` 可见 + `New session` 按钮 + 恢复列表 `Current session` + 坏行提示 `/1 unreadable line/` | **强**。每条断言都会在「没回放」时失败：4 条消息文本是预写的具体句子；横幅文案含预判种类（无 native 绑定 → Context rebuild，若预判恒 native 此断言即红）；`Current session` 证明 `activeSessionId` 确实落到了预写会话；坏行提示带具体数字 1 | ✅ |
| ② | 中断标注 `toHaveCount(1)` + 可见 | **强**。恰一条：partial 与 turn_end{interrupted} 同轮双来源若产出双份即红（count=2）；完全不标注也红（count=0）。对变与不变都不成立的弱断言形态在此不存在 | ✅ |
| ③ | 点 New session：横幅与消息 `toBeHidden` + 空态可见；离开（/projects）再回（/session）：空态仍在 + 横幅仍隐 | **中强**。清空断言强（具体文本从可见变隐藏）；「不被拉回」依赖 `toBeHidden` 的自动重试窗口（Playwright 默认 5s）——若自动续接是异步慢触发（>5s）理论上可漏判，但本链路触发在 effect 同步判定层（`autoResumeDoneRoot` 命中即早退，无 IPC 发出），漏判窗口实际不存在。弱于「断言 IPC 未发出」但强于 T8.1 §4-4 那种「对变与不变都成立」的形态 | ✅ |

**T8.1 曾发现的弱断言形态（断言对变与不变都成立）本 spec 未出现。** 一处非缺陷观察：三条用例共享一次 `beforeAll` 启动且串行依赖（③ 点掉新建会话后 ①② 不可重跑），是仓内既有款式（command-palette.spec 同款），登记不阻塞。

## 3. 抽查发现

**未发现功能缺陷，未发现红线被绕开。** 以下如实登记：

1. **（测试覆盖缺口，不影响结论）store 双保险去重的第一道守卫（`foldEndedTurn:218-220`）是纯防御码且无独立单测钉住。** 读码确认正常路径不可达：`end` 事件固化后 `streamingTurn` 置 null，重复 `end` 被 `ingestSessionEvent:317` 的归属判定（`event.turnId !== active`）挡掉；`loadReplay` 在飞时不写历史。探针③（删掉该守卫）证实 desktop 全部 497 单测仍绿——单测标题「同 turnId 不双份」实际经由上游归属判定成立，守卫本身没有能红的用例。防御码保留是对的（防未来事件重放/顺序变化），但「fold 去重」的声称严格说测的是链路而非该行。第二道守卫（页面合流去重，`SessionPage.tsx:144-146`）同为防御性，无单测直测（页面层无渲染测试，仓内款式如此）。建议归测试加固小工单。
2. **（口径，不影响结论）Worker / 审查轮用户输入的「当场 vs 回放」不对称未在交付报告说全。** 渲染层 `startLocalTurn` 刻意不追加 Worker / 审查轮的输入（`session-run.ts:43-46`，理由：任务合同任务页可见，不重复）；但主进程 transcript 对五类轮全记 `user_message`（a 单合同 ③ 与 a 单验收 §1-B）。后果：Worker 轮进行中会话页只有 assistant 流式输出无用户侧条目，重启回放后同一轮却多出「任务目标一句」的用户消息——同一轮在两种呈现下消息数不同。行为皆有依据（两边合同各自如此写），非缺陷；但口径差异本身在交付报告只说了前半（为何不进），未说明「回放时会出现」的后半。建议在进度文档或下单补一句。
3. **（边界，不影响结论）切项目时若有在飞轮，上一项目的历史消息残留在消息区。** `SessionPage.tsx:93-95` 的在飞早退发生在 `:98` 清残留之前——在飞轮跨项目存活（store 是全局单例、事件桥不因切项目断开），此时清掉会话态反而会丢正在输出的轮，取舍正确；但交付报告「切项目时先清上一项目的会话态再决定回放什么」的陈述隐含了「总会清」，实际带前置条件（无在飞轮才清）。实害有限（在飞轮结束后 effect 因 `autoResumeDoneRoot !== 新项目` 再次触发即清），登记备查。
4. **（正面观察）fold-on-end 的「不闪烁」声称比注释更强。** 固化与 `streamingTurn: null` 在同一个 zustand `set()` 内原子完成，React 单次渲染内历史条目以同一 key（`${turnId}:assistant`）接管，中间不存在「两份都在」或「都不在」的帧。
