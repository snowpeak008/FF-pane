# FF-pane 技术选型

**文档版本：** v1.0
**配套文档：** 项目设计计划-v1.0.md（产品设计）
**原则：** 全部选型服务于"本地优先、单人可维护、简单实用"。依赖版本以工程初始化当日各库最新稳定版为准，锁定在 lockfile 中，本文档不写死版本号。

---

# 1. 选型结论一览

| 层 | 选型 | 一句话理由 |
|---|---|---|
| 桌面框架 | Electron | 产品核心是管理 CLI 子进程 + 数据管道，Node 生态最强处 |
| 语言 | TypeScript（全栈单语言） | 主进程、渲染层、适配器、RAG 管道共享类型定义 |
| 前端 | React + Vite + Tailwind CSS + shadcn/ui | 成熟、信息密度友好、无多余视觉包袱 |
| 状态管理 | Zustand | 够用且简单 |
| i18n | i18next + react-i18next | key-based JSON 语言包，社区可贡献 |
| 数据真实源 | Markdown / 导入原文件（见设计文档第 10 章） | 卸载软件后数据仍完全可用 |
| 索引 | better-sqlite3：FTS5 全文 + sqlite-vec 向量 | 单文件、内嵌、可随时重建 |
| Agent 接入 | Node child_process + JSONL 流式解析 | 见第 4 章 |
| 密钥 | Electron safeStorage（OS 级加密） | Windows DPAPI / macOS Keychain / Linux libsecret |
| 文档解析 | pdfjs-dist（PDF）、mammoth（docx）、自研分块 | 见第 8 章 |
| 嵌入模型 | Provider 配置的 /embeddings 端点 或 本地 Ollama | 不绑定任何嵌入服务商 |
| 打包分发 | electron-builder + GitHub Releases | 标准路径 |
| 质量工具 | Vitest（单测）、Biome（lint + format）、Playwright（后期 E2E） | 工具链最少化 |

# 2. 桌面框架：为什么是 Electron 而不是 Tauri

| 维度 | Electron | Tauri 2 |
|---|---|---|
| 核心逻辑语言 | TypeScript（与前端同语言） | Rust（或经 sidecar 绕行） |
| 子进程与流处理 | Node 原生强项，spawn + stream 生态成熟 | tokio 可做，但适配器开发成本明显更高 |
| SQLite / RAG 生态 | better-sqlite3、sqlite-vec、pdfjs、mammoth 均为 npm 原生 | 需 Rust 侧桥接或 sidecar |
| 安装包体积 / 内存 | 大（~100MB / 数百 MB 内存） | 小 |
| 安全模型 | 需自律（contextIsolation、禁 nodeIntegration） | 默认更严格 |

判断依据：本产品 90% 的复杂度在 **进程编排（Agent CLI 子进程）+ 数据管道（解析/分块/索引）+ 界面**，这三块全部落在 TypeScript/Node 生态的最强处。体积与内存对一个开发者桌面工具是可接受的代价。

Tauri 作为后期迁移选项保留：工程结构上把领域逻辑放在与 Electron 无关的独立包中（见第 3 章），若日后安装包体积成为真实痛点，迁移成本可控。

# 3. 工程结构（pnpm monorepo）

```text
ff-pane/
├── apps/
│   └── desktop/          Electron 主进程 + preload + 渲染层装配
├── packages/
│   ├── shared/           跨包类型定义与工具函数
│   ├── core/             领域逻辑：Project / Plan / Task / Run / Memory 状态机
│   │                     （纯 TS，零 Electron 依赖，可单测可复用）
│   ├── adapters/         Agent Runtime 适配器（codex / claude / gemini /
│   │                     opencode / generic-exec）
│   ├── rag/              知识库管道：解析、分块、嵌入、混合检索
│   └── storage/          Markdown 读写 + SQLite 索引维护
├── locales/              语言包 zh-CN.json / en-US.json
└── docs/                 设计文档
```

硬性规则：

```text
1. core 与 rag 不 import 任何 Electron API，保证可脱离桌面环境测试。
2. 渲染进程不直接碰文件系统和子进程，一切经 preload 暴露的受控 IPC。
3. contextIsolation 开启，nodeIntegration 关闭。
```

# 4. Agent 适配器实现要点

统一适配器接口（示意）：

```typescript
interface AgentAdapter {
  capabilities(): AdapterCapabilities;   // 6 项能力声明（设计文档 5.1）
  start(ctx: SessionContext): AsyncIterable<AgentEvent>;
  send(input: string): Promise<void>;
  cancel(): Promise<void>;               // 进程树终止（Windows: taskkill /T）
  resume?(nativeSessionId: string): AsyncIterable<AgentEvent>;
}

type AgentEvent =
  | { kind: 'session_start'; nativeSessionId?: string }
  | { kind: 'text'; content: string }
  | { kind: 'file_change'; path: string; diff: string }
  | { kind: 'command'; cmd: string; exitCode: number }
  | { kind: 'permission_request'; request: PermissionRequest }
  | { kind: 'end'; reason: EndReason };
```

实现方式：

```text
child_process.spawn 启动 Agent CLI 的 headless 模式
  → stdout 按行读取（readline）
  → 解析 JSONL 事件
  → 映射为统一 AgentEvent
```

各 CLI 的 headless 参数（codex exec 的 JSON 输出、claude -p 的 stream-json、
gemini / opencode 的 JSON 输出模式）**以接入实现时各 CLI 当时版本的实际参数为准**，
差异全部隔离在各自适配器内部，core 层只见统一事件。

L2 通用接入：用户配置命令模板（含 `{task}` 占位符）+ 工作目录 + 环境变量，
一进一出收集 stdout。

密钥注入：由主进程在 spawn 时写入子进程 env，范围仅限该次 Run，渲染层不可见。

# 5. 数据与索引

```text
真实数据源：.workbench/（项目）与 ~/.aiworkbench/（全局）中的
            Markdown / JSON / 导入原文件 —— 布局见设计文档第 10 章
索引层：    better-sqlite3（同步 API，主进程内使用，避免 ORM）
全文检索：  FTS5，使用 trigram tokenizer 兼顾中文与英文子串检索
向量检索：  sqlite-vec 扩展，余弦相似度，维度随嵌入模型
混合检索：  BM25 top-k 与向量 top-k 双路召回 → RRF 融合
可重建性：  删除 index.sqlite → 全量重扫源文件即可恢复，索引永远不是唯一数据
```

# 6. 密钥存储

```text
写入：Electron safeStorage.encryptString() → 密文存本地文件
      （底层为 Windows DPAPI / macOS Keychain / Linux libsecret）
读取：仅主进程可解密；渲染进程永远拿不到明文
展示：界面只显示尾 4 位
禁区：密文与明文均不进入 Git、日志、记忆、知识库、Handoff（设计文档 4.3）
```

# 7. i18n 实现

```text
UI 语言：  i18next + react-i18next，locales/*.json，key-based；
          缺失 key 回退 en-US；启动时检测系统 locale
AI 输出语言：与 UI 语言完全解耦，实现为 Prompt 组装层（设计文档 8.2.2）
          第 1 层角色定义中的一条固定指令，
          按 全局 → Profile → 项目 三级覆盖取值
代码约束： UI 字符串禁止硬编码，CI 中用脚本扫描违规
```

# 8. RAG 管道实现

```text
解析器注册表（按扩展名分发）：
  .md / .txt / 源代码  → 直接读取
  .pdf                → pdfjs-dist 提取文本 + 页码
  .docx               → mammoth → HTML → 纯文本
  .html               → 正文抽取

分块（自研，约数百行，不引入框架）：
  Markdown 按标题树、PDF 按页与段落、代码按函数/类边界（启发式）
  目标 300~800 token，15% 重叠，每块记录出处（文件/标题路径/页码）

嵌入：
  OpenAI 兼容 /embeddings 端点或本地 Ollama（经 Provider 配置）
  批量请求 + 并发限制 + 按块内容哈希断点续传
  未配置嵌入模型 → 纯 FTS 模式，功能不缺失

不采用 LangChain / LlamaIndex：依赖重、黑盒多；
本产品的 RAG 管道 = 解析 + 分块 + 两条 SQL 查询 + RRF，自研量可控。
```

# 10. 被放弃的备选方案

| 备选 | 放弃理由 |
|---|---|
| Tauri 2 | Rust 核心显著提高适配器与 RAG 管道的开发成本；保留为后期迁移选项 |
| Wails（Go） | 同上，且桌面生态更小 |
| Web 应用 + 本地服务进程 | 文件对话框、密钥库、托盘等桌面体验差，双进程部署复杂 |
| LangChain / LlamaIndex | 依赖重、抽象黑盒多，自研管道量可控 |
| 独立向量数据库（Qdrant / Chroma 服务） | 违背"本地单文件、可随时重建"原则，sqlite-vec 足够 |
| Redux / MobX | 状态规模用不上，Zustand 够 |
| Node-PTY / xterm.js | 设计文档 5.5 明确不做 PTY 接入与内嵌终端 |
