# 1.0.33 界面内存不再一直涨 —— 验收办法（T11.14）

> 计划：[`docs/界面内存增长修复计划.md`](../界面内存增长修复计划.md)。开发 2026-11-13，尚未验收。

## 前提

- 改动都在界面。开发模式下开发服务器已经把它推进了正在用的界面（11-13 下午）；关掉重开后日志第一行是 `FF-pane 1.0.33 started`。
- 日志在 `~/.aiworkbench/logs/main-日期.log`（UTC 时间）。

## 步骤

1. **内存不再按小时涨**：团队正常干活 2 小时以上，`[memory]` 行里的 `renderer=` 不再一路涨（11-13 前每小时涨 0.5–1GB），停在几百 MB 上下。
2. **性能记录在清**：`[renderer-mem]` 行末有 `perfCleared=N`。开发模式下 N 是几十到几百（每 5 分钟）；打包后的版本是 0。
3. **少重画**：同样的团队规模下，`perfCleared` 比 11-13 下午改之前（6 个窗口约 13910 条 / 5 分钟）少一个数量级以上。
4. **WebGL 装回去**：遇到 GPU 进程崩了、或 1.0.32 自动结束 GPU 进程后，10 秒左右 `[renderer-mem]` 里的 `webgl=` 回到和 `terminals=` 一样（11-13 那次崩完停在 `webgl=0` 半小时）。

## 已做的检查（开发时）

- 现场：11-13 界面进程内存区域表和完整内存 dump，结论见计划 §2；改动上线后 5 分钟清掉的记录 13910 → 48 条，界面 701MB → 170–180MB。
- 单测：`tests/renderer-perf-clear.test.ts`（清性能记录）、`tests/webgl-pool.test.ts` 新增 3 条（丢了上下文隔 2 秒装回、一分钟内连丢 3 次不再装、等着装时终端关了不装）、`tests/workbench-runtime-store.test.ts`（内存没到显示精度的波动沿用原对象）。全量单测 2888 条通过。
- e2e：`tests/e2e/workbench-terminal.spec.ts` 新增一条：让终端的 WebGL 上下文丢掉且永不恢复，渲染方式依次是 WebGL → DOM → WebGL。工作台相关 e2e（workbench-mcp、supervisor-watch、workbench-terminal、workbench-restart）15 条通过。
- 说明：只结束一次 GPU 进程时上下文会恢复，xterm 自己接上，不需要 C；C 管的是恢复不了的那种（11-13 现场 GPU 进程 1 秒内连崩两次）。
