# 1. 对 v0.1 的分析结论

v0.1 是一份理论完备的提案，但作为开发依据存在三类问题。本文档基于以下取舍展开。

## 1.1 保留的核心（v0.1 的正确部分）

| 设计 | 保留理由 |
|---|---|
| 角色（Role）与 AI 品牌解耦 | 这是产品存在的根本理由，不可动摇 |
| 项目状态归本地工作台所有 | 换 AI 不丢项目，是核心价值 |
| Plan / Task / Run 三层分离 | 任务可重试、结果可追溯的基础 |
| 记忆候选 → 审核 → 正式 的流程 | 防止 AI 推测污染项目事实 |
| 权限跟随角色和任务，不跟随品牌 | 简单且必要 |
| 跨 Agent 用交接包（Handoff），不伪装成会话恢复 | 诚实的产品设计 |

## 1.2 砍掉或推迟的部分（v0.1 过度设计的部分）

| v0.1 设计 | 处理 | 理由 |
|---|---|---|
| 五级接入（A~E 级，含 PTY 模拟） | 精简为两级 + 一个预留位 | PTY 读屏模拟输入不稳定且维护成本极高；实际主流 Agent CLI 都有 headless JSON 模式 |
| Researcher、Memory Curator 角色 | 砍掉 | 查资料是 Planner 顺手的事；记忆整理由用户在界面上点几下完成，不需要一个专职 AI 角色 |
| A2A 协议 | 完全移出设计 | 远程企业 Agent 协作与本产品第一年的目标无关 |
| 20 余字段的 Handoff 包 | 精简为 8 个字段 | 字段越多越没人看，交接的本质是"计划 + 进度 + 决定 + 坑" |
| 14 维权限信封 | 精简为 5 项实用权限 | 读路径、写路径、命令、网络、危险操作确认，够用 |
| 9 种任务状态 | 精简为 6 种 | draft/approved/queued 三态在单 Worker 顺序执行下没有区分意义 |
| 事件账本（Event Ledger）作为独立核心对象 | 降级为 Run 日志 | 第一阶段不需要全局事件溯源系统 |

## 1.3 v0.1 缺失、本版补充的部分

1. **多语言模式**：UI 界面语言 与 AI 输出语言 两套独立机制（第 9 章）。
2. **Provider 配置**：用户可自行填写 API 地址、密钥、模型的完整配置设计，含密钥安全存储（第 4 章）。
3. **三层记忆体系**：项目记忆 → 可提炼的共享记忆 → 用户主动提取的知识库，三者职责、流向、存储全部落实到字段（第 8 章）。
4. **具体数据存储布局**：目录结构、文件格式、检索方案（第 10 章）。
5. **界面页面清单**：每个页面放什么、不放什么（第 11 章）。

# 2. 产品定义

> 一个本地桌面工作台：用户在这里管理项目的计划、任务、记忆和权限，并把具体工作分派给任意可替换的 AI Agent（Codex、Claude Code、Grok 等）执行。

一句话验收标准：**用户今天用 Codex 规划、Claude 执行，明天全部换成 Grok，项目的计划、进度、决定、记忆一条都不丢。**

# 3. 核心概念模型（精简后）

系统只有 9 个核心对象，不再增加。

```text
Project        项目：路径、计划、任务、记忆、配置的边界
Role           角色：Planner / Worker / Reviewer
Provider       模型来源：API 地址 + 密钥 + 模型列表
Agent Profile  运行配置：Runtime + Provider + 模型 + 权限
Plan           计划：版本化的工作合同
Task           任务：计划拆出的有限责任单元
Run            执行：某任务的一次实际尝试
Memory         记忆：项目记忆 + 共享记忆（用户习惯）
Knowledge      知识库：大规模文档 RAG 检索系统，用户主动提取
```

对象关系：

```text
Project ──拥有──> Plan ──拆分──> Task ──尝试──> Run
Role ──绑定──> Agent Profile ──使用──> Provider
Run ──产出──> 报告 / Diff / 记忆候选
项目记忆 ──提炼──> 共享记忆
任意内容 ──用户收录──> 知识库
```

## 3.1 角色设计（三个，不再多）

| 角色 | 职责 | 默认权限 | 是否必须 |
|---|---|---|---|
| Planner | 与用户讨论、出计划草案、拆任务、答疑 | 项目只读 | 必须 |
| Worker | 按任务合同执行、改文件、跑命令 | 任务指定范围可写 | 必须 |
| Reviewer | 对照验收标准审查 Worker 产出 | 只读 + 测试类命令 | 可选，默认关闭 |

- 不设 Researcher：搜索资料是 Planner 的自然能力。
- 不设 Memory Curator：记忆审核在界面上由用户完成（单条记忆点"通过/拒绝"，10 秒的事），不值得为此维护一个 AI 角色。
- 支持用户自定义角色（本质是：一段角色提示词 + 一套默认权限），但不进第一阶段。

# 4. Provider 配置设计

这是用户接触最频繁的配置，必须做到"填完就能用"。

## 4.1 Provider 数据结构

```text
Provider {
  id            内部唯一 ID
  name          显示名，用户自定义，如 "我的 OpenRouter"
  type          openai_compatible | anthropic | cli_login | custom
  base_url      API 地址（cli_login 类型不需要）
  api_key_ref   密钥引用（密钥本体不存在此结构中，见 4.3）
  models        模型列表 [{ id, display_name, kind: chat | embedding }]
  default_model 默认对话模型
  embedding_model 可选，默认嵌入模型（知识库 RAG 使用，见 8.3）
  proxy         可选，代理地址
  timeout_s     可选，超时秒数，默认 120
  enabled       是否启用
}
```

## 4.2 四种 Provider 类型

| 类型 | 含义 | 需要填写 |
|---|---|---|
| openai_compatible | 一切兼容 OpenAI API 格式的服务：OpenAI、OpenRouter、DeepSeek、本地 Ollama/vLLM 等 | base_url + api_key + 模型名 |
| anthropic | Anthropic 官方 API 格式 | base_url + api_key + 模型名 |
| cli_login | Agent CLI 自带登录态（Codex/Claude Code/Grok 的订阅登录），工作台不管理其凭证 | 无，只需确认 CLI 已登录 |
| custom | 自定义请求模板，留给特殊服务 | 按模板填 |

设计要点：

- **模型列表支持两种来源**：点"获取模型列表"按钮从 `/models` 接口拉取；接口不可用时允许手动输入模型 ID。不做失败重试花活，拉不到就手填。
- **连接测试**：每个 Provider 有"测试连接"按钮，发送一次最小请求，显示 成功/失败 + 错误原文。错误原文直接展示，不做"友好化"包装（开发者用户需要原始报错）。
- **一个 Runtime 可搭配多个 Provider**：例如 OpenCode 可以配 OpenRouter，也可以配本地 Ollama。Runtime 与 Provider 的可搭配关系由 Runtime 的适配器声明。

## 4.3 密钥安全（不可妥协的规则）

```text
1. API Key 存入操作系统密钥库（Windows Credential Manager / macOS Keychain），
   配置文件中只存引用 ID。
2. 密钥永远不进入：项目记忆、共享记忆、知识库、Handoff 交接包、
   任务合同、日志文件、导出文件。
3. 界面上密钥输入后只显示尾 4 位。
4. Agent 子进程通过环境变量注入密钥，注入范围仅限该次 Run。
```

## 4.4 Agent Profile

Profile 是用户实际选用的完整配置，公式：

```text
Agent Profile = Runtime + Provider + 模型 + 默认角色 + 权限预设 + 输出语言
```

示例：

```text
Profile: "Claude 执行者"
  Runtime:  claude-code
  Provider: cli_login（Claude 订阅）
  Model:    默认
  默认角色:  Worker
  权限预设:  任务范围可写 + Shell + 无网络
  输出语言:  跟随全局（中文）

Profile: "DeepSeek 规划"
  Runtime:  opencode
  Provider: 我的 DeepSeek API
  Model:    deepseek-chat
  默认角色:  Planner
  权限预设:  项目只读
  输出语言:  中文
```

项目里的角色绑定就是：`Planner → 某个 Profile`、`Worker → 某个 Profile`。换 AI = 换绑定，一个下拉框完成。

# 5. Agent 接入设计（两级 + 一个预留位）

v0.1 的五级接入砍成如下三档。判断标准只有一个：**能不能拿到结构化结果**。

## 5.1 L1：结构化 CLI 接入（主力方式）

适用于支持 headless 模式 + JSON/JSONL 输出的 Agent CLI（Codex、Claude Code、Grok、OpenCode 等当前主流 Agent 均支持）。

工作台需要从适配器拿到的最小事件集：

```text
会话开始（含原生 Session ID，若有）
文本输出
文件修改（路径 + diff）
命令执行（命令 + 退出码）
权限请求
会话结束（结束原因）
```

适配器为每个 Runtime 声明能力清单（精简为 6 项，v0.1 列了 16 项）：

```text
支持原生会话恢复？
支持流式输出？
支持文件修改事件？
支持命令执行事件？
支持权限请求转发？
支持中途取消？
```

## 5.2 L2：单次命令接入（兜底方式）

任何 CLI 工具，一进一出：

```text
stdin/参数 传入任务文本 → 进程运行 → stdout 收集结果 → 进程结束
```

用户在界面上配置：启动命令、参数模板、工作目录、环境变量。新出现的 AI 工具即使没有专用适配器，也能以此方式先用起来。L2 接入的 Agent 只能当 Worker 执行小任务或当一次性问答工具，不建议当 Planner（无会话连续性）。

## 5.3 Runtime 覆盖计划（评审确认：尽可能覆盖市场主流）

模型覆盖与 Runtime 覆盖是两件事，分开达成：

- **模型覆盖靠 Provider 层**：openai_compatible 类型即可接入 OpenAI、DeepSeek、Qwen、Kimi、GLM、xAI（Grok API）、Mistral、本地 Ollama/vLLM 等一切兼容服务；anthropic 类型覆盖 Claude 系；Gemini 走其 OpenAI 兼容端点或原生适配。
- **Runtime 覆盖靠适配器矩阵**，并优先接入"自身支持多 Provider 的开放 Runtime"（OpenCode、Aider 等）——一个适配器就能把上述所有主流模型变成可用的 Planner/Worker。

| Runtime | 接入等级 | 阶段 | 说明 |
|---|---|---|---|
| Codex CLI | L1 | M1 | headless + JSON 事件流 |
| Claude Code | L1 | M1 | headless + stream-json |
| Gemini CLI | L1 | M1 | headless + JSON 输出 |
| OpenCode | L1 | M1 | 多 Provider 开放 Runtime，一次接入覆盖主流模型 |
| Grok Build | L1 | M2 | |
| Aider | L1 | M2 | 多 Provider，Git-first |
| Qwen Code / iFlow 等 | L1/L2 | M2+ | 按用户需求排期 |
| 任意 CLI 工具 | L2 | M1 | 通用单次命令接入兜底 |

新 Runtime 的接入成本目标：一个 L1 适配器 ≤ 500 行代码（进程启动 + 事件流解析 + 能力声明）。

## 5.4 预留位：ACP

Agent Client Protocol 作为未来的标准接入方式预留接口位置，第一阶段不实现。当有两个以上主流 Agent 的 ACP 支持稳定后再评估。

## 5.5 明确不做

- **不做 PTY 终端模拟接入**（读屏 + 模拟按键）。这条路会把产品拖成终端自动化工具，且永远不稳定。某个 Agent 若只能以 TUI 交互使用，就不接入它，等它出 headless 模式。
- **不内嵌终端分屏界面**。需要看原始日志时提供"打开日志文件"入口即可。

# 6. 计划与任务设计

## 6.1 计划（Plan）

计划是版本化的工作合同。字段：

```text
Plan {
  version       v1, v2, v3...（只增不改，修改即产生新版本）
  status        draft | approved | superseded | completed | cancelled
  goal          目标（一段话）
  scope         范围（做什么）
  non_goals     非目标（明确不做什么）
  constraints   约束与禁止事项
  decisions     本计划包含的已确认决定
  tasks         任务列表（含依赖关系）
  acceptance    总体验收标准
  approved_by   批准记录（用户 + 时间）
}
```

规则：

- 只有 `approved` 状态的计划可以派发任务。
- 批准动作只能由用户在界面上完成，任何 Agent 不能标记计划为已批准。
- Planner 修改已批准计划时自动生成新版本草案，旧版本转为 `superseded`。

## 6.2 任务合同（Task）

Worker 收到的不是聊天记录，是任务合同：

```text
Task {
  id
  plan_version    所属计划版本
  goal            任务目标
  write_scope     允许修改的路径列表
  forbidden       禁止事项
  depends_on      依赖的任务
  context_refs    注入的记忆条目 ID 列表（见第 8 章）
  acceptance      验收标准（可核对的条目）
  verify_cmd      验证命令（如测试命令）
  status          见 6.3
}
```

## 6.3 任务状态（6 种）

```text
pending    已批准待执行
running    执行中
blocked    被阻塞（等用户回答澄清请求 / 等权限审批）
failed     执行失败（可重试，产生新 Run）
done       Worker 声称完成且验证命令通过
accepted   用户（或 Reviewer + 用户）确认接受 —— 终态
cancelled  取消 —— 终态
```

关键规则沿用 v0.1：`done ≠ accepted`。"AI 说完成了"和"项目认为完成了"永远是两件事。

## 6.4 Run（执行记录）

每次尝试一条 Run 记录：

```text
Run {
  task_id, 序号
  profile         用哪个 Agent Profile 执行的
  started / ended
  end_reason      completed | failed | cancelled | crashed
  file_changes    修改文件列表 + diff
  commands        执行过的命令 + 退出码
  verify_result   验证命令输出
  report          Worker 的完成报告
  raw_log_path    原始日志文件路径（保留但不进主界面）
}
```

## 6.5 澄清请求（沿用 v0.1，格式固定）

Worker 遇到不确定的问题时提交结构化澄清请求（问题 / 影响 / 选项 / 建议），任务转 `blocked`，由用户或 Planner 回答后继续。不允许 Worker 和 Planner 绕开用户自由对话。

# 7. 权限设计（精简为 5 项）

每次 Run 的权限由 5 项组成，取"角色默认 ∩ 任务指定 ∩ 用户批准"的交集：

| 权限项 | Planner 默认 | Worker 默认 | Reviewer 默认 |
|---|---|---|---|
| 可读路径 | 项目内 | 项目内 | 项目内 |
| 可写路径 | 无 | 任务合同的 write_scope | 无 |
| Shell 命令 | 禁止 | 允许（危险命令除外） | 仅验证命令 |
| 网络 | 允许（查资料） | 默认禁止，任务可开 | 禁止 |
| 危险操作 | —— | 全部需用户逐次确认 | —— |

危险操作清单（固定，不可被 Agent 申请豁免）：

```text
删除文件超出 write_scope
git push
修改 .git 目录
读取密钥/凭证类路径（~/.ssh、.env 等，内置黑名单）
安装系统级软件
任何形式的发布与部署
```

Agent 可以在 Run 中发起权限扩展请求 → 任务转 `blocked` → 用户在界面上一键 批准/拒绝。批准仅对当前 Run 有效，不产生永久授权。

# 8. 三层记忆体系（本版核心补充）

这是用户明确要求细化的部分。三层各司其职，流向清晰：

```text
┌────────────────────────────────────────────────┐
│  第 1 层：项目记忆（Project Memory）              │
│  跟随项目。Agent 按需自动注入。                    │
│  来源：任务沉淀、用户手写、Planner 提议的候选。      │
└──────────────┬─────────────────────────────────┘
               │ 用户点"提炼"（可由系统建议）
               ▼
┌────────────────────────────────────────────────┐
│  第 2 层：共享记忆（用户习惯记忆）                  │
│  跨项目生效，权限极高：直接参与每次会话的           │
│  Prompt 组装，改变 AI 做事的方式与顺序。            │
│  内容：用户的开发习惯、做事顺序、技术与沟通偏好。     │
└────────────────────────────────────────────────┘

┌────────────────────────────────────────────────┐
│  第 3 层：知识库（Knowledge Base）— 独立于上两层    │
│  大规模文档 RAG 检索系统。用户主动提取为主，         │
│  可选开放为 Agent 的只读检索工具。                  │
└────────────────────────────────────────────────┘
```

## 8.1 第 1 层：项目记忆

### 分类（4 类，够用）

| 类别 | 内容 | 示例 |
|---|---|---|
| decision | 已确认的决定 | "存储用 SQLite，不用 PostgreSQL" |
| rule | 项目规则与约束 | "src/legacy/ 目录禁止修改" |
| lesson | 验证过的经验教训 | "本项目测试必须用 `pnpm test:win`，`npm test` 在 Windows 下会挂" |
| state | 当前状态快照 | "登录模块完成，Token 刷新有遗留 bug" |

### 记忆条目字段

```text
MemoryEntry {
  id
  category      decision | rule | lesson | state
  title         一句话标题
  body          正文（Markdown，建议 200 字内）
  status        candidate | active | archived
  source        来源：user_manual | task_<id> | plan_<version> | agent_proposed
  confidence    high（用户确认/测试证实） | low（AI 提议未验证）
  created / updated
  supersedes    替代了哪条旧记忆（可空）
  tags          可选标签
}
```

### 状态流转（3 态，比 v0.1 的 6 态精简）

```text
candidate ──用户通过──> active ──被新条目替代/过时──> archived
    └──────用户拒绝──> 直接删除
```

规则：

- Agent（任何角色）只能产生 `candidate`，写入 `active` 的唯一途径是用户在界面上点通过。
- 用户手写的条目直接 `active`。
- 任务进入 `accepted` 时，系统提示"本任务产生了 N 条记忆候选，去审核"，不弹窗打断，只在记忆页显示角标。

### 注入策略（避免上下文膨胀）

```text
Planner 注入：全部 active 的 decision + rule + state（通常总量很小）
Worker  注入：任务合同 context_refs 指定的条目（Planner 拆任务时挑选）
Reviewer注入：任务的验收标准 + 相关 rule
上限：单次注入不超过设定条数（默认 20 条），超出时按 类别优先级 + 更新时间 截断
```

第一阶段用 SQLite FTS5 全文检索做记忆查询，**不引入向量数据库**。记忆条目是短文本 + 有分类标签，全文检索完全够用。

## 8.2 第 2 层：共享记忆（用户习惯记忆）

评审确认的定位：**共享记忆就是用户的开发习惯，属于非项目记忆，权限极高——它直接参与 Prompt 的组装，改变 AI 做事的方式和顺序。** 产品目标是"越用越顺手"：用得越久，AI 越像一个了解你工作方式的老搭档，你需要重复解释的东西越来越少。

### 8.2.1 习惯条目分类（4 类）

| 类别 | 内容 | 示例 |
|---|---|---|
| workflow | 做事顺序与流程习惯 | "任何改动前先跑一遍现有测试""先出方案要我确认，再动手写代码" |
| tech | 技术偏好 | "优先 TypeScript""数据库默认 SQLite""不写行尾注释" |
| communication | 沟通偏好 | "回复用中文""结论先行，解释在后""commit message 用英文" |
| environment | 环境经验 | "Windows 下 pnpm 需要 --shamefully-hoist" |

不收架构决定（架构永远是项目相关的，归项目记忆）、不收任务状态、不收资料（归知识库）。范围收窄保证习惯记忆是一个小而精、全部可信的集合。

### 8.2.2 高权限：直接参与 Prompt 组装

每次会话的系统提示按固定层序组装，习惯档案位于第 2 层，先于项目记忆：

```text
第 1 层  角色定义（Planner / Worker / Reviewer 的职责说明）
第 2 层  用户习惯档案（由全部 active 习惯条目编译而成）
第 3 层  项目记忆（decision / rule / state，按角色策略注入）
第 4 层  当前输入（任务合同 / 用户消息）
```

"用户习惯档案"是习惯条目的编译产物：按类别分组、按重要度排序、渲染成一段紧凑的指令文本，任何习惯条目变更后自动重新编译。其中 workflow 类习惯被显式标注为"执行前必须遵守的流程约束"。

### 8.2.3 习惯先行（核心行为变化）

有了 workflow 习惯后，AI 对用户指令的响应方式发生根本变化——**一句话指令不再被立即执行，而是先经过习惯档案的"规划性整形"**：

```text
没有习惯档案时：
  用户："帮我做个登录页" → AI 直接开始生成代码

有习惯档案时：
  用户："帮我做个登录页"
  → Planner 先核对习惯档案：
     #W3 "先出方案要我确认，再动手"
     #W1 "UI 类工作先给页面结构，再写样式"
     #T2 "优先 TypeScript"
  → 输出：一份带步骤顺序的简短方案（页面结构 → 用户确认 → 实现 → 测试），
     等确认后才进入执行
```

用户随时可以说"直接做"来单次跳过整形，但习惯档案本身不失效。

### 8.2.4 习惯的来源与提炼

```text
来源一：用户手写（设置页直接添加，立即 active）
来源二：从项目记忆提炼——
   a. 用户在项目记忆页选中条目，点"提炼到共享记忆"；
   b. 审核候选时，若条目不含项目专有名词（路径、模块名、项目名），
      界面提示"该条目似乎是通用习惯，是否提炼？"——只提示，不自动执行。
   提炼时剥离项目专有信息（"本项目的测试命令"→"Windows 下 pnpm 项目"），
   用户在提炼对话框中确认或修改文本，保留溯源字段
   source_project + source_entry_id。
来源三：系统观察建议——用户在会话中重复出现同类纠正时
   （例如三次要求"先别写代码，先说思路"），系统生成习惯候选，
   提示"是否将此确认为长期习惯？"
```

因为权限极高（影响所有项目、所有会话的 Prompt），**任何来源的习惯条目都必须经用户确认才能 active**。习惯档案在设置页全程可见、可编辑、可单条停用。

### 8.2.5 冲突检查与规模控制

```text
入库前做全文相似检索，发现相近或矛盾条目时并排展示，
用户选择 合并 / 替代 / 都保留。
全量注入，上限默认 80 条；接近上限时提示用户合并或归档，不做自动淘汰。
```

## 8.3 第 3 层：知识库（实战型 RAG 检索系统）

评审确认的定位：**知识库是一个大规模的文档与内容检索系统（RAG），追求实战可用**，不是收藏夹。用户可以把整个文档目录、技术资料、历史方案沉进去，在需要时精准取出。

### 8.3.1 与记忆的本质区别

| | 记忆 | 知识库 |
|---|---|---|
| 谁在维护 | 半自动（Agent 提候选，用户审核） | 用户主动导入 + 系统自动索引 |
| 进入 Agent 上下文的方式 | 按策略自动注入 | 用户主动提取；或经用户开启的只读检索工具 |
| 内容性质 | 事实、经验、习惯（短文本） | 文档、资料、代码、方案（任意规模） |

### 8.3.2 收录（Ingestion）

```text
支持格式：Markdown / txt / 源代码文件 / PDF / docx / html
导入方式：
  - 单文件或整个文件夹批量导入（保留目录结构作为来源路径）
  - 从会话收录（任意消息 →"存入知识库"）
  - 手动新建条目
增量索引：按内容哈希判断变化，只重新索引变动的文件
容量目标：万级文档、十万级文本块可正常工作
```

### 8.3.3 处理管道

```text
解析（按格式提取正文与结构）
    ↓
分块（结构感知：Markdown 按标题层级、PDF 按页与段落、
      代码按函数/类边界；块大小 300~800 token，带重叠）
    ↓
双路索引：
  FTS5 全文索引（关键词 / BM25）——永远可用
  向量索引（嵌入模型生成，存 sqlite-vec）——配置了嵌入模型才启用
```

嵌入模型通过 Provider 配置（openai_compatible 的 /embeddings 端点，或本地 Ollama）。**未配置嵌入模型时，知识库降级为纯全文检索，功能完整可用**——向量检索是增强，不是前提。

### 8.3.4 检索（Retrieval）

```text
混合检索：FTS5(BM25) 与 向量相似度 双路召回 → RRF 融合排序
结果形态：命中块 + 上下文扩展（前后相邻块）+ 出处（文件路径 / 标题 / 页码）
过滤维度：来源目录、格式、标签、导入时间
```

### 8.3.5 使用（两条路径）

```text
路径一：用户主动提取（默认，主路径）
  知识库页搜索 → 选中结果 →"发送到当前会话"（自动附带出处引用）
  会话输入框的"从知识库插入"按钮走同一流程

路径二：Agent 只读检索工具（项目级开关，默认关闭）
  开启后，该项目的 Agent 获得一个只读检索工具：query 进、命中块出。
  Agent 每次调用了什么、命中了什么，在执行记录中全部可见。
  Agent 永远不能写入、修改、删除知识库。
```

### 8.3.6 导出与维护

```text
导出：选中条目 / 整个来源目录 → Markdown 文件（含出处元数据）
维护：来源管理页显示每个来源的文档数、块数、索引状态；
      支持移除来源（连带删除其索引）与一键重建索引
明确不做：自动摘要、自动打标签、网页剪藏、知识图谱
```

## 8.4 记忆与知识库的存储原则

记忆（项目记忆、习惯记忆）以 **Markdown 文件为真实数据源**；知识库以 **导入的原文件为真实数据源**。SQLite 中的全文索引与向量索引都只是派生数据，可随时删除重建。保证：

```text
用户可以用任何编辑器直接查看和修改
可以整体提交进 Git
可以直接拷贝迁移到另一台机器
卸载本软件后数据仍然完全可用
```

具体目录布局见第 10 章。

# 9. 多语言设计

两套独立机制，不要混为一谈。

## 9.1 界面语言（UI i18n）

```text
支持语言：zh-CN、en-US（首发两种，架构上支持随时增加语言包）
切换位置：设置页，立即生效，无需重启
默认值：跟随操作系统语言，无匹配语言包时回退 zh-CN
       （2026-09-01 经用户确认：产品以中文为默认语言，回退语言由 en-US 改为 zh-CN；
         系统语言检测保留，解析顺序仍为 已保存的选择 → 系统语言宽松匹配 → zh-CN）
缺 key 回退：某语言包缺某个 key 时用 zh-CN 的文案顶上（中文为基准语言）；
       这与上面的「解析回退」是两个问题，前者决定显示哪种语言、后者决定缺失文案从哪本取
实现约束：
  - 所有 UI 字符串走 key-based 语言包（JSON），代码中禁止硬编码文案
  - 日期时间按 locale 格式化
  - 语言包文件独立存放，社区可贡献新语言
```

## 9.2 AI 输出语言

与界面语言解耦——用户可能界面用英文、但要求 AI 用中文回复。

```text
设置层级（低层覆盖高层）：
  全局默认 AI 输出语言（设置页）
    ↓ 覆盖
  单个 Agent Profile 的输出语言
    ↓ 覆盖
  单个项目的输出语言

实现方式：作为一条固定指令注入角色提示词，
  如"Always respond in Simplified Chinese."
```

## 9.3 数据语言

记忆、计划、知识库内容**以写入时的语言原样存储，不做任何自动翻译**。翻译需求由用户在会话里让 AI 完成。

# 10. 数据存储布局

## 10.1 全局数据（用户目录）

```text
~/.aiworkbench/               （Windows: %USERPROFILE%\.aiworkbench\）
├── config.json               全局设置：界面语言、AI 输出语言、默认权限预设
├── providers.json            Provider 列表（密钥只存引用，本体在系统密钥库）
├── profiles.json             Agent Profile 列表
├── habits/                   共享记忆（用户习惯），一条一文件
│   ├── workflow/*.md
│   ├── tech/*.md
│   ├── communication/*.md
│   └── environment/*.md
├── knowledge/                知识库
│   ├── sources/              导入的原文件（保留导入时的目录结构）
│   └── notes/*.md            手动新建与会话收录的条目
└── index.sqlite              习惯 + 知识库索引（FTS5 全文 + sqlite-vec 向量，可重建）
```

## 10.2 项目数据（项目目录内）

```text
<项目目录>/.workbench/
├── project.json              项目配置：角色绑定、输出语言覆盖、权限策略
├── plans/
│   ├── plan-v1.md            计划正文（人类可读）
│   ├── plan-v1.meta.json     状态、批准记录
│   └── ...
├── tasks/
│   └── task-<id>.json        任务合同 + 状态
├── runs/
│   └── run-<id>/
│       ├── run.json          结构化执行记录
│       ├── changes.diff      文件修改
│       └── raw.log           原始日志
├── memory/
│   ├── decisions/*.md
│   ├── rules/*.md
│   ├── lessons/*.md
│   ├── state.md              当前状态快照（单文件，覆盖更新）
│   └── candidates/*.md       待审核候选
├── knowledge/                项目归属的知识库条目（可选）
└── index.sqlite              本项目检索索引（可重建）
```

设计规则：

```text
1. Markdown 是真实数据源，JSON 存结构化元数据，SQLite 只做索引。
2. .workbench/ 可整体提交 Git（raw.log 和 index.sqlite 默认写入 .gitignore）。
3. 会话原始记录归 Agent 自己（Codex/Claude 各自的会话文件），
   工作台只登记 Native Session ID 用于原生恢复，不复制会话内容。
```

## 10.3 会话恢复（沿用 v0.1 三分法，落实存储）

```text
同 Agent + 支持原生恢复 → 用登记的 Native Session ID 恢复，界面标注"原生恢复"
同 Agent + 不支持       → 用 计划 + 任务 + state.md + 最近 Run 报告 重建，标注"上下文重建"
换 Agent               → 生成 Handoff（见 10.4），标注"跨 Agent 迁移"
```

## 10.4 Handoff 交接包（精简为 8 字段）

```text
Handoff {
  project_goal      项目目标（一段话）
  plan              当前计划版本全文
  progress          任务清单及状态（done/进行中/待办）
  decisions         active 状态的 decision 记忆
  rules             active 状态的 rule 记忆
  recent_lessons    最近的 lesson 记忆
  open_issues       阻塞与未决问题
  expectation       期望接收方接下来做什么
}
```

生成后展示给用户预览（可编辑），确认后注入新 Agent 会话。密钥、原始日志、其他项目内容永不进入 Handoff。

# 11. 界面设计（7 个页面，不再多）

原则：信息密度优先，无引导动画、无吉祥物、无成就系统、无空状态插画。每个页面回答一个明确的问题。

## 11.1 项目列表（回答：我有哪些项目，各自到哪了）

```text
项目卡片：名称、路径、当前计划版本与状态、进行中任务数、最后活动时间
操作：打开 / 新建（选目录即建）/ 移除（不删文件）
```

## 11.2 会话页（回答：我正在和谁讨论什么）——主界面

```text
顶部状态条（常驻一行）：
  角色 | Profile 名 | 模型 | 权限摘要（如"只读"） | 会话类型（原生/重建/迁移）
主体：对话流
右侧可折叠栏：当前计划概要 + 进行中任务
消息级操作：任意消息右键 →"存入知识库"/"提为记忆候选"
底部：输入框 + 角色切换 + "从知识库插入"按钮
```

## 11.3 计划页（回答：我们决定做什么）

```text
版本列表（v1, v2...）+ 当前版本正文（目标/范围/非目标/约束/任务拆分/验收标准）
操作：批准（仅用户可点）/ 让 Planner 修改（产生新草案版本）/ 版本对比（文本 diff）
```

## 11.4 任务页（回答：现在做到哪了）

```text
按状态分列的任务列表：pending / running / blocked / failed / done / accepted
任务卡片：目标、write_scope、验收标准、最新 Run 结果摘要
blocked 任务置顶显示待答的澄清请求/权限请求，一键处理
操作：派发 / 重试（新 Run）/ 接受 / 取消
```

## 11.5 执行记录页（回答：AI 到底改了什么）

```text
Run 列表 → 单个 Run 详情：
  文件修改（diff 视图）/ 执行命令与退出码 / 验证结果 / Worker 报告
  "打开原始日志"入口（外部打开，不内嵌终端）
```

## 11.6 记忆页（回答：项目记住了什么）

```text
三个标签页：项目记忆 / 共享记忆（习惯档案）/ 待审核候选（带数量角标）
条目列表按类别分组，全文搜索框
条目操作：编辑 / 归档 / 提炼到共享记忆（项目记忆条目）
候选操作：通过 / 编辑后通过 / 拒绝
```

## 11.7 知识库页 + 设置页

```text
知识库：搜索框（混合检索）+ 命中结果（块 + 出处）+ 正文预览
  操作：导入文件/文件夹 / 新建 / 发送到当前会话 / 导出 Markdown / 删除
  来源管理：各来源的文档数、块数、索引状态、一键重建索引
设置：Provider 管理（含测试连接、嵌入模型）/ Profile 管理 / 界面语言 /
  AI 输出语言 / 默认权限预设 / 习惯档案管理
```

# 12. 标准工作流（端到端串一遍）

```text
1. 新建项目：选目录，绑定 Planner Profile 和 Worker Profile（各一个下拉框）
2. 会话页与 Planner 讨论（Planner 只读 + 已注入共享记忆和项目记忆）
3. 用户："出计划" → Planner 产出 plan-v1 草案 → 计划页显示
4. 用户在计划页修改、批准 → plan-v1 approved
5. 任务自动生成合同，用户在任务页逐个"派发"（第一阶段单 Worker 顺序执行）
6. Worker 执行：改文件、跑验证命令；越权操作自动转权限请求
7. Run 结束：任务转 done（验证通过）或 failed（可重试）
8. 用户看执行记录页的 diff 和验证结果 → 任务页点"接受" → accepted
9. 系统汇总本任务的记忆候选 → 用户在记忆页审核 → 属于个人习惯的条目顺手提炼到共享记忆（习惯档案）
10. 中途换 AI：项目设置里换绑 Profile → 预览 Handoff → 确认 → 新 Agent 带着完整上下文继续
```
