## 2. 逐项核查

### 1. 项目记忆互不可见（项目作用域）

- **验证方式：** Alpha 与 Beta 各落一条 active 的 rule 记忆（`rule-alpha.md` / `rule-beta.md`），分别经 `memory:list` 读回。
- **证据：** `expect(result.alpha.memory).toEqual(["rule-alpha"])`；`expect(result.beta.memory).toEqual(["rule-beta"])`。磁盘核对：`alpha/.workbench/memory/rules` 只有 `rule-alpha.md`，`beta/.workbench/memory/rules` 只有 `rule-beta.md`。
- **结论：** ✅ 通过。`memory:list` 的请求形状是 `ProjectScopedRequest`，主进程 `resolveProjectLayout(request.projectRoot)` 后只扫该项目的 `memory/`，物理上够不到另一个项目。

### 2. 共享记忆（习惯）确为全局

- **验证方式：** 建一条 workflow 习惯，经 `habits:list` 读回；核对落盘位置。
- **证据：** `habits:create` / `habits:list` 的请求里**没有 `projectRoot` 可填**（`CreateHabitRequest` / `undefined`），读回内容为该条习惯；磁盘上它落在全局数据根 `<dataRoot>/habits/workflow/` 下（该目录恰好 1 项），不在任何项目的 `.workbench/` 内。
- **结论：** ✅ 通过。全局是**结构性**的，不是"两个项目碰巧读到同一份"——通道层根本不接受项目参数（§8.2 共享记忆跨项目）。

### 3. 知识库确为全局

- **验证方式：** 经 `knowledge:create-entry` 建一条笔记，`knowledge:list` 读回；核对索引库与原文件落点。
- **证据：** 条目标题出现在 `knowledge:list` 结果中；`<dataRoot>/knowledge/notes/` 非空、`<dataRoot>/index.sqlite` 存在；两个项目的 `.workbench/knowledge` 均为空目录，`.workbench/index.sqlite` 均不存在。
- **结论：** ✅ 通过。**附一条如实记录**：`ProjectLayout` 里声明了 `knowledgeDir` 与 `indexDbFile` 两个项目级路径（W1.2a 预留），`initProjectLayout` 也会把 `knowledge/` 目录建出来，但 T6.5 的知识库层一律绑全局根（`main/knowledge/index.ts` 的 `initGlobalLayout(resolveGlobalRoot())`），当前**没有任何写入者**往项目级那两个路径写东西。本次核查已把"它们确实是空的"作为断言固定下来——将来若有人给项目级知识库接线，这条断言会先红。

### 4. `.workbench/` 边界 —— 计划

- **验证方式：** 只给 Alpha 落 `plan-v1.meta.json` + `plan-v1.md`，两个项目分别 `plans:list`。
- **证据：** Alpha 得 `[1]`，Beta 得 `[]`；磁盘上 `beta/.workbench/plans` 为空目录。
- **结论：** ✅ 通过。

### 5. `.workbench/` 边界 —— 任务

- **验证方式：** 只给 Alpha 落两个任务文件（`running` + `accepted`），两个项目分别 `tasks:list`。
- **证据：** Alpha 得 `["task-alpha-1","task-alpha-2"]`，Beta 得 `[]`；`beta/.workbench/tasks` 为空目录。
- **结论：** ✅ 通过。

### 6. `.workbench/` 边界 —— Run

- **验证方式：** 只给 Alpha 落一个 `runs/run-run-alpha-1/`（含 `run.json` + `raw.log`），两个项目分别 `runs:list`。
- **证据：** Alpha 得 `["run-alpha-1"]`，Beta 得 `[]`；`beta/.workbench/runs` 为空目录。
- **结论：** ✅ 通过。

### 7. 会话登记不串项目

- **验证方式：** 只给 Alpha 落 `sessions.json`（一条 `ls-alpha`），两个项目分别 `sessions:list`。
- **证据：** Alpha 得 `["ls-alpha"]`，Beta 得 `[]`；`beta/.workbench/sessions.json` **不存在**（读不到文件按空集处置，不是读到了别人的）。
- **结论：** ✅ 通过。会话登记表是**项目级单文件**（`ProjectLayout.sessionsFile`），不存在一张全局表按项目过滤的写法，也就不存在过滤漏掉的可能。

### 8. 项目卡片派生信息各算各的，缺数据如实降级

- **验证方式：** 一次 `projects:summary` 同时拿三个项目的摘要；另在界面上核对三张卡片。
- **证据（IPC）：**
  - Alpha：`planVersion:1` / `planStatus:"approved"` / `activeTaskCount:1`（两条任务里 accepted 的那条已收尾）/ `taskCount:2` / `lastActivityAt:RUN_ENDED_AT` / `lastActivitySource:"run"`（三个候选时刻里 Run 收尾最晚）/ `unavailable:[]`；
  - Beta：`workbenchPresent:true` / 无 `planVersion` / `activeTaskCount:0` / 无 `lastActivityAt` / `unavailable:[]`；
  - Gamma：`workbenchPresent:false` + 零值（数据目录被端掉后如实报缺失，**不伪装成一个干净的新项目**）。
- **证据（界面）：** 项目页三张卡片分别显示 `Plan v1 · Approved` + `1 in progress` + `Last activity … · runs`；`No plan yet` + `0 in progress` + `No activity yet`；`… details unavailable`。
- **结论：** ✅ 通过。且一个项目读不出来不影响另外两个（`summarizeProjects` 逐项目独立 try，单测另有两条专门断言）。

### 9. 结构性核查：作用域在契约层强制

- **验证方式：** 清点 `shared-ipc/contracts.ts` 的 `IpcInvokeContracts` 全表，按请求形状是否为项目作用域（`ProjectScopedRequest` 及其派生：`TaskActionRequest` / `MemoryActionRequest` / `UpdateMemoryRequest` / `ApprovePlanRequest` / `UpdateProjectSettingsRequest` / `StartSessionRequest`）分两类。
- **证据：** 58 条通道 = **项目作用域 15 条** + **全局 43 条**。
  - 项目作用域 15 条：`projects:get-settings`、`projects:update-settings`、`tasks:list`、`tasks:accept`、`tasks:cancel`、`runs:list`、`memory:list`、`memory:approve`、`memory:reject`、`memory:update`、`plans:list`、`plans:approve`、`sessions:list`、`handoff:generate`、`session:start`——**全部**要求调用方给出 `projectRoot`，主进程一律 `resolveProjectLayout` 后再读写，没有"当前项目"这类主进程侧的隐式状态可被串改。
  - 全局 43 条里与数据有关的是 Provider / Profile / 全局设置 / 密钥 / 习惯 / 知识库 / 项目注册表，**按设计就该是全局**（§10.1）；`session:respond-permission` 与 `session:cancel` 按 `turnId` 定位在飞轮次，而该轮次是由带 `projectRoot` 的 `session:start` 建立的，不引入新的作用域。
- **结论：** ✅ 通过。"当前项目"只存在于渲染层（`useUiStore.activeProjectId` → `useActiveProject` → 各页面把 `entry.rootPath` 传进请求）；主进程不持有它，因此**切项目不可能让上一个项目的读写落到新项目头上**。

## 4. 本次核查未覆盖的部分（如实登记）

| 未覆盖 | 原因 | 归属 |
|---|---|---|
| 两个项目**同时各跑一轮真实 Agent** 时的隔离（子进程 cwd、权限信封的 writePaths、Run 目录落位） | 需要两套可用 Provider 与真机 CLI，属验收演示范畴；单轮的 cwd 与权限信封已由 Phase 2 权限层与编排器单测覆盖 | 验收演示 |
| 同一个项目目录被登记两次（不同项目名）时的行为 | 注册表以 `rootPath` 唯一（`ProjectAlreadyRegisteredError`），不是"两个项目并存"的形态 | 已有 storage 单测覆盖 |
| 项目根目录互为父子（A 在 B 的子目录里）时的边界 | `.workbench/` 按各自项目根解析，互不包含；但 Agent 的写入范围是另一层（权限层 writePaths）的事，不属本单 | M3 评估 |
