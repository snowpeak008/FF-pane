  - **审查不铸新 Run，结论写回被审的那条 Run**：Run 的语义是「任务的一次实际尝试」（§6.4），
    审查不是尝试；更要紧的是 `completeTask` 的 done 门槛只认「本任务一条 `endReason=completed`
    的 Run」——给审查也铸一条 Run，审查者就能替执行者把任务盖成 done。故加 `Run.review?` 字段，
    attempt 序号继续只数 Worker 的尝试。回写走独立的 `updateRun`（只改 run.json），不走
    `persistRun`——后者连带写 raw.log 与 changes.diff，而那两份正是被审查的证据本身。
  - **结论不改任务状态，也不否决用户**：`acceptTask` 在状态机层就只认 `actor="user"`（§6.3
    done ≠ accepted）。界面上 `fail` 时接受键降级为 secondary 并加一行说明，**但仍可点**——
    「不替代用户确认」是双向的，Reviewer 说不行同样不能替用户否决。
  - **verdict 三态，解析失败一律落 `inconclusive` 并保留原文**：代价不对称——把 fail 猜成 pass，
    用户看到的是一份「通过了审查」的不合格改动；落 inconclusive 最坏只是让他自己读一遍原文。
    也因此 `parseReviewConclusion` 不返回失败：计划轮解析失败可以什么都不写盘（重来一次即可），
    审查轮已经真金白银跑过一遍只读命令，把结果丢掉才是浪费。
  - **轮次没跑完则不写结论**：取消 / 崩溃 / 失败不是「一次得不出结论的审查」，而是一次没发生的
    审查；写成 inconclusive 会覆盖掉此前那次真审查的结论，也会掩盖「被权限层掐断」这件事。
  - **信封直接取角色默认 ∩ Profile 预设，不走 `assembleRunEnvelope`**：那条路径会把任务信封
    （shell=allowed、writePaths=任务可写路径）并进来。虽然与 Reviewer 角色默认相交后结果仍是对的，
    但那是「靠交集恰好救回来」——读代码的人得自己在脑子里算一遍才敢确信审查者不能写文件。
    直接相交则「审查者不可写」是当场可见的事实。verify_only 白名单照给任务合同的 `verify_cmd`（§7）。
  - **第 4 层给审查材料而不是任务合同**：合同渲染的是**执行指令**（「你只能改这些路径」），
    会把审查者往「我该去做点什么」的方向带；审查者要的是「这些标准满足了没有」。材料含验收标准、
    禁止事项、可写范围、diff、命令与验证结果，并把 Worker 的完成报告明标为**自述而非证据**。
    不给 `raw.log`（§10.4 同款红线：体积不可控且极易夹带密钥回显）。
  - **diff 有预算（默认 6 万字符）且截断必须写明**：一次大改动的 diff 能到几十万字符，整段塞进去
    是整轮起不来而非「审得不够细」。整文件收或不收（不切半个 hunk——半个 hunk 比没有更坏，
    它看起来像一段完整的改动），并在文本里告诉审查者还有几个文件没看到、对没看到的部分别下结论。
  - **任务侧不持久化 verdict，由 `runs:list` 当场派生**：任务可以有多条 Run，在 Task 上存一个
    verdict 等于要求某处代码回答「多条 Run 各有结论时任务算什么」——那个问题没有正确答案。
    任务卡片要的其实是「最后那次尝试审过没有」，算得出来且永远与事实一致（同 §11.1 派生信息不持久化）。
    取 attempt 最大者而非数组末位：`runs:list` 的顺序由目录枚举决定，与尝试先后无关。
  - **开关与绑定分开存，关掉开关不清绑定**：审查是会被反复开开关关的功能（「这个任务重要，
    让它审一下」），每次重开都要重选审查者是纯粹的摩擦。故「没有 Reviewer」由 `reviewerEnabled:

  - **调度层不累积结果**：十万级块 × 千维向量全留内存就是数百 MB。向量一算出来即经 `onEmbedded` 交给调用方落库，`embedChunks` 只返回统计报告——这也正是断点续传成立的前提（已算的必须已经落盘）。`onEmbedded` 抛出即中止整轮并向上抛：静默继续会让「已算」与「已存」错位，续传从此不可信。
  - **同一轮内重复文本只算一次**：按指纹归并后共用一次请求的结果再扇出到各下标（模板页脚、重复的 README 段落在文件夹导入里很常见）。

## 5. 关键技术事实备忘

- **pnpm 11**：allowBuilds 是「包名: true」映射（数组无效）；安装失败会自动改写 pnpm-workspace.yaml 插入提示行；.npmrc 只承载 auth/registry；`pnpm add` 失败时 package.json 变更会回滚——预装依赖后必须验证包真实存在（T0.5 首派终止的教训）
