## 2. 授权

`ffpane_memory_add` 只看三件事：`sanitizeLocked` 为真则拒绝；否则已授予的管理者，或 `openedBy=user`，可以写。角色名本身不算授权。`isManagerGranted` 还要求注册表里的角色是 manager。

`ffpane_memory_search` 任何窗口都能调。查询只用 `caller.projectRoot`。`projectRoot`、`projectId`、`status` 这些参数不读。

冷启动 `restoreColdLayout` 不会把磁盘上的 manager 放进授予集合。探针用一棵冷读树核对：

| 窗口 | 结果 |
|---|---|
| 顶层、`openedBy=user`、角色 manager | 未授予。因为是用户自己打开且没被锁，按合同可以写 |
| 子窗口、角色 manager、父级还在 | 未授予，`openedBy` 不是 user，不能写 |
| 父级 id 不在树上、角色 manager、权限 yolo | 被清洗锁住，权限降为 read-only，未授予，不能写。即使探针把 `managerGranted` 设成真、`openedBy` 设成 user，锁仍然拒绝 |

仓库单测还看了：普通子窗口拒绝并提示用 `ffpane_report`；被清洗的用户窗口拒绝；已授予的子管理者可以写；甲项目窗口带着乙项目路径去查，实际查的是甲，正文里没有乙的秘密。

主进程 `describe` 在项目能对上 id 时用该项目的 `rootPath`，不用窗口 cwd，也不用工具参数。令牌在 `authRegistry.upsert` 之后签发，正常调用时注册表里有这个窗口。

## 3. 投毒面

写入把 `status` 固定为 `candidate`、`confidence` 固定为 `low`。参数里自带的 `status: "active"` 被丢掉。来源是 `workbench`，带窗口 id、消毒后的标题、角色。时间用 `createdAt`。

旧注入没有改口。`apps/desktop/src/main/session/index.ts` 的 `loadActiveMemory` 仍是 `listEntries(..., { status: "active" })`。`selectMemoryForRole` 仍先丢掉非 active。本单没有改这两处。探针：刚写入的候选不在 active 列表里，规划者选取也选不中；用户侧 `updateEntryStatus(..., "active")` 之后才能选中。交接包 E2E「active 记忆入包 / candidate 不入」本轮仍过。

检索装箱保留 `status` 和完整 `source`。子窗口查到刚写入的候选时，JSON 里是 `status: "candidate"`，`source.kind` 是 `workbench`，标题是消毒后的窗口名。工具说明写了「已生效的和待审核候选」。

**必须修复 ②：** 索引状态和文件状态不一致时，文件说了算，而且不再过滤。探针先按工具路径写入候选并更新索引，再直接把文件改成 archived、不调用 `entrySaved`。下一次 `searchCallerProjectMemory` 仍返回这条，`status` 为 `archived`。合同写的是不含 archived。修法：回读成功后，状态不是 active 或 candidate 就跳过。

有编辑权限的窗口还可以把 `.workbench/memory` 里的 frontmatter 直接写成 active。旧注入读的是文件，不经过这个 MCP。计划 §3.3 已说明 Windows 上不是操作系统级隔离。这不是本工具多开的写入口，本轮不挡；修 ② 也关不住这条。见建议。

## 4. 消毒、上限、频率

标题走 `stripControls` 再去掉换行。正文保留换行，去掉其它 C0 和 DEL，`\r\n` 收成 `\n`。空标题、空正文、`state` 类别拒绝。超长在消毒之后按码点计数：标题 120、正文 2000、查询 200。空白查询拒绝。探针确认 201 个「查」被拒绝。

来源标题同样消毒，最多 80 个码点；空了就写成「窗口」。控制字符不会进来源。`<script>` 这类文字会留下，记忆页用文本节点显示，不执行。

检索最多 20 条。多出来的记 `truncated: true`。标题加正文的 UTF-8 合计不超过 16KB，装不下就截断正文并停下，同样把 `truncated` 设为真。状态和来源字数不占这 16KB，与「标题加正文合计」一致。

逐次调用的 10 秒间隔有单测：没到点拒绝，到点可以再写。失败的空标题不占用间隔。

**必须修复 ①：** 间隔记在写入成功之后。`describe` 和写文件都是异步的，两笔同时进来时，谁都还没记下时间。控制通道 `onRequest` 返回 Promise 后就去读下一条，sidecar 每次工具调用单独连一次管道。探针 `Promise.all` 两笔 `ffpane_memory_add`，两笔都成功。修法：在开始写之前就占住这个窗口的时间；或者同一窗口的添加排队。占住之后写失败，宁可多等 10 秒，也不要让并发双双成功。

## 7. 建议（非阻断）

1. 编辑权限的窗口可以直接改 `.workbench/memory` 下的 Markdown，把 `status` 写成 active。下一轮旧会话会注入。要把「只有用户点通过才进旧注入」做成挡得住文件改写，得把记忆挪出项目可写目录，或给条目做应用签名。那是另一项产品决定，本单合同没要求。
2. 检索对命中的文件整份读入，16KB 只限制返回给模型的标题加正文。本工具新写入最多 2000 字。手改的超大文件仍会先占主进程内存。
3. `base.md` 写了先查、不能写就汇报。工具说明里有「待审核候选」，返回 JSON 里有 `status`。可以在说明书里加一句：`candidate` 还没经过用户确认，不要当成已经生效的规则。
4. 修复 ① 和 ② 时补上对应单测。现有单测只覆盖了把时钟往前拨之后的第二次写入，以及索引和文件一致时的候选。

## 8. 给 Tony 的手动试用（3～5 步）

这两项没修好之前，先不要把「连着猛点添加」当成已经挡住。按下面顺序试用正常路径即可。

1. 打开一个项目的工作台，新建窗口，设成管理者，启动 Claude 或 Codex。让它记一条这个项目的规矩，例如「这个仓库用 pnpm，不要用 npm」。
2. 打开记忆页，切到「候选」。应能看到这条，标签上有窗口名字和角色（管理者）。先不要点「通过」。
3. 让这个管理者再开一个子窗口。子窗口应能查到刚才那条，并看得出还是待审核；让子窗口自己再记一条，应被拒绝。
4. 回到候选，点「删除」，这条应消失。再记一条并点「通过」之后，以后的旧会话才会自动带上它；没通过时不该出现。
5. 同一个窗口写完一条立刻再写第二条，应提示至少等 10 秒。
