> 开发时出的事：Tony 的 FF-pane 跑在开发模式，改界面源码会被开发服务器推进他正在用的界面。06:28（UTC）整页重载了一次（终端都接回，A 随之上线：5 分钟清掉 13910 条、界面 701MB → 169MB），B 是热替换、没重载（之后 5 分钟只清 48 条，界面稳在 170–180MB）。以后改界面源码前先问 Tony。起因见 [主进程卡死与残留清理计划](./主进程卡死与残留清理计划.md) §7.3 第 3 条。

## 1. 现象（`~/.aiworkbench/logs`，11-08 至 11-13）

- 界面进程内存**在团队干活时一直涨，约每小时 0.5–1GB；晚上闲着时不动**。JS 堆（`[renderer-mem] jsHeap`）一直 40–70MB，DOM 节点数稳定。
- 每一份运行的最高值：11-08→11-09 到 12.4GB；11-10→11-11 到 **17.6GB 后界面因内存耗尽崩掉**（`renderer gone: reason=oom`）、自动重载；11-12 上午 10.7GB；11-13 上午 2GB（前一晚刚重开）。
- 11-13 11:33 重开后一小时：133MB → 583MB。

## 2. 查明（11-13 现场 + 隔离复现）

### 2.1 涨在哪

- 现场界面进程（PID 11132）抓内存区域表：569MB 私有内存里 **400MB 在 Chromium 的分配器 PartitionAlloc**，V8 那块只有约 31MB。涨的是 Blink/Chromium 的 C++ 内存，JS 堆看不见。
- 现场抓完整内存 dump 数特征串：React 开发版性能记录的附加数据（`devtools`、`primary-light`、`Changed Props`、`tooltipText`）**各约 43.5 万份**。开了 67 分钟，约每秒 108 条。

### 2.2 为什么

- **只在开发模式**：React 19.2 的开发版（`react-dom-client.development.js` 的 `logComponentRender` 等）每渲染一个组件就调一次 `performance.measure()`，给开发者工具画「性能轨道」，**从不清理**。浏览器把这些记录一直存着。
- 隔离测量：每条约 **800 字节**，全在 JS 堆外；`performance.clearMeasures()` 一调就放掉（10 万条：界面 54MB → 130MB → 清掉后 57MB）。
- 打包后的版本用生产版 React，不记这些。Tony 一直用开发模式（`FF-pane.exe` → `pnpm dev`），所以一直在涨。
- **谁在频繁渲染**：热点是 `Tooltip`、`Popper`、`Primitive.div`，变的 props 是 `children`，还有 `workingSetBytes`、`processCount`、`lastActiveAt`。来源是 `WorkbenchRuntimeBar.tsx`：每 3 秒取一次各窗口状态（内存、进程数、最近活动）。AI 窗口的这些数每次都变，每个窗口标题栏上带提示框的徽章就整组重画。6 个窗口每 3 秒约 300 条，和现场每秒 108 条对得上。

### 2.3 排除了的

- **终端输出过 contextBridge**：4 个窗口单色刷屏 3 分钟（生产版、开发版界面各一次），界面一直 85–150MB，不涨。
- **字形图集**：图集超过 64MB 就整体重装（`webgl-pool.ts`），现场图集一直 1–4MB、没回收过。注：隔离复现时 256 色加随机汉字刷屏会让 xterm 的字形缓存（JS 对象）涨得很快，是另一回事，现场没碰到。

### 2.4 顺带发现：GPU 进程重开后终端不再用 WebGL

- 11-13 11:52 现场 GPU 进程自己崩了两次（`exitCode=34`，原因不明，时间上和我跑 e2e 重合）。之后所有终端 `webgl=0`，用 DOM 渲染撑了半小时，窗口重新挂载才恢复。
- 原因：`webgl-pool.ts` 的 `onContextLoss` 只卸掉 WebGL，不再装回去。1.0.32 自动结束 GPU 进程后也会这样。

## 3. 改法（待 Tony 定）

- **A. 开发模式定期清性能记录**（治本，几行）：界面在开发模式下每 5 分钟（和现有内存日志同一个定时器）调 `performance.clearMeasures()`、`performance.clearMarks()`。开发者工具录性能时是实时抓的，不受影响。`[renderer-mem]` 里加上清掉的条数，以后看得见。
- **B. 少重画**（两种模式都省 CPU）：运行状态每 3 秒取回来后，和上一份一样的窗口不更新；徽章只订阅自己那个窗口的状态，内存数按显示精度（如 0.1GB）取整后再比。
- **C. GPU 进程重开后装回 WebGL**：`onContextLoss` 后隔一会儿（如 2 秒）重新装；一分钟内连着丢 3 次就不再装（GPU 真坏了时退回 DOM 渲染）。
- **D. 现场临时办法**：在 A 上线之前，团队空闲时重开 FF-pane，内存就回到几百 MB。

建议顺序：A → C → B。A、C 各是几行，B 要动运行状态的数据流，稍大。

## 4. 验收

- A：开发模式开着团队干活 1 小时，界面进程内存不再按小时涨；日志里每 5 分钟有清掉的条数。
- B：开发版界面数性能记录，6 个 AI 窗口时每 3 秒新增的条数明显少于现在的约 300 条。
- C：手动结束 GPU 进程后 10 秒内日志 `webgl=` 回到终端数。
