## 2. 抽查发现

**未发现影响结论的缺陷，红线全部未破。** 以下如实登记：

1. **（设计观察，不影响结论）server 层 close() 等 launch 落定无自身上限，卡死风险由两层外部机制兜住。** `server.ts:526-529` 的 `await pending` 无 race 超时；不卡死的保证是 ① launch 内部 `readyTimeoutMs`（默认 60 s）deadline 贯穿地址解析与健康检查、三种失败形态都有出口，② 退出路径的 1 s 预算把 close 包住、超时照样 quit、进程由 Job Object 收尾。语义正确（退出场景预算兜底覆盖），但若将来有**非退出路径**调 close()（如切 Profile），starting 期最长可等 60 s——届时若成为体感问题可给 close 加自身上限。仅登记备查。
2. **（覆盖口径观察，不影响结论）`QUIT_RUNTIME_CLOSE_BUDGET_MS = 1000` 的数值本身无用例钉住。** 超时路径用例经 `runtimeCloseBudgetMs: 50` 注入观察（`session-quit.test.ts:239-252`），缺省常量改成 0 或 10000 都不会红（探针④证实）。机制（缺省常量真被消费、超时分支可达）经本验收临时探针核实为真；数值是「实测 3 倍裕量」的工程判断，钉死数值的单测价值不大——如实登记不建议补。
3. **（正面观察）零 env 注入前提有双层钉子。** `env.ts` default 分支注释钉住理由 + `session-env.test.ts:30` 单测钉住 `runtimeApiKeyEnvVar("opencode") === undefined`——将来为 opencode 加按 Profile 凭证注入（主管理员裁定①的场景）时会先撞红该单测，届时 registry 头注的「再改按 Profile 实例化」退路指引就在改动现场。前提不是口头约定。
4. **（正面观察）「先 prepare 后 close」的理由链读码闭合。** 不止注释声称：`adapter.ts:191-196` 确有「abort 调不通 → server.restart()」的兜底路径，先关 server 确会触发退出期间重启的反向操作——顺序约束防的是真实存在的机制，非假想。
5. **（回归 flake 登记，复跑排除）全量第 2 跑 1 例失败：`opencode.test.ts`「env 指纹变化：无活跃轮次时自动重启，有活跃轮次时拒绝抢占」（该文件耗时 12.2 s，明显负载性）。** 单独复跑该文件即绿（36/36），随后两次全量亦绿。不在已知 flake 三条名单内（generic-exec cancel / task-parallel 第 3 条 / 全量首跑不明异常），但形态同款（负载性、复跑即绿）——按「触发则复跑绿即登记」处置，建议并入 §4.5 观察名单（opencode server 生命周期用例走真子进程 + 定时器，负载下健康检查时序敏感）。
