## 2. 抽查发现

**未发现功能缺陷，未发现红线被绕开。** 以下如实登记：

1. **（交付报告数字勘误，不影响结论）locales 增量实为 zh/en 各 +9 键，非报告所称 +10。** 脚本对比 `d2312e1` 与 HEAD 叶子键集合：新增 `settings.profiles.genericExec.*` 9 键，zh/en 新增集合逐键相等、全量 656=656 parity 无恙。纯计数错误（与 T8.4 的 +22→+17 同类），建议落档时顺手勘误。
2. **（单测覆盖缺口，不影响结论但建议补钉）「配置变更指纹重建」单测只覆盖 command 一维。** 探针①证实：指纹削去 `taskDelivery`（乃至只剩 `command`）后 `session-registry.test.ts` **15/15 仍绿**——若未来有人重构指纹时漏掉 args 或 taskDelivery，现有单测拦不住，会复现「改了配置但复用旧实例」。当前实现三字段全收（`registry.ts:157`）、功能无恙；缺口在测试而非产品。建议补一条参数化用例（改 args / 改 taskDelivery 各断言重建）。
3. **（边界观察，量级极小）displayName 不进指纹：** `resolveGenericExec` 把 `profile.name` 作为 displayName 传入构造（`registry.ts:166`）但指纹只含 command/args/taskDelivery——只改 Profile 名而不改命令配置时，缓存实例的 displayName 保持旧名。displayName 当前无任何生产消费方（全仓 grep：仅 adapters 自家单测断言），无用户可见影响；如未来 UI 开始显示 adapter.displayName 需连带考虑。备查，不立项。

## 3. B 项独立评估：指纹完整性与「不挂删除钩子」取舍

### 3.1 指纹完整性

`GenericExecProfileConfig` 全部 3 字段（command / args / taskDelivery）逐一核对进指纹（`registry.ts:157`）——**实现完整**，不存在「改了配置但复用旧实例」的字段遗漏。指纹外的两项：`displayName`（§2-3，非功能配置）；aider 的 `tempDir`（指纹本身，由 profileId 派生恒定，`agentSessionsDir` 为进程内常量——闭包捕获，重启前不变，重启后缓存清空，恒定性成立）。**单测覆盖有缺口**（§2-2）：重建路径只钉 command 变更。

### 3.2 不挂删除钩子的取舍（逐层核实）

1. **generic-exec 实例无 OS 资源**：`createGenericExecAdapter`（`generic-exec/adapter.ts:315-332`）返回值是 `{ runtime, displayName, capabilities, startTurn }` 纯闭包——构造期只做 `validateGenericExecConfig`（纯逻辑）+ 字符串拼接，**零 IO、零句柄**；spawn 在 `startTurn` 内、进程句柄住轮次闭包。属实。
2. **aider 实例的 tempDir 只是路径字符串**：`createAiderAdapter`（`aider/adapter.ts:468-475`）同样纯闭包；`options.tempDir` 仅在 `startAiderTurn` 里参与 `path.join`（`:239-241`），目录创建（`mkdirSync`）在 startTurn 的轮次路径里按需发生（`:338`）——**构造期不 touch 文件系统，无句柄**。读 adapter 构造函数确认属实。
3. **删除后新派发已被挡**：编排器受理入口 `loadProfile` 查无即 `{ accepted: false, reason: "Profile 不存在" }`（`orchestrator.ts:610-613`）——被删 Profile 的缓存条目不可能再被 `resolveForProfile` 触达（调用点唯一，`:616`，其前置就是 loadProfile 成功）。
4. **残留量级**：缓存条目 = `{ fingerprint: string, adapter: 闭包 }`，数量上界为进程存活期内出现过的 generic-exec / aider Profile 数（现实个位数），每条几 KB 级 JS 对象；重启即清。
5. **对照代价**：挂钩子需 data 层（profiles:remove handler）跨到 session 层（registry 实例）新增通知通道，或让 storage 回调注册表——两层现无依赖边，为清理几个无资源闭包引入新耦合。

**评估结论：取舍成立。** 残缓存条目确无 OS 资源（两类实例均核实为纯闭包），aider 的 tempDir 只是字符串无句柄；「复杂度与收益不成比例」的论证在读码后站得住。
