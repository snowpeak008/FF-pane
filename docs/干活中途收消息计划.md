# 干活中途收消息计划（T11.7）

> 状态：Tony 2026-11-07 提出并说开工。Claude 窗口已提交 1.0.24；Codex 窗口 2026-11-28 补完（见 §7），尚未真机验收。总览见 [`改进计划总览-2026-10.md`](./改进计划总览-2026-10.md)。

## 1. 起因

Tony 看 dsh-superagent 的介绍视频，问能不能「临时插入消息阅读」：agent 正在干活时来了新消息，下一步就能读到，不用等这一轮干完。

我们原来的做法：消息一律等窗口这一轮结束、空闲了，才往终端里打字投递（`idle-deliver.ts`）。管理者发一句「停，做偏了」，执行要把手上这一轮做完才看得到。

查了本机装的两个 CLI 本身支持什么：

- **Claude Code 2.1.302**：PostToolUse / PostToolUseFailure hook 可以返回 `hookSpecificOutput.additionalContext`，模型下一步就能看到。2026-11-07 用 `claude -p --model haiku` 实测过：hook 在 Read 之后插了一句带暗号的话，模型在回答里原样复述了暗号。
- **Codex 0.166.0**：hooks 已是稳定功能，PostToolUse 也有 `additionalContext`。但只靠启动参数启用 hooks 要加 `--dangerously-bypass-hook-trust`，这个参数会让用户自己配置的、项目目录里的 hooks 也一起免审核运行。

## 2. 已定的事

- 不往终端里打字：走 hook 的附加上下文，所以和「输入框有字就不投递」不冲突。
- 只插上级和用户本人（「待你拍板」点的选项）的消息。下级汇报、平级消息照旧等这一轮结束再提醒，免得打断。
- 未读全是该插的：把正文插进去，读出即标记已读，空闲时的提醒随之撤掉。未读里还夹着不急的：只插一句「谁发来几条，做完这一步先读收件箱」，不标已读（收件箱游标只能整体往前走，不能只标一部分）。
- 同一批只说一次：最新那条该插的消息没变，就不再说。
- 每调用完一个工具问一次，CLI 等着 hook 退出，所以只等 800ms，取不到就算了，这一轮结束还有原来的提醒兜底。
- Codex 先不做（§5）。

## 3. 代码

- 新模块 `main/workbench/mid-turn-inbox.ts`（纯函数）：`planMidTurnInbox(unread, lastAnnouncedId)` 返回不插 / 插正文 / 插一句提示。
- `mcp-tools.ts` 的 `takeMidTurnInbox`：读未读，按「用户本人或上级」分类，插正文时复用 `takeInboxDigest`（标已读、撤提醒）。
- `handlers.ts`：控制通道新请求类型 `inbox-midturn`，按窗口记上次插过的那条（只放内存）。
- `mcp/workbench-hook.ts`：PostToolUse / PostToolUseFailure 上报之后请求 `inbox-midturn`，有内容就输出 `additionalContext`。
- 只对用 `--settings` 装了我们 hooks 的 Claude 窗口生效（含 DeepSeek 窗口，它跑的是 Claude）。

## 4. 限制

- 只在工具调用之间生效。窗口在跑一条很长的命令、或者一直在想不调工具，就得等那一步结束；这时仍靠原来的空闲提醒。
- 插的是正文时已标记已读；模型如果没理会，平台不会再提醒同一批。

## 5. 待定：Codex

要做的话：启动时用 `-c` 传 hooks（PostToolUse 指向同一个 hook 脚本），并加 `--dangerously-bypass-hook-trust`。代价是这一次启动里，用户在 `~/.codex` 里自己配的 hooks、项目目录 `.codex/hooks.json` 里的 hooks 也都免审核运行，打开别人的仓库时有风险。另外 Codex hooks 的 TOML 写法要实测。等 Tony 定做不做。

## 7. Codex 部分（2026-11-28 补完，Tony 定「11.7 也要补完」）

**实测结论**（本机 codex-cli 0.166.0，argv 里用 `-c` 传内联 hooks，测试目录在 `test-results/scratch/codex-hook-probe/`）：

- 内联写法是 `-c 'hooks.PostToolUse=[{hooks=[{type="command",command="…",timeout=10}]}]'`，和 Claude 的 `hooks` 结构一样是「事件名 → 分组 → hooks 数组」；`--strict-config` 下写错字段名会报 `config could not be loaded`，正确写法正常加载。
- `PostToolUse` 的输入是 Claude 形状的 JSON（`session_id`、`tool_name`、`tool_use_id`、`tool_input`），输出是 `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"…"}}`，与 Claude 相同，`inboxHookOutput` 直接复用。
- **命令串走 PowerShell**：必须写成 `& "node.exe" "脚本" CodexPostToolUse`。同一个 hooks 分组里放两条（一条带 `& `、一条不带），同一次运行只有带 `& ` 的被执行；不带的那条静默失败。
- **不带 `--dangerously-bypass-hook-trust`，内联 hooks 根本不运行**（实测没有任何调用记录）。所以要么带这个参数，要么这个功能不存在。

**代价与处置**：`--dangerously-bypass-hook-trust` 会让本次启动里用户在 `~/.codex` 和项目 `.codex` 里自己配的 hooks 也免审核运行。本机核查过：用户 `config.toml` 里没有自定义 hooks，只有两个自带插件（browser、computer-use）在 `Stop` 上挂了 `mcp_tool` 型钩子，指向用户配置里的 `node_repl` MCP server。Tony 2026-11-28 已同意补完，按计划 §5 的原方案带这个参数，默认打开。

**代码**

- `hook-launch.ts` 的 `codexMidTurnHookConfig(nodePath, scriptPath)` 产出 `hooks.PostToolUse` 的值。
- `cli-args.ts` 的 `buildInteractiveCodexArgs` 加 `extraConfig`（排在所有 `-c` 之后）和 `bypassHookTrust`。
- `launch-cli.ts` 的 Codex 分支在有 `notifyArgv`（即找到 node）时一并传这两样。
- `workbench-hook.ts` 加 `CodexPostToolUse` 分支：只问中途消息、插 `additionalContext`，**不上报**——Codex 的回合信号仍由 `notify` 负责，免得改变现有的状态判断。

**测试**：`codex-mid-turn.test.ts` 2 条；`workbench-cli-args.test.ts` 加 1 条（内联 hooks 排最后、免审核参数单独一个、开场白仍在末尾）。

**真机验收要看的**：Codex 窗口干活时发一条上级消息，它在下一个工具调用后就能看到；关闭窗口后没有残留；用户自己配了 hooks 的项目里，确认这些 hooks 免审核运行是否符合预期。
