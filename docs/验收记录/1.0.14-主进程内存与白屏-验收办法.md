# 1.0.14（T11.0d）主进程内存与白屏：改动与验收办法

**日期：** 2026-10-27
**状态：** 已提交（2026-10-27，版本 1.0.14），尚未验收。
**计划：** [主进程内存与白屏修复计划.md](../主进程内存与白屏修复计划.md)（崩溃记录、代码排查都在里面）

## 1. 实测：同一份画板，改前和改后

用《海上生存日记》画板的副本（3927 个文件、1.7GB，`board.json` 6264 行；复制到 `test-results/canvas-sandbox/`，原项目只读），两份构建都是 `electron-vite build` 的产物，同一个脚本（`test-results/scripts/measure-canvas.mjs`）：打开画板，等 30 秒，把缩略图区从上滚到底，再连着点开 20 张大图，关掉画板。

| | 改前（1.0.13） | 改后（1.0.14） |
|---|---|---|
| 打开前 | 主进程 140MB，界面 64MB | 主进程 142MB，界面 63MB |
| 打开后 5 秒 | **主进程 3150MB**，界面 1551MB | 主进程 157MB，界面 253MB |
| 打开后 20 秒 | 主进程 883MB，**界面 6701MB** | 主进程 157MB，界面 253MB |
| 之后 | 界面卡死，脚本连缩略图区都找不到了（就是 Tony 看到的白屏） | 滚完全部缩略图、看完 20 张大图：主进程最高 240MB，界面最高 747MB |
| 第一张缩略图出来 | 787ms | 729ms |

改前打开画板几秒内主进程就到 3GB、界面到 6.7GB，和崩溃记录里主进程峰值 3.2–4.7GB 对得上。

## 2. 改动

### 画板读图（主因）

- 新协议 `ffpane-canvas://`（`shared/canvas-image-url.ts`、`main/workbench/canvas-thumbs.ts`）：界面 `<img>` 直接取文件，不再整张转 base64 经 IPC 传。删掉 `workbench:read-canvas-image` 和 `readCanvasImageBytes`。CSP 的 `img-src` 放行这个协议；回包带 `access-control-allow-origin: *`，带标记预览把原图画进 canvas 后照样导得出来。
- 缩略图：Electron 的 `nativeImage.createThumbnailFromPath`（系统缩略图，不在主线程解码；本机实测每张 40–170ms），长边 256，存 PNG（游戏素材常带透明）。一次最多做 4 张，同一张同时要只做一次。**缓存放在 `~/.aiworkbench/cache/canvas-thumbs/`，不写进项目**（计划里原写放项目 `.ffpane/`，改了：不弄脏项目，AI 窗口也看不到）。文件名带原图路径和修改时间，原图变了自动重做。实测每张 30–65KB。
- 缩略图懒加载（`loading="lazy"`），滚到哪取哪；原图只在大图里取。
- 计划里的 1024 一档没做，留给无限画布（T11.0c）。

### AI 出图不弹画板

- `ffpane_generate_image`、`ffpane_open_canvas` 不再发 `workbench:open-canvas`（事件删掉），只放进画板。画板按钮变成「打开画板（新图 N）」；打开画板就清零。
- AI 直接往 `.ffpane/canvas/` 存的图（目录监听收进来的）也算新图。只算真新加的：出图时目录监听和放图谁先收进来都只记一次。
- 工具说明改成「不会在用户界面上弹出画板」。

### 画板去重

- `placeImageOnBoard`：图已经在画板上就不再加行；要挂到别的行当新版本时从原来那行挪过去（标注、附注留着）。
- 读到重复行时在内存里合并（留第一次出现的），**原 `board.json` 先原样复制成 `board.before-dedupe.json`（只留第一次的，不覆盖）**，下一次写画板时写回合并后的。《海上生存日记》开 FF-pane 1.0.14 后第一次改画板时会从 6264 行变成 3911 行。

### 减少反复的大块读写

- 终端输出缓冲（`terminal/ring-buffer.ts`）：输出拷进 64KB 的连续块，不再每段留一个小 Buffer（小 Buffer 来自 Node 共享的 8KB 池，几十字节的转圈输出能占住整块池）。截断规则不变。
- 提示符检测和 `ffpane_read_output`：新增 `getReplayTail`，只拷最后 256KB，不把整份 1MB 拼成字符串再截；结果和原来逐字相同（单测对比）。
- 团队消息索引 `readThreadIndex`：按文件缓存，没变直接用，只往后追加时只读新加的部分；变短或开头变了整份重读。
- 画板：清临时文件同一项目 10 分钟一次（原来每次打开画板都列一遍几千个文件）；目录监听同一文件 300ms 内的多次事件合并成一次；有标注的图只读文件头拿宽高（原来每次写画板都整张读）。
- 提示符检测：`observe()` 读过、从没进过检查的终端关掉后也清缓存。
- 计划里「终端输出推送加背压」**没做**：要给界面加确认收到的通道，改动面大；这次实测和崩溃记录都指向画板，先看 1.0.14 的日志再定。

### 先能看见、出事了兜底（`main/diagnostics/`）

- 日志：主进程的 console 同时写 `~/.aiworkbench/logs/main-YYYY-MM-DD.log`，保留 7 天。启动第一行写版本、日志目录和崩溃 dump 目录。
- 每 5 分钟（启动后 1 分钟第一次）记一行内存：主进程 rss / 堆 / external / arrayBuffers，界面进程、GPU 进程，终端数和回放缓冲总量。
- 主进程 JS 堆第一次超过 1.5GB 写一份堆快照到日志目录（只留最近 2 份）。
- Electron 自带的崩溃记录打开（只存本机、不上传），以后崩了有带进程类型的 dump。
- 界面进程没了：记日志、自动重新加载；一分钟内第 4 次起不再重载，弹框「再试一次 / 关闭 FF-pane」。终端在主进程里，不受影响。
- 界面卡住 30 秒：弹框「重新加载界面 / 继续等待」。
- 子进程（GPU 等）没了记日志。
- 主进程超过 2.5GB 或界面进程超过 2.5GB：内容区顶上一条提示「建议找个空档关掉重开，窗口会续接」，可以点「知道了」。
- 只开一份：`requestSingleInstanceLock`，再启动时新的一份直接退出，原来的窗口切到前面。冒烟自检不拿锁。
- 关窗退出 5 秒还没退干净就强退（记日志）。
- 判断规则是纯函数 `main/diagnostics/policy.ts`。

### 说明

- `使用说明.md`：画板不再弹出、按钮上的新图数、缩略图缓存位置；只能开一份、界面崩了自动重载、日志位置。

## 4. 验收办法（《海上生存日记》真项目，dev 模式）

先关掉 FF-pane 再用 FF-pane.exe 打开（主进程改了，热更新不够）。

| # | 做法 | 应该看到 |
|---|---|---|
| 1 | 打开画板，滚到底，点开几张大图 | 很快出缩略图；任务管理器里 FF-pane 的内存不再冲到几个 GB |
| 2 | 让执行窗口出一张图 | 画板不弹出、页面不切；按钮变成「打开画板（新图 1）」；打开后变回「打开画板」 |
| 3 | 在画板上改一处（比如标一张「不要」） | `.ffpane/canvas/` 里多一个 `board.before-dedupe.json`；画板里同一张图只出现一次 |
| 4 | 已经开着 FF-pane 时再双击 FF-pane.exe | 不多开一份，原来的窗口切到前面 |
| 5 | 看 `~/.aiworkbench/logs/` | 有当天的 `main-日期.log`，每 5 分钟一行 `[memory]` |
| 6 | 照常带团队跑一天 | 不再白屏；如果出了提示或崩了，把当天日志和 `[memory]` 几行给我 |
