## 0. 2026-11-20 重新量（只读，没关任何进程）

当时 FF-pane 是 1.0.33 dev 模式，已经连着跑了 29 小时，开着 9 个窗口：6 个 Claude、3 个 Codex。下表按进程树归属统计，数字是私有内存（提交量）。任务管理器默认显示的「内存」是私有工作集，会更小一些，但各部分的比例差不多。

| 部分 | 私有内存 | 占比 | 说明 |
|---|---|---|---|
| 6 个 Claude CLI（`claude.exe`） | 约 4.0GB | 约 59% | 每个 580–880MB。对话记录 1–2MB 的窗口也有 580MB；对话记录 71MB 的管理者是 884MB |
| 3 个 Codex CLI 和它们的子进程 | 约 1.25GB | 约 18% | `codex.exe` 190–545MB；外加 Codex 桌面版插件带出来的电脑操控进程（`cua-repl`、`node_repl`、`code-mode-host`，每个窗口约 40MB、4–6 个进程），以及一层 `node codex.js` 外壳（23MB） |
| FF-pane 主进程 | 834MB | 约 12% | **工作集只有 198MB，JS 堆 44MB 加 external 49MB，另外约 700MB 的原生内存查不到来源。** 5 分钟的内存日志只记了 rss，没记私有内存，所以看不出它是不是一直在涨 |
| FF-pane 界面 + GPU | 283 + 234MB | 约 8% | 1.0.33 之后已经稳定 |
| 9 个工作台 MCP 小进程 | 约 190MB | 约 3% | 每个窗口一个 `electron.exe`（以 node 模式跑 `workbench-mcp.js`），私有 21MB，工作集最多 86MB |
| 合计 | **约 6.8GB** | | dev 专用的 pnpm、electron-vite 另占约 0.5GB，打包版没有 |

另外看了一周的内存日志（`~/.aiworkbench/logs`，每 5 分钟一行，记的是工作集）：开着 10–12 个窗口时，FF-pane 自己的主进程、界面、GPU 三个加起来平均约 1.0–1.1GB，最高 2.07GB。界面进程超过 900MB 的情况只出现在 11-13（1.0.33 修复之前）和 11-16 下午。

**结论：**

1. **任务管理器会把 FF-pane 开出来的 CLI 都算到 FF-pane 名下。** 「FF-pane 占得最多」里大约四分之三其实是 Claude 和 Codex 进程，FF-pane 自己约占四分之一（约 1.5GB）。
2. **Claude Code 一启动就有约 600MB**，对话越长占得越多。这是它自己的进程，FF-pane 改不了，能做的只有**让同时活着的 CLI 少一点**，也就是 §3 的空闲窗口休眠，收益最大。
3. FF-pane 自己还有三处能省：主进程有一大块原生内存来源不明；每个窗口都多开一个 MCP 进程；Codex 窗口带着桌面版的电脑操控插件，还套了一层 node 外壳。

### 0.1 推荐做法（按收益排）

| # | 做什么 | 10 个窗口（4 个在忙）大约能省 | 风险 / 工作量 |
|---|---|---|---|
| A | **空闲窗口休眠**（§3）和**开窗时先休眠再开**（§4）：空闲超过 15 分钟的窗口结束 CLI 进程，窗格、会话编号都留着；有消息投给它、用户点它或在里面打字时自动续接 | **3–4GB**（6 个空闲窗口 × 约 600MB） | 中。续接、投递核对都是现成的；难点是判断「真空闲」，条件见 §3.1 |
| B | **查主进程那约 700MB 原生内存**：先在 5 分钟日志里补上各进程的私有内存（`app.getAppMetrics()` 的 `memory.privateBytes`）；如果一直在涨，就照 T11.14 的办法做两份现场 dump 对比，找出是哪个分配器在涨 | 0.3–0.6GB（猜的，要量了才知道） | 低。第一步只加一行日志 |
| C | **Codex 窗口减负**：给 FF-pane 的 Codex 窗口用 `-c` 关掉电脑操控这类桌面版插件（不改 `~/.codex/config.toml`）；直接启动 `codex.exe`，不再经过 `node codex.js` | 每个 Codex 窗口约 60MB、5–7 个进程 | 低。要先问 Tony：FF-pane 的 Codex 窗口要不要用电脑操控 |
| D | **MCP 改成共用一个**：主进程开一个本机 HTTP 端口，所有窗口连这一个，按令牌区分窗口，不再每个窗口开一个小进程 | 约 200MB、10 个进程 | 中到高。四种 CLI 都要支持 HTTP 方式的 MCP；`ffpane_wait_events` 一次挂 9 分钟，长连接超时要实测。放最后，或者不做 |

- 继续压界面和 GPU：1.0.33 之后两个加起来约 0.5GB，再压也省不了多少。
- 换技术底层：理由同 [主进程内存与白屏修复计划](./主进程内存与白屏修复计划.md) §6。这次量出来，大头是 CLI 进程，换什么底层都省不掉。

做完 A、B、C 后，10 个窗口（4 个在忙）预计从约 6.8GB 降到 3–3.5GB。

### 0.1b 和 CC-Panes 对比（2026-11-20，读 `test-results/ref/cc-pane` 的代码和文档，a313dd1，0.12.21）

Tony 看到别人用 CC-Panes 开十几个 CLI 窗口，内存看起来不高。本机没装 CC-Panes，下面是从它的代码和它自己的测量记录读出来的：

- **它的 CLI 进程挂在另一个后台进程下面。** CLI 进程的父进程是 `cc-panes-daemon.exe`，不是界面进程（`cc-panes-core/src/pty/mod.rs`，`src-tauri/src/lib.rs:2197-2232`，进程链记在它的 `docs/71-multi-pane-resource-contention.md:118-125`）。这个后台进程没有窗口，所以任务管理器把它和所有 `claude.exe` 列在「后台进程」里，不算到 CC-Panes 头上。**看起来小，主要是统计归属不同。**
- **CLI 本身一样占内存。** 它自己的记录：开 17 个 `claude.exe` 时整机用了 57.1/93.6GB（docs/71:141）；另一次出了重复启动的 bug，50 个 `claude.exe` 约 19GB（`docs/61`:7）。它也没有空闲 CLI 休眠：「Tier3 进程级休眠」写着「记录不实施」（`docs/78`:293-295），也不限制同时开几个。
- **界面也不轻。** 它记过：界面进程 3.8GB（14 个标签跑 3 天）、压力测试峰值 3.2GB，后来降到 280–790MB。FF-pane 现在是 0.3–0.5GB。
- **值得学的有两点：**
  1. MCP 是**主程序里共用一个 HTTP 服务**，Claude 用 `--mcp-config` 写 `url`，Codex 用 `-c mcp_servers.<名>.url=...`（`claude.rs:307-321`，`codex.rs:399-413`）。这说明 §0.1 的 D 在 Claude 和 Codex 上可行，长挂的调用怎么处理，可以照它的做法。
  2. 看不见的终端 1 秒后撤掉 WebGL，30 分钟后把画面存下来、销毁 xterm（`terminalBackgroundLifecycle.ts:21-22`）。FF-pane 切走的页面本来就卸载终端，这一条收益不大。
- **一个疑点：** 按它的记录，平均每个 `claude.exe` 约 380MB，FF-pane 这边是 580–880MB；本机在 FF-pane 外面单独开的 Claude 也只有 428MB。可能和 FF-pane 给 Claude 加的东西有关（技能目录 `--plugin-dir`、hooks、MCP 工具说明），也可能只是对话长短和版本不同。要实测：同一个版本，空着不发消息，比较裸启动和带 FF-pane 参数启动的内存，各加一项看差多少。记为 §0.1 的 **E**，排在 B 后面，量完再定改不改。

### 0.1c Tony 的反馈和整机内存（2026-11-20）

- **Tony：空闲休眠在实际开发中改变不了什么。** 卡的时候是十几个窗口同时在干活，没有空闲窗口可以休眠。A 先放下，不做。
- Tony 之前在 Cursor 里同时跑三十多个才把内存跑满。要先问清楚跑的是 Cursor 自带的 agent 对话，还是 Cursor 终端里的 Claude Code：
  - Cursor 自带的 agent 对话：模型和对话的主体在 Cursor 的服务器上，本机所有对话共用编辑器的一套进程，每个对话只多几十 MB。Claude Code 每个窗口是一个完整的独立程序：自己的运行时、整份程序代码、终端界面、整段对话都在内存里，所以要 400–900MB。这是两种产品结构的差异，FF-pane 改不了。
  - Cursor 终端里的 Claude Code：进程和 FF-pane 里的一样。那差别就在每个 Claude 的大小（单独开约 430MB，FF-pane 里 580–880MB），查 E。
- **同一时刻的整机内存：** 31.8GB 物理内存只剩 7.1GB，提交量 56.7/68.4GB。FF-pane 整棵进程树约 7GB，其余是：
  - Unity 11.6GB；
  - **28 个 `explorer.exe`（`/factory,{75dff2b7-…} -Embedding`），共 6.5GB，其中 26 个没有窗口**，每个约 170MB。启动时间：11-03 两个、11-07 九个、11-14 20:36–20:39 三分钟里连着起了 16 个、11-18 一个。都是 COM 拉起的，有程序在「打开文件夹」，用完不退。后来查了（2026-11-20）：
    - 这是 Windows 的「单独进程的文件夹窗口宿主」（`CLSID_SeparateMultipleProcessExplorerHost`）。每个都加载过 WPS、搜狗输入法、百度网盘、OneDrive、Adobe 的右键菜单 / 图标扩展，有 60 多个线程、2000 个句柄，说明它们当时确实开过文件夹窗口；窗口关了，进程却没退。最可能的原因是这些第三方扩展占着不放，没有当场证实。
    - **和 FF-pane 无关：** 都是你自己账户下由系统 COM 拉起的，不是 FF-pane 的子进程。FF-pane 只有两处会打开文件夹或文件（技能目录、`.ffpane` 文件），都要手点。画板缩略图用的 `createThumbnailFromPath` 实测不会拉起它（`test-results/scratch/thumbtest`）。
    - 那一时段的 agent 记录里也没有打开文件夹的命令。11-14 20:36 那一批正好是 Steam 和 Wallpaper Engine 第一次启动的时候（系统日志 20:36:17 装上了 Wallpaper Engine 服务），11-03、11-07 的还对不上来源。
    - 2026-11-20 经 Tony 同意，结束了 26 个没有窗口的（只结束 `/factory,{75dff2b7…}` 且没有窗口的）。桌面和两个开着的文件夹窗口没动。之后整机提交量是 48.0/67.8GB。
  - `asus_framework` 8 个进程 4.5GB（华硕的后台服务）。
  - 结论：开十几个窗口时卡，不一定是内存满了；整机内存有一大块被 FF-pane 以外的东西占着。卡的那一刻要当场量一次，分清是内存满、CPU 满还是界面渲染忙。

### 0.1d Electron 是不是根本原因（2026-11-20）

Tony 找了几个人验证，认为根本原因是 Electron，换成和 CC-Panes 一样的 Tauri，FF-pane 自身的内存会少很多。实测拆开 FF-pane 自身约 1.5GB 的私有内存：

| 部分 | 私有内存 | 换成 Tauri 后 |
|---|---|---|
| Electron 框架本身（实测：空白 Electron 应用，主进程、GPU、网络、页面四个进程，`test-results/scratch/emptyelectron`） | 175MB | WebView2 也是 Chromium，同样有主进程、GPU、页面进程，大约省几十到 100MB |
| 界面里的内容（xterm.js、React） | 约 280MB | 一样。CC-Panes 也是 xterm.js 加 WebGL，它记过界面进程到 3.8GB |
| GPU 里的终端画面（WebGL） | 约 230MB | 一样 |
| 主进程里我们自己的东西 | 约 830MB | Rust 写会小一些。但空白 Electron 主进程只有 69MB，多出来的约 700MB 是异常，不是 Electron 天生的（§0.1 B），在 Electron 里查也能省 |
| 每个窗口一个 MCP 小进程 | 约 190MB | 这是我们自己的设计。CC-Panes 用一个共用的 HTTP 服务，Electron 里也能这么做（§0.1 D） |

结论：Electron 自己的固定开销约 175MB，换底层最多省掉其中一部分。FF-pane 自身多出来的部分主要来自 B 和 D 两处，在 Electron 里修了就能从约 1.5GB 降到约 0.6–0.7GB，和换 Tauri 的效果差不多。换底层要把主进程全部用 Rust 重写，是几个月的工作量。10 个窗口时整机的大头仍是 CLI，约 5GB，换什么底层都不变。

建议用同一把尺子比一次：在测试目录装 CC-Panes，两边各开 10 个空闲 Claude 窗口，把所有相关进程都加上（CC-Panes 要算它的主程序、后台进程、WebView2 和 Claude；FF-pane 算整棵进程树）。

### 0.1e 主进程那约 700MB 查清了：node-pty 每结束一个终端就漏一个工作线程（2026-11-20）

- **现场：** 给主进程（pid 40212，已跑 35 小时）拍了只记内存分布的快照（`test-results/scratch/mem/mainA.dmp`，分析脚本 `analyze.py`、`threads.py`）。私有内存 943MB，其中 **62 个名为 `WorkerThread` 的 Node 工作线程**，每个的 4MB 栈全部提交，共 249MB；每个工作线程还有自己的 JS 引擎，V8 那块 4GB 预留里提交了 226MB，而主线程的 JS 堆只有 44MB。FF-pane 自己的代码只开一个工作线程（看门狗）。
- **原因：** `@lydell/node-pty` 1.2.0-beta.15 在 Windows 上给每个终端开一个工作线程读输出（`windowsConoutConnection.js`）。用 conpty.dll 模式（FF-pane 默认，`terminal/factory.ts:39`）时：CLI 自己退出，`_$onProcessExit` 什么都不做；被 `kill()`，要等之后再来一次输出才 `dispose()`，通常等不到。所以**每个结束过的终端都永久留下一个工作线程**。开着的约 11 个终端是正常的，其余约 51 个都是漏的。
- **复现**（`test-results/scratch/ptyleak/leak.cjs`，单独脚本，用 FF-pane 同一个 node-pty）：起始 12 个线程、19MB；20 个终端自己退出后 29 个、261MB；再 20 个后 49 个、477MB；再 20 个被结束后 69 个、695MB。**每个结束的终端漏约 11MB。** 窗口开得越多、重启得越多、跑得越久，漏得越多。
- **修法已验证**（`fix.cjs`）：终端退出约 1.5 秒后，手动结束它的输出工作线程（`pty._agent._conoutSocketWorker._worker.terminate()`）。同样跑 40 个终端，线程数回到 9 个，内存 19 → 33MB。正式做法：在 `terminal/factory.ts` 的退出和结束路径上补这一步，并做成 pnpm patch 或包一层，不散在业务代码里。再查一下 node-pty 上游有没有修。
- **修完的效果：** 主进程从约 830MB 回到约 150–250MB，且不再随运行时间增长。开着的终端每个仍要一个工作线程（约 11MB，10 个约 110MB），这是 node-pty 在 Windows 上的设计。
- 临时办法：重启 FF-pane 就能放掉漏掉的部分。重启前要先确认团队没有在跑后台长任务。

### 0.1f 有人建议「改用 Tauri + portable-pty」（2026-11-20）

这个建议的判断是：FF-pane 重在 PTY 和子进程，不在界面；建议改用 Rust 的 portable-pty，重点优化 PTY、MCP、知识库三块。我的评价：

- **方向对了一半：** 问题确实在 PTY 这一层，§0.1e 就是。但这是 node-pty 的一个具体 bug，十来行就能补上，不需要为它换语言、换框架。
- **portable-pty 比 node-pty 多省的：** 开着的终端每个约 11MB 的工作线程（portable-pty 用普通系统线程读输出，只要几十 KB）。10 个终端约 100MB。
- **MCP：** 对，就是 §0.1 D，在 Electron 里就能做，约 200MB。
- **知识库：** 这次快照里没看到它占大块，没有证据，要量了再说。
- **换底层解决不了的：** CLI 约 5GB 不变；界面和 GPU 约 0.5GB 不变（WebView2 也是 Chromium，终端也一样用 xterm.js 加 WebGL）。
- **账算下来：** 在 Electron 里修 node-pty 漏线程加 D，FF-pane 自身从约 1.5GB 到约 0.7GB；全部换成 Tauri + Rust，大概是 0.5–0.6GB，代价是重写整个主进程。所以换底层是个折中：多省约 100–200MB，但要几个月；并且现在最大的那一块不用换也能修掉。

## 1. 现状

- **Claude 窗口每个约 900MB**（920、884）。照这个数，10 个 Claude 窗口光 CLI 就要约 9GB。Codex 窗口约 260MB。
- dev 专用约 430MB（electron-vite、两个 pnpm），打包版没有。Tony 选择继续用 dev 测试，这部分不动。

已有的：

- 每个窗口的进程数和内存：`terminal/manager.ts` 已经在量，`ffpane_list_windows` 给管理者看。
- 开窗门槛：`workbench/resource-guard.ts`，可用内存低于设置值就拒绝开新窗口（默认 1GB）。

jcode 省内存，是因为一个后台进程托管所有会话。Claude Code、Codex 的进程模型我们改不了。我们能改的是：**同时活着的 CLI 进程少一点，界面进程瘦一点。**

### 1.1 2026-10-27 再量一次（Tony 说 Electron 占 4GB、CPU 也高，想换底层）

当时 FF-pane 没有打开的窗口，按进程树归属（只读，没关任何进程）：

| 谁 | 进程数 | 私有内存 | 累计 CPU 秒 |
|---|---|---|---|
| **Codex 桌面版**（`ChatGPT.exe`，OpenAI.Codex 26.928，也是 Electron） | 20 个界面进程 + 子进程 | **约 11.4GB**；单个页面进程 2.6、2.4、1.9、1.5、1.1GB | 约 17000，其中一个页面进程 8761 |
| FF-pane dev 残留两份（10-24 16:42、10-25 00:45 起的 `pnpm dev`） | 各 3 个：主进程、GPU、网络；**没有界面进程、没有窗口** | 各约 410MB，共约 820MB | 主进程 2525 / 267 |
| 本机 | — | 31.8GB，剩 15.9GB | — |

结论和下一步：

- 任务管理器里的「Electron」不一定是 FF-pane：Codex 桌面版也是 Electron，占得多得多，CPU 也主要是它。要先分清 Tony 看到的 4GB 是哪个程序。
- FF-pane 有**关不干净的残留**：两份 dev 的主进程和 GPU 进程还在，但界面进程没了。可能是界面进程崩了（主进程还在，`window-all-closed` 不会触发），也可能是关窗没退出。要查：残留怎么来的；界面进程崩了以后主进程该退出还是重开窗口。
- 同日查到崩溃记录，崩溃和内存冲高另写成 [主进程内存与白屏修复计划](./主进程内存与白屏修复计划.md)（T11.0d），本计划仍管「少开 CLI 进程、界面瘦身」。
- 下次 Tony 正常开着团队时，按 §2 的办法当场量一次（按进程树分 FF-pane / Codex 桌面版 / CLI），再决定要不要谈换底层。
- 画板现在打开时把所有原图转成 base64 读进界面（见 [画板计划](./画板无限画布与待检查计划.md) §2），打开过画板的界面进程会大很多；剖析时开、关画板各量一次。

## 2. 第一步：剖析（不改功能）

先查清界面进程的 1.25GB，再决定怎么改，不猜。

1. dev 和打包版（`out/`）各开同样的 3 个窗口，记界面进程内存。差值就是 dev 自身的开销。
2. 抓渲染端堆快照（DevTools Memory），按构造函数看大头：xterm 缓冲、WebGL、React 状态里的大数组、画板图片、markdown 渲染。
3. 数 WebGL 上下文：每个终端一份（`TerminalView.tsx` 的 `tryLoadWebgl`）；GPU 进程 192MB 也一起看。
4. 切换标签十次、开关画板十次，看内存回不回落（查泄漏）。
5. 主进程：每个窗口 1MB 输出缓冲（`terminal/types.ts` 的 `DEFAULT_OUTPUT_BUFFER_BYTES`），确认关窗后释放。
6. Claude 窗口：同一窗口开新会话时、聊 2 小时后、压缩后各记一次内存，看是否随会话长度涨。

产出：`docs/验收记录/内存剖析-<日期>.md`，列出前三个大头和各自的改法，再按结论排第 4 步。

## 3. 第二步：空闲窗口休眠（收益最大）

10 个窗口里同时干活的通常只有三四个。空闲的先关掉进程，窗口留着，要用时续接回来。

### 3.1 什么窗口能休眠

全部满足才休眠：

- 状态空闲（不是忙、等批准、出错待处理），且空闲超过设定时间（默认 15 分钟，设置里可改、可关）；
- 收件箱没有未读；
- 没拿着 `ffpane_lock` 的锁；
- 不在在线监管（`ffpane_wait_events` 挂着的不算空闲）；
- 角色是执行、检查、规划、普通。**管理者、监管者不休眠**（他们靠等事件干活）；
- 运行时支持按编号续接：Claude、Codex 支持；Grok 没核实前不休眠；
- 有原生会话编号（没聊过的窗口直接关进程，唤醒时冷启动）。

### 3.2 休眠和唤醒

- 休眠：先确认输入框空（`prompt-ready.ts`），再结束 CLI 进程树（现有 Job 圈禁）。窗口、标题、角色、上级关系、会话编号都留着。窗格显示「休眠中」和一个「唤醒」按钮，终端区显示最后一屏（回放缓冲）。
- 唤醒的时机：
  - 有消息投给它（`send_message`、`report`、`broadcast`、`nudge`、拍板结果）；
  - 用户点「唤醒」，或在窗格里打字；
  - 管理者调 `ffpane_restart_window`。
- 唤醒走现有续接路径。消息等到输入提示出现再投递，并照常核对提交（1.0.9 的机制），保证不丢。
- `ffpane_list_windows` 多一个状态「休眠」；管理者说明加一句：休眠的窗口照常发消息，平台会叫醒它。

### 3.3 代价（写进设置说明）

- 唤醒要几秒（Claude 启动慢于 Codex）。
- 休眠久了提示词缓存过期，唤醒后第一轮多花一些 token。
- 所以默认 15 分钟，不设得更短。

## 4. 第三步：开窗排队

现在内存不够就直接拒绝开窗。改为：

1. 不够时，先挑可休眠的窗口（§3.1）里空闲最久的休眠掉，再量一次；
2. 够了就开，返回里写明「为开这个窗口休眠了 X」；
3. 还不够才拒绝，原因照旧。

界面上每个窗格显示内存（数据已有），超过 1.5GB 标黄，方便 Tony 看出谁最占内存。

## 5. 第四步：界面进程瘦身

按第一步的结论做，候选：

- WebGL 只给看得见的终端；看不见的退回 DOM 渲染或直接卸载。
- 参考 cc-pane：看不见的终端 5 分钟后撤 WebGL，30 分钟后把画面存下来、销毁 xterm，切回来再恢复。
- 画板图片用缩略图，看大图时再载原图。
- 修第一步发现的泄漏。

## 6. 第五步：推荐配置

只读角色（监管者、规划）推荐用 Codex，约是 Claude 的三分之一。监管者已经这样。管理者说明里补一句，不强制。

## 7. 验收

1. 剖析记录写完，前三个大头有数据。
2. 开 10 个窗口（4 个在忙、6 个空闲）：15 分钟后 6 个空闲的进入休眠；记录前后总内存。
3. 给休眠的执行发消息：唤醒后接上原会话（记得之前的内容），消息只投一次、已提交。
4. 拿着锁的、有未读的、在线监管的窗口不休眠。
5. Codex 窗口休眠期间被 Codex 桌面版归档，唤醒仍接回原会话。
6. 可用内存不足时开新窗口：先休眠空闲窗口再开，返回写明休眠了谁。
7. dev 和打包版各过一遍。

## 8. 风险

- 误杀正在干活的窗口：只看平台给的真实状态，不看终端文字；进程结束前再查一次状态。
- 唤醒时续接失败：走 1.0.10 已有的退路（找不到就开新对话，交接里写明），并提示 Tony。
- 休眠后用户以为窗口挂了：窗格上写清「休眠中，收到消息会自动唤醒」。
